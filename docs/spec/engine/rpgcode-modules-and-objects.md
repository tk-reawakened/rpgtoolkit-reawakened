# RPGCode: modules and objects

Two related areas of the language, each with rules the VM needs fixed because a restored snapshot must resolve every call and every member the same way the original run did:

- **Modules** — what a program's other files contribute to it: includes, redirection, and the order in which two definitions of the same name are chosen.
- **Objects** — classes, their members and methods, how an object is created, looked up, dispatched, inherited and freed.

The language itself is in [rpgcode-language.md](rpgcode-language.md); error handling in [errors and threads](rpgcode-errors-and-threads.md).

**How to read this page.** A plain paragraph says what Toolkit 3.1 does. A block opening with the words **Reawakened rule** is a deliberate addition or difference of this project ([ADR 0007](../../adr/0007-docs-spec-is-the-normative-specification.md), decision 2); where it is a departure from 3.1 it says so.

## Modules

A module rule decides what a program's other files contribute to it.

### Includes

* `#include "file.prg"` or `include("file.prg")`. Only functions and classes are imported; loose top-level code in an included file does not run. The include root is `Prg/` under the project folder, and a name with no path separator resolves there. — legacy behaviour (R2-Q21). **Reawakened rule:** resolution and matching go through the asset resolver, so the `Prg/` root, its subfolders and the ASCII-only fold are the one path rule the readers and the scripts share; the legacy reader used the name exactly as written.
* **Implicit include (MOD-2).** `file.func(args)` queues `Prg/file.prg` for inclusion while the program is loaded, and only then is `func` a name to call. — legacy behaviour (R2-Q21); it corrects the earlier "on first use" reading.
* **A `file.`-qualified call binds to that file (MOD-2), after object binding. Reawakened rule — a departure from 3.1.** The compiled call site records the file. At run time, if the qualifier names a live dictionary object, its member is read and called first (the object model takes precedence); otherwise the file is queued for inclusion and `func` is resolved among that file's own definitions first, then the ordinary order applies (a built-in before a script function). This object-first precedence matches PKG-4's namespace rule and prevents an unrelated `d.prg` asset from hijacking a real dictionary `d` member. *Rejected alternative:* always trying the file first, which lets adding or renaming an asset silently change an existing object's call. The compiled call stores the folded file name, so a restore reproduces the fallback binding.
* **Hoisting and include position.** Definitions are hoisted within their file, so a function may be called earlier in that file than its definition. A literal `#include` is collected wherever it appears in the file — even inside a function or a branch that never runs — and applied when that file's parse ends, so a call written before the `#include` line still resolves once the file is loaded. — legacy behaviour (R2-Q21). A computed `include(expr)` runs at run time, and its file's definitions are available from that point on.
* **One flat list of script functions (MOD-1) — Reawakened rule, a deliberate departure from 3.1.** `#include`, an implicit `file.func` call, and the first run of a file each add that file's functions to a single flat list of script-function names at that moment. When two entries in that list share a name and parameter count, the **last one added wins**. A `file.`-qualified call bypasses the flat list and reaches that file's own definition. Every override raises a warning naming the old and the new definition. This is the owner's last-wins rule (R-41) kept on purpose: legacy kept the *first* definition and silently skipped a later one of the same name and parameter count (R2-Q21, R1-Q9), and the divergence is recorded here so a later fidelity review can reverse it. <!-- OWNER: MOD-1 / entry 3.8 — alternatives: adopt the legacy first-wins ordering (silent skip) or keep the owner's last-wins ordering with a warning (decided). The unqualified-after-include question is answered below: an include merges the file into the program, so the unqualified name is reachable once the include has been read. -->

### Includes: repeats, cycles, missing files and visibility

Ruled by entry 3.8, doc-first:

* An included file is merged into the including program, so its functions and classes become part of that program and an unqualified name in it is reachable once the program is loaded. — legacy behaviour (R2-Q21).
* The same include name is added once; a repeated include does not add its definitions a second time. — legacy behaviour (R2-Q21, which matched the exact text at load time). **Reawakened rule:** matching is on the folded path, at load and at run time alike, so one file included under two spellings is still one file.
* An include inside a function is allowed but has no scoping effect: it is a program-wide include. — legacy behaviour (R2-Q21).
* A missing file is ignored silently at load time; an empty file imports nothing and is not an error; `include()` of a missing file at run time raises a runtime error. — legacy behaviour (R2-Q21).
* An include cycle is not guarded in legacy: each included file is parsed afresh and cached only after its own parse finishes, so A including B including A recursed without end. — legacy behaviour (R2-Q21, inferred). **Reawakened rule:** an include whose file is already being parsed is treated as already included and reported as a cycle diagnostic, so parsing always terminates; a rebuild must not hang or crash on a cycle.
* **Reawakened rule — where a run-time include list lives (MOD-3):** the ordered list of files a program has included at run time is part of that program's compiled record, and the program's source hash covers its main text plus that list, so a restore rebuilds the same include set before any call resolves. (The compiled record is rebuilt from the program reference on restore; that reference needs a field for the list — see the open questions in [rpgcode-language.md](rpgcode-language.md).)

### Redirects

* `redirect("oldName", "newName")` remaps a function name globally, including built-ins. `killRedirect("name")` and `killAllRedirects()` undo it. The legacy `#`-prefixed operands and an implicit `file.method` target (`#redirect(#a, #b.c)`) are dialect forms ([rpgcode-dialects.md](rpgcode-dialects.md)).
* There is one redirect table for the whole run. — legacy behaviour (R2-Q22); **Reawakened rule:** the VM holds it as its `redirects` state section, so it travels in a saved game and a snapshot restores it.
* `redirect`, `killRedirect` and `killAllRedirects` take effect when source text is parsed, in textual order, and only on text parsed after them; a program already compiled keeps its old bindings. — legacy behaviour (R2-Q22). **Reawakened rule — a restore stays faithful:** the redirect table in force when a program is compiled is recorded in that program's compiled record and folded into its cache key, so recompiling after a restore uses the same table; if the current table no longer matches, the program is recompiled and the state-restore mismatch policy restarts the thread from source.
* A target may be a built-in name; after substitution the name is looked up like any other call name. — legacy behaviour (R2-Q22).
* There is no chaining: one substitution is made, so with a→b and b→c the name a becomes b only. — legacy behaviour (R2-Q22).
* A target of the form `file.func` also queues that file for inclusion. — legacy behaviour (R2-Q22).
* A redirect stops applying only through `killRedirect`/`killAllRedirects` or by loading a saved game, never because a program ended. It applies to call syntax only. — legacy behaviour (R2-Q22).
* **Reawakened rule:** redirect names fold like every other name (the ASCII fold), so a redirect and the call it matches agree on every runner.

**References.** R2-Q21, R2-Q22, R1-Q9 (`docs/provenance/facts-round-2.md`, `docs/provenance/facts-round-1.md`); §1.5 (paths and the ASCII fold) in `docs/spec/`; the pre-compiled refusal in [../formats/rpgcode-program.md](../formats/rpgcode-program.md); AD-5 and AD-7 (`redirects` state section), AD-17 (host boundary) in the architecture spine.

### Pure-RPGCode plugins and middleware (MOD-4) — Reawakened rule

**Status (entry 19.1, 2026-10-19; ruled; built by entry 19.8).** `registerPlugin(pluginDefinition)` below is the explicit, layered route to wrap an engine command. It is a thin layer over the environment table of [FUN-8](rpgcode-language.md#keywords-and-structure) (entry 18.5): it computes the interception and the saved `original` for the author, and it is never a second dispatch mechanism ([PKG-5](#pkg-1)). The route an author takes by hand with the environment table itself (store a callable under a command's name, and save the one it replaced with `bindingOf`) stays valid and is not replaced: [Writing a middleware library today](#writing-a-middleware-library-today-entry-187) says how. The interceptor's `next` is its last parameter and the wrapper's own parameters are the ones before it. <!-- OWNER: MOD-4 — Jensen, 2026-10-19 (epic-rpgcode-platform Notes: ADR 0004 decision 8 names `registerPlugin` and it MUST be built; it is a thin layer over the 18.5 environment-table interception, never a second dispatch mechanism). Supersedes the 18.7 status that left it open for a later ticket. Rejected alternative: leave `registerPlugin` unbuilt and document only the reassignment recipe, which breaks the decision-8 promise. -->

RPGCode scripts can register custom commands and middleware interceptors via the built-in `registerPlugin(pluginDefinition)` function:

```rpgcode
registerPlugin({
    name: "audio-blips",
    commands: {
        message: (text, next) => {
            playSound("blip.wav");
            next(text); // yields to next plugin layer or native built-in
        }
    }
});
```

* **Onion middleware composition.** Multiple plugins wrapping the same command compose into an ordered chain (`Plugin A -> Plugin B -> Native Built-in`). When an interceptor runs, the engine provides `next` as a callable parameter representing the next layer down. Calling `next(...)` forwards execution and arguments to that layer.
* **No global monkey-patching.** Plugins register explicitly through the plugin registry rather than overwriting global variables or command tokens. Variable assignments (`message = 5`) do not alter or clobber command dispatch. **Proposed ruling (pending owner review; entry 18.5):** the one assignment that does take effect on a command name is storing a *callable* under it, which the environment table in [rpgcode-language.md](rpgcode-language.md#keywords-and-structure) (FUN-8) honours for the running scope; that is the lighter, per-scope way to wrap a command and it does not replace `registerPlugin`, which stays the explicit, layered route with `next` chaining and does not depend on it. <!-- OWNER: MOD-4 — 2026-10-18, entry 18.5: the plan's scope (a) asks for callable reassignment of command names, which this bullet's earlier wording ("overwriting global variables") did not distinguish from a plain-value assignment. Rejected alternative: leave the bullet silent, so two spec pages would appear to disagree. -->
* **Waiting commands.** When `next(...)` calls a command that yields or waits for user input (such as `message` waiting for a keypress), the calling thread suspends inside the interceptor frame. Under rule **G1**, this suspended frame serializes to plain JSON so mid-tick game state can be saved and restored cleanly.
* **Lifecycle (OWNER).** Plugins register during startup initialization (e.g. from an `init.prg` or project manifest, or, for a package, at package start-up in manifest order, [PKG-5](#pkg-1)). The registered plugin table is **established by the game startup sequence** before saved threads resume, on a new game and again on every restore: package code is governed by the installed package version and is never frozen into a save (the actor rule: save data and names, hydrate behaviour). See point 3 of the next bullet. <!-- OWNER: MOD-4 — Jensen, 2026-10-19 (director ruling on PR #286): layers a package registers with `registerPlugin` are rebuilt at start-up from the installed packages in manifest order and are not saved; keeps the 2026-10-18 "established by start-up" text. Rejected alternative: save the layers as values, which runs stale package code against a newer package version. -->
* **What `registerPlugin` is, precisely (entry 19.1; the four points entry 18.7 found unruled; mechanism ruled by entry 19.8).** *What it does for a game author:* it is the tidy way to wrap engine commands: you give each command a function that does its own work and then calls `next` to pass the call down to the layer below, and the engine takes care of the bookkeeping that the recipe below does by hand. *Precisely:* `registerPlugin(def)` takes a dictionary (OOP-10) with a `name` and a `commands` dictionary of command name to interceptor, and for each command, in the dictionary's enumeration order, does in effect what the recipe does: it finds the binding below (the top layer already registered for the command, else the engine's own binding, see [How the layers are held](#registerplugin-layers-entry-198)) and puts in front of it a wrapper callable that runs the interceptor with `next` set to that binding. Nothing else dispatches: a call goes through the one table ([PKG-5](#pkg-1)). Points 1, 2 and 4 are **Proposed rulings (pending owner review; entry 19.1)**; point 3 is owner-directed. (1) **`next` is the interceptor's last parameter**, and the wrapper's arity is the interceptor's arity minus one, so the wrapper takes exactly the arguments a call of the command passes (the arity rule of 18.7); `next` is the saved binding, a callable that runs the layer below. *Rejected alternative:* append `next` only when the interceptor's definition accepts it (the 18.5 rejection: it needs a second storage beside the variable and an arity rule that changes with the definition). (2) **`commands` is a dictionary and each entry is one layer;** two entries are registered in enumeration order, a later registration of the same command is the outer layer (the same order as reassignment), and an entry that is not a callable is a catchable runtime error (`callable.not-callable`) that registers nothing, not even the entries before it. *Rejected alternative:* a list of pairs, which duplicates what a dictionary already is. (3) **(OWNER, Jensen 2026-10-19 via director review) Package layers are rebuilt, not saved.** Layers registered by an installed package through `registerPlugin` are **rebuilt at start-up from the installed packages in manifest order** and are **not saved**; a save records only the package names and versions in force, so a restore against different installed versions can report a diagnostic on mismatch. A script's own 18.5 reassignment (a global holding a callable under a command name, the recipe below) is ordinary script state and still saves as values per 18.6. *Rejected alternative:* save the package's layers as values, which freezes package code into saves and runs stale code against a newer package version. Entry 19.8 builds the first half (the layers are held outside every save and rebuilt by start-up, below); the save record of package names and versions and the mismatch diagnostic wait for the package loader ([PKG-7](#pkg-1)), because the engine has no package loader and no installed package version to record yet. (4) **`name` is a label** (diagnostics and the `command.overridden` warning), not a key: two registrations may share one, and `registerPlugin` returns a dictionary `{ name, remove }` whose `remove` callable takes the registration's layers out of their commands (it returns `1`, and `0` when they were already removed) and keeps every other layer, **for this session only** (the next start-up rebuilds the layer from the installed package). A layer another registration put in front of a removed one keeps working and reaches the layer below the removed one. *Rejected alternative:* `unregisterPlugin(name)`, which is ambiguous when names repeat.
<a id="registerplugin-layers-entry-198"></a>
* **How the layers are held, reached, saved and removed (entry 19.8).** *What it does for a game author:* a layer a package registers is part of the running game's setup, not of your saved game. The game rebuilds every package's layers each time it starts, before any saved script resumes, so a saved game that was waiting inside a layer carries on inside the rebuilt one. *Precisely:*
  * **The layer table is session data, never state.** The registered layers live in the script services of the running game (the layer table), beside the command registry, and never in `GameState`: no field, no schema or compiler bump, nothing in a save and nothing in a state hash (G1). Each layer has an id `L<n>` and each registration an id `R<n>`, both from one counter of the table, so the same installed packages registering in the same order make the same ids on every start.
  * **How a call reaches a layer.** The first entry of the environment table is the running scope's own callable variable (FUN-8); the same entry then offers the top registered layer of the name. `resolveCall` receives one `held` callable exactly as before and gains no entry, no argument and no tier. A callable variable the scope holds therefore runs ahead of the package layers (it is a deliberate override of the scope, or it was made after them); `bindingOf(name)` answers that variable if there is one, else the top registered layer, else the engine's own binding, so a hand-written wrapper installed after a package covers the package's layers and reaches them through its `original`. A handle that names a command by its own name (the engine's binding) runs the engine's command only and skips every layer, as it did before. A call written `namespace.name(...)` ([PKG-4](#pkg-4)) reaches the commands the package's manifest definition lists, not the layers of a `registerPlugin` call.
  * **The layer below.** At registration the layer below is the top layer already registered for the command; if there is none, the engine's own binding (a built-in, a script function or a command a plugin claims, the same answer `bindingOf` gives with no variable in the way). It does not depend on the scope that called `registerPlugin`, so a package registers the same layers from any frame. A command with no binding at all is `unknown.command`, as for `bindingOf`.
  * **The wrapper.** A wrapper is a callable whose `def` is `plugin.layer:<id>` (no script can write that name) and which captures nothing. Calling it appends the layer below as the last argument and runs the interceptor on the calling thread, exactly as an indirect call does: a wait inside the interceptor, or inside the command that `next` reaches, parks that thread inside the interceptor's frame; by-reference arguments reach the interceptor's `&` parameters; `end()` unwinds. A call with *n* arguments needs an interceptor with *n* + 1 parameters; anything else is `callable.arity` naming the command and both counts. A wrapper whose registration was removed passes the call to the layer below unchanged.
  * **Saving and restoring.** A save holds no layer. A saved thread that is parked inside an interceptor holds its frame and its `next` as ordinary values; a `next` that names a layer holds the layer's id. To resume it the host first **establishes the layers by running every package's start-up program, in manifest order, on a fresh state, before it loads the saved state** (the core helper is `runPackageStartup`; a new game does the same on its own fresh state). Start-up is deterministic and runs on a fresh state in both cases, so it makes the same layer ids and the same closure cells (`cell<n>`) as the first run did, and the loaded state's cells and handles agree with the rebuilt table. Start-up does not draw random numbers and does not wait (it runs the threads phase only, so the clock does not move); a start-up program that has not finished after its slices, or that waits, stops the run with `package.startup-unfinished`. A layer registered after start-up is not rebuilt, so a handle to it in a save is `callable.unknown-def` naming the layer when it is called.

**#588 extension to `registerPlugin` — owner-approved provider keys, shared resolution and continuation.** The approved menu-provider facet is `menuProviders`, separate from `commands`, keyed by exactly `main`, `items`, `equipment`, or `abilities`; each supplied value is a callable screen provider with the semantics in [E-80](plugins-and-battle.md#e-80). A provider replaces the complete screen for its key, without `next`; the shared cross-language registry applies the same ordered winner to direct calls and nested entry. An omitted key or empty provider dictionary contributes nothing; if the `stock_menu` package is loaded, its provider remains active for every unoverridden screen. Without a custom provider or a loaded stock provider, a direct facade call raises catchable `menu.provider-missing` and leaves `MenuSection.screens` unchanged. It uses the same registration identity, `{ name, remove }` handle, all-or-nothing validation, startup rebuild, and session-only lifetime as the `commands` facet. `commands` remains a required dictionary but may be empty (`commands: {}`), permitting menu-only registrations; empty `commands` and `menuProviders` dictionaries install no entries. Removal excludes an RPGCode override from future winner selection and exposes the preceding provider or, if present, the loaded stock default; an already-entered frame may finish only in the current runtime. Runtime removal is not saved, and restore fails with `restore.menu-provider` if a saved current or parent continuation identity is absent from startup-rebuilt registrations.

The RPGCode provider receives one read-only menu context and runs as a nested call on the requesting script thread. `MainMenu()`, `ItemMenu()`, `EquipmentMenu()`, and `AbilitiesMenu()` select the matching provider key; `InternalMenu(0/1/2/4)` maps to those calls. The native TypeScript `PluginDefinition` exposes the same provider property and keys; its `MenuProvider(input: MenuProviderInput) => MenuProviderResult` callback is invoked once for each `enter`, `input`, or `child.closed` event. Its continuation state and `menu.screen` wait are plain data, allowing the same thread to resume through normal wait resolution; Promise/closure continuations are not used or saved. The required `commands` array may be empty (`[]`) for a menu-only package, and an empty `menuProviders` map registers no overrides. See the exact transition, exception, compute, identity, and restore rules in [E-80](plugins-and-battle.md#e-80).


#### Writing a middleware library today (entry 18.7)

**What it does for a game author.** A middleware library is a `.prg` file that changes what an engine command does for the whole game: a weather library that puts the weather in front of every message, an audio library that tags every message with the music playing, a HUD library that holds the screen for a moment before a message shows. A game installs several of them, in order, and each one hands the call on to the one before it, ending at the engine's own command. A library never edits the game's scripts, and the game's scripts never mention the libraries. Four working examples, written only in RPGCode, are in `packages/core/test/fixtures/plugins/` (`weather-system.prg`, `audio-stems.prg`, `pace.prg`, `hud-log.prg`, with `key-gate.prg` for a command that waits for a key); `boot.prg` installs them and `game.prg` uses them.

**The recipe, precisely.**

* **Shape of a library.** The file defines one install function and nothing else, because `#include` imports functions only and a loose top-level statement of an included file does not run. The start-up program `#include`s each library, calls each install function once, and then ends by `run()`ning the game. `run()` ends the calling program, so the wrappers are made by a program that no longer exists when the game uses them; they keep working because a callable's owning program is saved with it (`vm.defOwners`, [FUN-8](rpgcode-language.md#keywords-and-structure)).
* **Shape of a wrapper.** The install function declares `local(original)`, sets `original = bindingOf("name")` and then `name = (params) => { ... original(args) ... }`. The saved handle `original` is a captured local, so it is a cell of the closure and not a global, and a second library using the same local name does not collide with it. The wrapper's parameters are the command's parameters, and it takes exactly the arguments a call passes (a call with another count is `callable.arity`); a parameter the command writes back (for example `wait(&key)`) is declared with `&` so the value reaches the caller's variable, and without the `&` it is lost.
* **Order.** Libraries are installed in call order, and the one installed last is the outermost layer: a call runs layers from the last installed to the first, then the engine, and returns in the opposite order. Two layers that change the text do not commute, so the install order is part of a game's behaviour.
* **Several commands.** A wrapper may call another wrapped command; the call goes through that command's layers too (a HUD layer's `sleep(1)` is stretched by a layer wrapped around `sleep`).
* **Waiting.** A wrapper may wait, and the original it calls may wait; either way the script thread stays stopped inside the wrapper's frame and the saved game holds that frame (G1). A save taken then restores and finishes exactly as the unsaved run does.
* **State.** Handles the library stores in globals (`weatherSet`, `weatherNow`) and the wrapper that holds the same local share one cell, so a change made through one is seen by the others ([FUN-8](rpgcode-language.md#keywords-and-structure), "Captured locals share one cell"). Two installs of the same library make two sets of cells.
* **Removing a layer.** Storing the saved handle back under the name (`mwin = original`, as `hud-log.prg`'s `hudRemove` does) puts back the layer that was covered and keeps every layer under it. `kill(mwin)` does not do that: it removes the variable, so every layer installed under the name goes with it and the engine's own command runs bare.
* **Saving.** The layers are values in the game's variables and cells, so a saved game carries them and a restore does not need the libraries to be installed again; the restore does need the library files, because the saved handle names a definition that is compiled from them again (a missing file is `program.missing`). This differs from the lifecycle line above, which describes `registerPlugin`'s table being established again at start-up.
* **Determinism.** A layer is ordinary script: it runs on the fixed tick, under the step budget, with the seeded random numbers and no clock, so two runs of the same game from the same seed give the same state hash on every tick (G3), and the headless golden `synthetic-11-middleware` pins one such run.

## Packages (PKG-1 to PKG-8) — Reawakened rule

**What it does for a game author.** A package is a named, versioned bundle of RPGCode that adds commands, objects and event listeners to a game. The stock battle and the stock menu are packages. Your game lists the packages it uses in its plugin list; when two packages define the same command the one later in the list wins and can hand the call on to the earlier one. A package can only reach the outside world the way any script does, through the engine, and it declares in its manifest which outside things it asks for (reading a file, playing a sound) so a runner can show that list the way a phone shows app permissions.

**The rules, precisely.** Entry 19.1; built by entries 19.6 to 19.9. Where this section and a native plugin pack agree, there is one mechanism.

<a id="pkg-1-one-manifest"></a>
* **PKG-1 — one manifest, one dispatch (OWNER).** A package is an entry of the one plugin manifest (`PluginManifest`, `packages/core/src/script/manifest.ts`), the same ordered list that selects the native packs. There is no second list and no second dispatch: a command call resolves through the single environment table (FUN-8, entry 18.5) whether a native pack or a package supplied the command. AD-8's later-wins rule is the order rule: manifest order is layer order, the later entry's handler runs first and reaches the earlier one through `next`, and a repeated name raises one `command.overridden` warning. *Evidence:* ADR 0004, decision 6 and the `manifest.ts` header. *Rejected alternative:* a separate package list beside the plugin manifest, which gives one command two orderings and AD-8 no single place to apply.
* **PKG-2 — what a package is (OWNER fields).** A package has a **name**, a **version**, a **namespace** and its **declared host requests**. **Ruling (OWNER; entry 19.1) — the field spelling:** the manifest entry gains `name` (the entry's `id`, a lower-case ASCII identifier: letters and digits with `-` or `_` separators, so `stock_battle`, `stock_menu` and `stock_rpg` are valid; owner amendment 2026-10-21 records the lower-case underscore grammar the stock packages use), `version` (a string compared for equality only; no ordering is implied), `namespace` (an identifier of the same grammar; the default is the folded name) and `requests` (a list of host-request kind names). The existing `enabled` and `options` stay. The header's "no version field" line of `manifest.ts` is replaced by entry 19.6. *Rejected alternative:* semantic-version ranges and dependency resolution between packages, which is a package manager the owner has not asked for and which a game's single ordered list does not need yet. **Built (entry 19.6; `packages/core/src/script/manifest.ts`).** An entry is a package entry exactly when it carries `version`; `namespace` and `requests` without a `version` are a located `manifest.package-version` diagnostic. A package name and namespace must match `^[a-z][a-z0-9]*(?:[-_][a-z0-9]+)*$` — a leading letter, then letters and digits separated by a single `-` or `_` (`manifest.package-name`, `manifest.namespace`), `requests` a list of distinct kinds of the one runner-request union (`manifest.request-kind` names an unknown or repeated kind). Two packages whose namespaces fold to the same ASCII-lower-case text are a `manifest.duplicate-namespace` diagnostic at the later entry, on parse and on patch. `listPackageDeclarations` returns the declarations as plain data in manifest order; the host resolver reports a package whose installed definition has a different `version` string as `plugin.version-mismatch` (equality only). Core loads nothing.
* **PKG-3 — the main file names the packages (OWNER).** The packages a game names are the TKR package-list extension of the main file ([main-file.md](../formats/main-file.md#tkr-package-list-extension)); entry 19.9 reads and writes it and feeds the manifest ([E-02 step 3](main-loop-and-startup.md#reawakened-boot-sequence)). The legacy plugin rows (37 and 38) stay data: the menu and battle names map to the `stock_menu` and `stock_battle` packages in memory ([E-02 step 3](main-loop-and-startup.md#reawakened-boot-sequence)) and every other legacy name names no package. **Proposed ruling (pending owner review; entry 19.1):** listed packages are appended after the engine's default entries, in listed order, so a game's package wraps the engine's own commands and a later listed package wraps an earlier one. *Rejected alternative:* the list replaces the default manifest, which would drop the engine's own packs from any game that names one package.
<a id="pkg-4"></a>
* **PKG-4 — namespaces (entry 19.7).** *What it does for a game author:* every package has a namespace, by default its name, and `weather.rain()` always runs the `rain` that the `weather` package supplies, even when a package later in your plugin list also supplies a `rain` and so wins the plain call `rain()`. *Precisely:* the **exports** of a package are the commands its definition lists (a command and its aliases); a package's script functions and objects join the same lookup, by the same rule, when the package loader of PKG-7 supplies them. A call `namespace.name(args)` runs that package's **own layer** of `name`, not the top layer of the name, and the layer's `next` reaches the layer below the package in manifest order (a package that wraps `name` can still pass the call down). The namespace is a read-only view over the effective manifest, not a stored object: it adds nothing to `GameState`, to `vm.objects` or to a save, and a restore needs only the manifest to rebuild it, so G1 holds and no golden moves. An unqualified call resolves through the one environment table (FUN-8) exactly as before: the later package wins. **AD-8's single-warning rule holds:** two packages that supply the same name raise one `command.overridden` warning when the registry is assembled, naming the earlier and the later package, and a qualified call raises none. **Where it sits in the order (Proposed ruling, pending owner review; entry 19.7):** a qualified call whose qualifier is a package namespace and does not name a live object is a call into that package; a live object of the same name keeps the object-first rule of MOD-2 (a variable the script made is explicit, and a parameter always shadows). The namespace is chosen ahead of the `file.` qualifier, and when the program's file table also holds `namespace.prg` the first call the namespace serves raises one `namespace.hides-file` warning naming that file (once per namespace and file in a run; the warning is a log record, not state). If the named package supplies nothing under `name`, the call is the `unknown.command` failure naming `namespace.name`; it does not fall back to the file, to another package or to the unqualified table, since that would let one spelling reach different code. **Order and removal.** The result depends only on the effective manifest: the same packages installed in another order give another, equally fixed result (the later wins the plain call), and a package that is removed or disabled in the manifest contributes no layer and no namespace, so the plain call reaches the binding below it again and `namespace.name` is `unknown.command`. Namespaces compare ASCII-folded; a repeated namespace is refused when the manifest is parsed ([PKG-2](#pkg-1)) and again when the registry is assembled. The engine's default packs are not packages and have no namespace. *Evidence:* the manifest is the explicit declaration; MOD-2's implicit file include only guesses from the text; `registry.ts` already keeps each name as a stack of layers, so a package's own layer is the layer of its plugin id. *Rejected alternatives:* the file first, which lets dropping an unrelated `.prg` into `Prg/` change which code a package call reaches; a stored dictionary object per namespace, which would put manifest data into every save and make a save depend on which packages were installed when it was written.
* **PKG-5 — `registerPlugin` is a layer over the 18.5 environment table (OWNER).** See [MOD-4](#pure-rpgcode-plugins-and-middleware-mod-4--reawakened-rule): `registerPlugin(pluginDefinition)` computes the interception and the saved `original` for the author and never adds a dispatch mechanism of its own. A package runs its `registerPlugin` calls at package start-up, in manifest order. *Rejected alternative:* a registry that dispatches ahead of or beside the table, which makes a call's target depend on which mechanism touched the name last.
* **PKG-6 — declared host requests are informational (OWNER; trust baseline).** A manifest lists the host-request kinds the package uses (G2: every external effect is a host request; file input and output goes through the AD-17 sandbox) so a runner may show them. Nothing is refused: RPGCode packages are trusted because the VM contains them ([ADR 0008](../../adr/0008-rpgcode-packages-and-trust-baseline.md)). **Proposed ruling (pending owner review; entry 19.1, Assumption A-4) — an undeclared request:** a package that issues a request it did not declare is not refused and the Logger does not warn; the declaration is data for the runner, not a check. *Rejected alternative:* refuse or warn on an undeclared request, which is a capability model the owner has deferred and would give a false sense of a boundary the VM, not the manifest, enforces.
* **PKG-7 — where a package's code comes from (Assumption A-1).** **Proposed ruling (pending owner review; entry 19.1):** a package is a folder inside the project, referenced by name from the manifest, loaded by the host (core loads nothing, G2); how packages reach the editor is not decided here. *Rejected alternative:* a zip or archive form, which adds an unpacking step the owner has not ruled on.
* **PKG-8 — per-package step counters (OWNER: the data lands now).** Entry 19.13 counts every VM instruction executed by a frame whose `ProgramRef.owner` is a package name; an instruction in a callable uses the owner carried by that callable and its recorded `vm.defOwners` entry. The optional plain-data `vm.stepCounters` map is keyed by package name and stores non-negative integer totals; it is absent until the first owned instruction. The counters add across threads and survive snapshots/restores. The debug adapter view is Epic 10. The counters are excluded from `hashState`, so no existing golden moves. **Evidence:** the counters describe how a result was reached, not the result, and two runs that differ only in which package ran a step must still hash the same. *Rejected alternative:* include them in the hash, which re-records every script golden for data that has no effect on play.

<a id="emit-1"></a>
## Events and emitters (EMIT-1 to EMIT-22) — Reawakened rule

**What it does for a game author.** Every object in RPGCode can emit and listen to events. Emits can be cancelable, and listeners may change the event. A shield can listen for a hit and halve the damage; a quest script can listen for a character falling and award something. You add a listener with `on`, remove it with `off`, listen once with `once`, and send an event with `emit` (the game carries on) or `emitCancelable` (the script waits for every listener, then gets the event back and can see whether a listener cancelled it). There is no bubbling and no capture: an event goes to the listeners of the object it was sent on and to nobody else. If you want a quest script to hear about an actor, the stock actor package re-emits its actor event on the game under its package namespace.

**The rules, precisely.** Entry 19.1; built by entries 19.10 to 19.12. Everything an emitter holds is plain JSON (G1); nothing here uses a Promise, a generator or a host callback (G1, G3).

* **EMIT-1 — the model (OWNER).** The emitter is an object capability in the style of Godot signals and Node's EventEmitter: `on`, `off`, `once`, `emit` and `emitCancelable` (names approved 2026-10-19). There is no bubbling and no capture. *Rejected alternative:* DOM-style capture and bubbling through a parent chain, which needs a tree the objects do not have and makes order depend on it.
* **EMIT-2 — the commands (OWNER, Jensen 2026-10-19 party decisions: every object in RPGCode can emit and listen, in method syntax).** The **method form is normative**: `hero.on("damage", fn)`, `game.on("fallen", fn)`, `hero.once("type", fn)`, `hero.off("type", fn)`, `hero.off("type")` (every listener of that type), `hero.emit("type", detail)` and `hero.emitCancelable("type", detail)` (which returns the event object). `on`, `off`, `once`, `emit` and `emitCancelable` are **host-provided methods hydrated onto every object** by the rule of [OOP-12](#oop-12), so no closure is saved for them (G1) and, per OOP-12, a data field of the same name shadows the method (an author's own `on` key keeps working, and the free-function alias below still reaches the emitter). Being methods, they are bound callables (OOP-11). An emitter is any object (a dictionary, a class instance, an actor, a board) and the built-in `game`. **Equivalent alias:** the free-function form with the emitter first, `on(emitter, "type", fn)`, `emit(emitter, "type", detail)` and the rest, is the same operation. `fn` is a callable; it receives the event object as its one argument and keeps its own receiver (OOP-11). `detail` is a dictionary and may be left out. *Rejected alternative:* a free-function-only form, which contradicts the owner's model that every object can emit and listen.
* **EMIT-3 — a plain emit is queued (OWNER).** `emit` appends the event to the queue and the emitting script carries on at once; no listener runs inside the `emit` call. Listeners are run later by the dispatcher in the order events were queued, and for one event in the order the listeners were registered. A listener that emits appends to the same queue (no recursion; an event queued during dispatch is delivered after the events already queued). **Proposed ruling (pending owner review; entry 19.1) — when delivery happens:** in a named `events` phase of the tick that queued the event if the emit happened in an earlier phase, else in the next tick; the phase's place in the AD-26 list is reconciled by entry 19.15. *Rejected alternative:* delivery at the end of the emitting step, which is a synchronous side door and puts a listener inside the emitter's step budget.
* **EMIT-4 — adding and removing listeners, also during dispatch (OWNER; plan entry 19.10).** `on` appends to the emitter's listener list for that type. `once` registers a listener removed just before it first runs; removing a `once` listener before it fires prevents it from firing. `off(emitter, type, fn)` removes the first listener of that type whose callable equals `fn` (same `def`, `captures` and receiver); `off(emitter, type)` removes all of that type. A removal made while that type is being dispatched means a listener that has not yet run for the event in progress is skipped, and one that already ran is unaffected; a listener added during dispatch does not run for the event in progress and runs from the next event. Registering the same callable twice registers two listeners. Dispatch fixes the list of listeners at its start, so these outcomes do not depend on timing. *Rejected alternative:* live iteration of the changing list, whose result depends on where an insert lands.
* **EMIT-5 — a cancelable emit (OWNER).** `emitCancelable` parks the emitting thread (a G1 wait: plain JSON in the `vm` section, saveable at any step) until every listener has run in registration order, then returns the event object. A listener may call `cancel()` or change fields of the event (a shield halves a damage field). **Proposed ruling (pending owner review; entry 19.1) — a cancel does not stop later listeners:** all listeners still run and see `canceled` set, so the order of listeners decides what the final fields are, not whether they run; the emitter reads `canceled` afterwards. *Rejected alternative:* stop at the first cancel, which would let one listener silently hide the rest and makes registration order change whether other listeners run. **Proposed ruling (pending owner review; entry 19.1):** `cancel()` on a non-cancelable event (a plain emit, or the `error` event) is a catchable runtime error, not a silent no-op, so a mistaken cancel is seen. *Rejected alternative:* ignore it quietly.
* **EMIT-6 — the event object.** **Proposed ruling (pending owner review; entry 19.1):** the event is a dictionary (OOP-10) holding `type`, `target` (the emitter), `detail` (a dictionary), `cancelable`, `canceled`, and the bound method `cancel`. One event object is shared by all listeners of that dispatch, so a listener's change to `detail` is seen by the next listener and by the emitter that gets the object back. A plain emit holds a copy of `detail` made at emit time (nested objects stay handles), so a later change by the emitter does not alter a queued event. *Rejected alternative:* a fresh copy per listener, which would make "a shield halves the damage" invisible to the code that applies it.
* **EMIT-7 — one bus, no side door (OWNER).** RPGCode and TypeScript plugins share one queue and one listener table. A TypeScript plugin listens through the package its manifest declares (a native listener is registered by the host when the package starts), never by passing a closure into core state; its listener is called by the same dispatcher in the same order, and its emits enter the same queue. There is no synchronous path to a listener from either language.
* **EMIT-8 — which objects are built-in emitters (OWNER; Epic 8.1 ruling).** The built-in emitters are the game, boards and actors, plus the **party and inventory** as the only additional built-in emitters. Party roster events are emitted on `party`; `itemAdded`, `itemRemoved` and `goldChanged` are emitted on `inventory`. No other engine or package object becomes a built-in emitter by this ruling. A stock actor package may re-emit `fallen` on `game` as its namespaced `stock-rpg.fallen` event; core emits only actor-scoped `fallen`. *Rejected alternative:* making every engine object an emitter, which widens the saved shape without an approved need.
* <a id="emit-9"></a>**EMIT-9 — the game `error` event (OWNER).** Every runtime error is also emitted on the game emitter, like `window.onerror`: type `error`, `detail` `{ code, message, file, line, handled }`, non-cancelable. It is fired in addition to ERR-2 handling and does not catch or replace the script's handler; it fires whether or not a handler caught the error (`handled` says which). See [ERR-2](rpgcode-errors-and-threads.md#err-2--which-failures-are-errors-and-which-are-catchable). Entry 19.12 builds it. **Proposed ruling (pending owner review; entry 19.1) — details:** the event is queued like a plain emit; an error raised while delivering an `error` event is handled as usual but is not emitted again, so a faulty listener cannot loop; `file` is the program's file name and `line` its line, an empty string and `0` where the failure has no program. *Rejected alternative:* emit synchronously from the point of failure, which runs a listener inside the failing step.
* **EMIT-10 — the G1 check (OWNER; AD-32).** The event bus is asynchronous because a queued dispatch is plain JSON: the queue, each emitter's listener table (callables are `CallableValue` records, so a listener is data) and the dispatch cursor (which event, which listener index, the list fixed at dispatch start) are state in an owned `events` section, and the parked emitter of a cancelable emit is the `event.dispatch` wait of its thread in the `vm` section ([EMIT-5](#emit-1), [EMIT-16](#emit-16)), with registration order as the only order. A save taken between any two steps, including between two listeners of one dispatch, restores and finishes exactly as the unsaved run does. No state-machine problem is expected; the spike of entry 19.2 verifies it, and if it finds one this ruling and AD-32 are revisited before entries 19.10 to 19.12 are refined. A listener runs under the step budget like any script (R-33); a listener the budget interrupts continues next tick and the dispatch waits for it. *Rejected alternative:* the earlier AD-32 wording, a synchronous priority-ordered `world.eventQueue`, which puts a listener inside the emitter's step.
* <a id="emit-11"></a>**EMIT-11 — engine-originated cancelable emits (OWNER, Epic 20).** An emit made by the engine in a phase with no script thread to park runs its listeners in registration order in a short dispatch inside that phase, under a step budget, and never waits on input; a listener that would wait for input is a catchable runtime error. A script-thread invocation may use the ordinary script scheduler and waits. *Rejected alternative:* park the engine phase itself, which would stop the tick.
* <a id="emit-12"></a>**EMIT-12 — custom event types, and events declared by an asset or a package (OWNER, Jensen 2026-10-19: points 1 and 4; the rest Proposed).** *What it does for a game author:* you can invent your own events on any object, for example a wolf that emits `howled`, and nothing has to be set up first. An enemy, character or package can also list the events it sends, so the editor can offer them and the engine can warn you about a misspelt one. *Precisely:* (1) **Any string is a valid event type on any emitter**, built-in or script-made; sending or listening to a type nothing else knows is not an error (EMIT-2). (2) **Proposed ruling (pending owner review):** an asset that produces actors (character, enemy, NPC, board sprite) and a package manifest may carry an optional list of **declared event types**: a name and, optionally, the detail fields it carries. Legacy 3.1 files declare none and load as before, as the audio settings block does for the main file (21.2); the field spellings are ruled with the actor inventory (20.2). (3) **Declarations are data on the asset or the package, never on the object:** they are read by name on load, like OOP-12 hydration, so they add nothing to a save and a missing package loses only its declarations. (4) **Declarations are advisory at runtime (OWNER, Jensen 2026-10-19).** When an emitter's type declares a list, `emit` or `on` of a type outside it, and outside the built-in types ruled in 20.1, gives a located diagnostic `emit.undeclared-type` and still runs; an emitter whose type declares nothing gets no diagnostic. The engine never refuses a type. Strictness is a tooling concern: the language server and editor read the declared lists (and EMIT-13) for warnings on a misspelt type and for autocomplete, handed to Epics 10 and 11. (5) A package that declares the name of a built-in event type is a manifest diagnostic, so a custom `fallen` cannot pass for the real one. *Rejected alternatives:* a strict list that refuses an undeclared type, which contradicts the product sentence that every object can emit; declaring events only in script, which gives the editor nothing to read; storing declarations on the actor, which would put them in every save.
* <a id="emit-13"></a>**EMIT-13 — standard events (OWNER for naming, Jensen 2026-10-19; Epic 8 and Epic 20 for their rows).** *What it does for a game author:* one list of every event the engine and the stock packages send, so you know what you can listen for and what it carries. *Naming convention (OWNER):* a notification is past tense lowerCamelCase (`fallen`, `revived`, `statusChanged`, `leveledUp`, `entered`, `left`, `talked`); a cancelable pre-event is `before` plus the present (`beforeDamage`, `beforeEnter`, `beforePlay`); an event emitted on an actor needs no prefix (the target scopes it); an event a package emits on a shared emitter (game, board, media) carries the package namespace prefix. Each epic that adds an event adds its row here; an event not in this table remains valid as a custom type, with the EMIT-12 declaration diagnostic. `fallen` is core and fires only on the transition into the fallen state; `defeated` belongs to the battle package. Board `beforeEnter` is cancelable and engine-originated listeners cannot wait on input. `dialogue.completed` is the Epic 8 wrapper completion event; the stock RPG package bridges it to actor-scoped `talked`.

### How a queued emit is delivered (EMIT-14, EMIT-15) — entry 19.10

**What it does for a game author.** `emit` never runs a listener on the spot. The game carries on, and a moment later in the same tick (or at the start of the next one, see below) every listener of that event runs, one after another, in the order you added them. A listener is an ordinary script callable that gets the event; it can wait, call other functions and emit more events like any other script. Add a listener with `on(emitter, "type", fn)` or `emitter.on("type", fn)`, remove it with `off`, and use `once` for a listener that should run a single time.

**The rules, precisely.** Every row below is a **Proposed ruling (pending owner review; entry 19.10)** that builds EMIT-3, EMIT-4 and EMIT-10 and rules what they left open. Everything the emitter holds is plain JSON (G1).

* **EMIT-14 — the commands and the events phase.**
  * **The commands.** The free-function aliases of EMIT-2 are the built-ins `on(emitter, type, fn)`, `once(emitter, type, fn)`, `off(emitter, type, [fn])` and `emit(emitter, type, [detail])`; entry 19.11 adds `emitCancelable(emitter, type, [detail])` and `cancelEvent(event)` ([EMIT-16](#emit-16), [EMIT-17](#emit-17)). The method forms `emitter.on(type, fn)` and the rest do the same thing and are bound callables when read without a call (OOP-11, OOP-12). The emitter is any live object (a dictionary or a class instance) and must be one, or the call is the catchable `object.invalid`. `type` is a string, any string (EMIT-12), and any other value is `builtin.bad-arg`. `fn` must be a callable, or the call is `callable.not-callable`. `detail` is left out or is a dictionary, and anything else is `builtin.bad-arg`. The four commands `on`, `once`, `off` and `emit` return `0`, do not wait and run no listener. A data field of the object with the same name as a method wins on a method call and on a read (OOP-12), and the free-function form still reaches the emitter. A class that declares a method or field of that name wins too.
  * **Registering.** `on` appends a listener (the type, the callable and `once` = no) to the end of the one listener table, so registration order is the order of the table. `once` appends one with `once` = yes. The same callable registered twice is two listeners. `off(emitter, type, fn)` removes the first listener of that emitter and type whose callable equals `fn` (same `def`, `captures` and receiver, EMIT-4), and `off(emitter, type)` removes every listener of that type; a call that matches nothing does nothing and is not an error.
  * **Emitting.** `emit` makes the event object now: a new dictionary (OOP-10) whose keys are, in order, `type`, `target` (the emitter), `detail`, `cancelable`, `canceled` and `cancel` (a callable bound to the event, [EMIT-16](#emit-16)), the middle two `0` for a plain emit (the `cancelable` emit is EMIT-16). `detail` is a new dictionary holding a copy of the given one made at that moment (nested objects stay handles, EMIT-6), or an empty dictionary when none was given. The event is appended to the queue as the emitter and the event object. The event object and its `detail` are alive while the event is queued or being delivered, and are then ordinary garbage (R-34).
  * **The `events` phase.** AD-26 adds the `events` phase immediately after `threads`; the complete ordered list is defined in [the Reawakened phase rule](main-loop-and-startup.md#reawakened-phases): `input`, `waits`, `threads`, `events`, `movement`, `edges`, `triggers`, `animation`, `audio`, `time`. EMIT-3's "delivery in the tick that queued the event if the emit happened in an earlier phase" is therefore exact: an emit made by input, waits, threads or a listener is delivered in that tick's `events` phase (as far as the budget below allows), and an emit made by a later phase is delivered in the next tick's. Entry 19.15 reconciles the spine and the shared barrels.
  * **The dispatcher.** The engine, not a script loop, runs the delivery. Each time it takes the oldest queued event and fixes the list of listeners at that moment: those of that emitter and that type, in table order (EMIT-4: the list does not depend on timing; a listener registered after the event was queued but before it is taken **is** in the list, and one registered after it is taken is not). It then runs the listeners of the list in order. Before a listener runs, the dispatcher checks that it is still in the table: one that was removed since the list was fixed is skipped, and a `once` listener is removed from the table just before it runs. Each listener runs on a new thread of kind `persistent` owned by the world, whose one statement calls the listener with the event object as its only argument, so a listener has its own frames and error-handler slot, may wait, and keeps the receiver its callable carries (OOP-11). A listener that takes a number of parameters other than one is the catchable `callable.arity`, and a listener whose `def` names a command runs that command with the event.
  * **The budget and waits.** The listeners the dispatcher starts in one `events` phase share one `STEP_BUDGET` (R-33). A listener that finishes inside the budget is followed in the same phase by the next listener and then by the next event. A listener the budget interrupts, or that waits, carries on in the following `threads` phases like any thread, and the dispatcher waits for it to finish before the next listener or event, so nothing is delivered out of order. The dispatch cursor is the saved state of that wait. No delivery happens while a blocking command waits (R-32): the phase returns at once.
  * **Errors.** A runtime error in a listener is reported and handled as in any thread (ERR-2): the failing statement is skipped and the thread ends. It never stops the other listeners of the event or the later events.
  * **A freed emitter.** An emitter that is freed (`release`, or collected by R-34) loses all its listeners at that moment; events already queued for it are still taken but have no listener. The listener table never keeps its emitter alive. It does keep alive what each callable names: the cells it captures and its receiver (OOP-11), so a closure registered with `on` keeps its captured state for as long as it is registered.
* <a id="emit-15"></a>**EMIT-15 — the saved `events` section.** `events` is AD-10's section for the emitter (owner: entry 19.10; entries 19.11 and 19.12 extend it) and is saved at schema version 1 as `{ nextListener, listeners, queue, dispatch }`, plus `emitters` once a built-in emitter has been registered ([EMIT-20](#emit-20)). `nextListener` is the id the next registered listener takes and never goes down. `listeners` is the table in registration order, each `{ id, emitter, type, once, callable }` with `emitter` the text `object:<handle>`, or the key of a built-in emitter ([EMIT-20](#emit-20): `game` for the game), `once` a boolean and `callable` the callable record, never a closure (G1). `queue` is the pending events in order, each `{ emitter, event }` with `event` the handle of the event object. `dispatch` is `null` between deliveries and otherwise `{ emitter, event, order, index, thread }`: the event being delivered, the ids of the listener list fixed when it was taken, the position of the listener in progress and the id of its thread, or `null` when none is running. `emitters`, when present, maps each registered built-in key to the handle of its object ([EMIT-20](#emit-20)); like `cells` in the `vm` section it is absent until the first registration, so a state that never registered one keeps the shape it had, and no step migrates a save. A save taken at any step restores to a state that finishes exactly as the unsaved run does (EMIT-10), including between two listeners of one dispatch. A save made before the section existed loads with the empty section (`nextListener` 1, no listeners, an empty queue, `dispatch` `null`). Loading checks the shape, that every handle names a live object, that every `emitters` handle names a live object and no handle is registered under two keys, that every listener id is distinct and below `nextListener`, that `order` and `index` agree, that `dispatch.thread` names a thread, and each listener callable as any callable (FUN-8, entry 18.6). `reset()` clears the section with the `vm` section it refers to (E-06).
  The optional native-only `nativeDetails` map preserves the original plain
  detail values for native events while the script-visible event stores VM
  `Value`s: native booleans become script `1`/`0`, and native `null` becomes
  script `0`; native listeners receive the original boolean or `null` through
  the host event view. Its keys are decimal event handles and its values are
  the original detail records (including nested arrays/records). It exists
  only while a native event is queued or being delivered and is removed when
  delivery completes, when a queued or in-progress event is discarded, when
  its emitter is unregistered, or when an engine cancelable event is rejected
  for waiting or exceeding its budget. Restore validation, before any event
  is read, requires each key to be a positive safe integer naming a live event
  object and each detail to be a finite-number/boolean/string/`null` recursive
  plain-data value; malformed metadata is a `restore.shape` error. The map is
  optional and absent when no native event needs the sidecar, so this remains
  schema version 1 and older saves retain their shape.

### How a cancelable emit is delivered (EMIT-16 to EMIT-18) — entry 19.11

**What it does for a game author.** `emitCancelable` is `emit` that waits for the answer. The script sends the event and stops on that line while every listener runs, one after another, in the order they were added; then it carries on, and the call's value is the event. A listener can change the event (a shield halves `event.detail.damage`) or call `event.cancel()`. Afterwards the script reads `event.canceled` and the changed `detail` and acts on them. A cancel does not stop the other listeners; they still run and can see that the event was cancelled. Only the script that sent the event waits: the game and every other script carry on. The script resumes at the start of the tick after the last listener finished, so an event whose listeners all fit one tick costs the sender one extra tick. `emit` never waits.

**The rules, precisely.** Every row below is a **Proposed ruling (pending owner review; entry 19.11)** that builds EMIT-5 and EMIT-6 and rules what they left open.

* <a id="emit-16"></a>**EMIT-16 — the command, the event and the wait.**
  * **The command.** `emitter.emitCancelable(type, [detail])` and the free-function alias `emitCancelable(emitter, type, [detail])` take the same arguments as `emit` and fail the same way (`object.invalid`, `builtin.bad-arg`; EMIT-14). The call parks the emitting thread and, when the wait ends, returns the event object (a dictionary, OOP-10).
  * **The event.** It is made exactly as `emit` makes it (EMIT-14) and appended to the same one queue, so a cancelable event is delivered in queue order with every other event, by the same dispatcher, to the same list of listeners fixed when it is taken (EMIT-14), with `cancelable` set to `1`. Every event, plain or cancelable, ends with the key `cancel`: a callable bound to the event whose definition is the built-in `cancelEvent`, so `event.cancel()` is the call of EMIT-17. A cancelable event does not introduce a second saved shape: the `events` section remains schema version 1 (EMIT-15); only native events may additionally use its optional `nativeDetails` sidecar.
  * **The wait.** Queueing the event and parking the thread are one operation, so a thread that has queued a cancelable event is always parked on it (no step lies between the two for a save or a step-budget stop to fall in). The thread takes the named wait `{ kind: "event.dispatch", global: false, id: "emitCancelable", payload: [<event handle>], resumeRefs: [] }`, registered through the AD-9 wake contract like every other kind and kept in the `vm` section as plain JSON (G1). It is never `global`, not even on a blocking thread: a global wait stops delivery (R-32) and the event could never be delivered.
  * **The wake.** The waits phase polls the wait with the one resolver (AD-9): it is done once the event is neither queued nor the delivery in progress, which is after its last listener ran, was skipped or finished. The thread then resumes with the event object as the value of the call. A listener that waits, or that the budget interrupts, keeps the delivery in progress, and the emitter keeps waiting. An event queued behind other events waits behind them.
  * **Latency.** The waits phase comes before the threads phase and the `events` phase after it (EMIT-14), so an emitter that parks in tick T and whose event is delivered inside that tick's `events` phase resumes in tick T+1: one tick, whatever the number of listeners, as long as they finish inside the phase's budget. The spike of entry 19.2 measured 1.97 ticks with a hand-built wait; the first-class wait removes the second tick. *Rejected alternative:* resuming the emitter inside the tick that delivered the event, which needs the threads phase to run twice and changes THR-3's one-turn-per-tick rule.
  * **Liveness.** The event object and its `detail` are alive for as long as a thread waits on it (R-34), as they are while the event is queued or being delivered. A thread killed while waiting does not stop the delivery.
  * **Cost.** The emitting thread pays only the call itself, because the listeners run on their own threads under the dispatcher's budget (EMIT-14): measured in the engine test, `r = h.emitCancelable("damage", { dmg: 50 })` costs its thread 14 steps (a plain `h.emit(...)` 15), and a listener costs 15 steps for a one-statement body (one dispatch of 1, 3 and 8 such listeners fits an `events` phase budget of 15, 45 and 120 steps). The 19.2 spike measured about 39 steps per listener with a script-built dispatcher; its per-fighter figures (three listeners 219 steps of a tick, eight 591, leaving 435 and 63 under `STEP_BUDGET`) are the bound the test holds the dispatcher to.
* <a id="emit-17"></a>**EMIT-17 — `cancel`.** `event.cancel()` and the free-function alias `cancelEvent(event)` set the event's `canceled` to `1`, return `0` and never wait. Cancelling twice is the same as once. A cancel does not stop later listeners (EMIT-5): they run, see `canceled` `1`, and may change any field. The catchable errors: `builtin.bad-arg` when the argument is not an event object (a live dictionary with the keys `cancelable` and `canceled`); `event.not-cancelable` when `cancelable` is `0` (a plain `emit`, or the non-cancelable `error` event of EMIT-9), so a mistaken cancel is seen (EMIT-5); `event.not-dispatching` when the event is not the one being delivered at that moment (a listener that kept the event and cancels it after the delivery, or before it). The emitter, once resumed, only reads `canceled`.
* <a id="emit-18"></a>**EMIT-18 — a cancelable emit from a listener.** The dispatcher waits for a listener's thread to finish before the next listener or event (EMIT-14). A listener that parked on a cancelable event would wait for an event queued behind its own delivery, and the two would wait for each other for ever, stopping all delivery. So `emitCancelable` called on the thread running a listener is the catchable runtime error `emit.reentrant`; a listener that needs another listener's answer uses a plain `emit` (queued, delivered after this event), or starts a thread that sends the cancelable event. *Rejected alternative:* a stack of dispatch cursors that delivers the nested event at once, which changes the saved `dispatch` shape (EMIT-15) and is not needed until a game asks for it.

### The game emitter, the registration seam and the TypeScript side (EMIT-19 to EMIT-22) — entry 19.12

**What it does for a game author.** `game` is an emitter every script can reach by that name. `game.on("error", fn)` hears every runtime error the engine reports, with the error's code, message, file and line and whether an error handler of yours took it, the way a web page hears `window.onerror`; your own code and the stock packages use `game` for events that belong to the whole game (`game.emit("quests.questDone", { ... })`). A TypeScript plugin shipped with the game can listen on `game` and emit on it too. Its listeners and events join the same queue and the same listener order as yours, so a script cannot tell which language sent an event, and the plugin cannot make a listener run on the spot any more than a script can. Boards and actors become emitters through the same registration (Epic 20 does that).

**The rules, precisely.** Every row below is a **Proposed ruling (pending owner review; entry 19.12)** that builds EMIT-7, EMIT-8 and EMIT-9 and rules what they left open.

* <a id="emit-19"></a>**EMIT-19 — the name `game`.** `game` is an engine-backed name (a Reawakened addition beside `threads[i]`, [virtual variables](rpgcode-language.md#virt-1)) that reads as the game emitter: an ordinary dictionary (OOP-10) in the handle table with no members of its own, so a script may keep its own fields on it. It is made the first time anything needs it (a read of `game`, an `error` event, a TypeScript emit) and is the same object for the rest of the run; a read never makes a second one. `game.on(type, fn)`, `on(game, type, fn)` and the other forms of EMIT-2 and EMIT-14 work on it like on any object. Writing to `game` follows VIRT-1. Its key in the listener table is `game` ([EMIT-20](#emit-20)).
* <a id="emit-20"></a>**EMIT-20 — built-in emitters and the registration seam.** A **built-in emitter** is an object that a section owner has *registered* under a key. The game is the first (key `game`); entries 20.4 and 20.9 register one per board and per actor under the owner-namespaced keys `board:<id>` and `actor:<id>`. Registering a key that is already registered returns its object and changes nothing; registering a new key makes a dictionary object (OOP-10) and records the key and its handle in the section's `emitters` ([EMIT-15](#emit-15)). The engine keeps a registered object alive for as long as it is registered, whether or not a script names it (R-34). Listeners of a built-in emitter are filed in the one listener table under its key, not under `object:<handle>`, so a TypeScript package can name `game` before its object exists ([EMIT-21](#emit-21)) and the key means the same after a restore. A script reaches the object by whatever name its owner gives it (`game`, [EMIT-19](#emit-19)); every method of EMIT-2 works on it. The owner *unregisters* a key when the thing it names goes away: the key's listeners are dropped and the object is no longer kept alive (it is then ordinary garbage, EMIT-14, "A freed emitter"). `reset()` forgets every registration with the rest of the section ([EMIT-15](#emit-15)); the owner registers again when it starts again. Nothing registers a built-in emitter for the party or the battle (EMIT-8).
* <a id="emit-21"></a>**EMIT-21 — the TypeScript side of the bus (EMIT-7).**
  * **Listening.** A package definition may list *native listeners*, each `{ emitter, type, command }`: an emitter key, an event type and the name of one of its commands. An `emitter` may instead be the one pattern `actor:*`, meaning every actor emitter of the session: the dispatcher matches the pattern against the event's key, so the listener keeps its place in table order, is stored as plain data with the listener table, and is never filed under a key that does not exist. No other pattern exists: any other use of `*` in an emitter is a located `plugin.listener-bad-emitter` warning and registers nothing. A script's `off` names a concrete emitter, so it never removes a pattern listener. When the package starts (when the engine builds the script services for the resolved packages: boot, `reset` and a restored save), each listener is added to the listener table as an ordinary listener of that key and type whose callable is `{ def: <command>, captures: [], receiver: null }`, in package order and then in listed order, so it sits in the same registration order as every script listener. A table that already holds a listener with that key, type and `def` is not given a second one, so a restore does not double it. The dispatcher runs it like any other listener (EMIT-14): on its own thread, with the event object as the command's only argument, in the events phase, never inside the call that made the event. The command reads the event through the plugin view (the read-only game state of the command view); it changes nothing directly (AD-8).
  * **Emitting.** A command that wants an event sent reports the plain-data effect `{ kind: "emit", args: [<emitter key>, <type>, <detail>] }`. When the command returns, the VM appends the event to the one queue exactly as a script's plain `emit` does (EMIT-14): a new event object whose `detail` is a new dictionary holding the given fields. The key is `game` or a registered built-in key ([EMIT-20](#emit-20)); the type is a string; the detail is left out or is a plain object whose fields are numbers, strings, booleans (stored as `1` and `0`) or `null` (stored as `0`). Anything else is the catchable `builtin.bad-arg`, and a key that names no emitter is `object.invalid`. The effect is recorded in the effect log under the kind `emit` with no section, because the events section's owner is the core itself.
  * **No side door.** Neither side can run a listener from the other's call. A TypeScript emit only appends to the queue, and a listener written in TypeScript runs only when the dispatcher starts it. The TypeScript side is never handed a callable, the listener table, the queue or the dispatcher. There is no cancelable emit from TypeScript (a command cannot park its calling thread on `event.dispatch`); a cancelable event is sent from RPGCode, and TypeScript listeners see it and may cancel it with `cancelEvent` like any listener ([EMIT-17](#emit-17)).
* <a id="emit-22"></a>**EMIT-22 — the `error` event in detail (EMIT-9).** The event is queued when the failure is reported, as a plain emit on `game` (EMIT-14, [EMIT-19](#emit-19)): type `error`, `cancelable` `0`, and `detail` a dictionary whose keys are, in order, `code`, `message`, `file`, `line` and `handled`. `code`, `message`, `file` and `line` are the host diagnostic's own (an empty `file` and `line` `0` where the failure has no program). `handled` is `1` when the failing frame's error handler took the error, which is a label handler whose label was found (control went to the label) or the resume-next handler (ERR-1), and `0` for every other case: no handler, a handler cleared because its label could not be found, and top-level code. The event is queued for every failure the host receives as a diagnostic, that is every catchable runtime failure of ERR-2, whatever the failing thread, and `debug(false)` does not stop it (`debug(false)` silences the interpreter's own log messages, not the diagnostic). A load-time problem and a refused load raise no `error` event, because no frame exists (ERR-2). An error raised by the thread that is running a listener of an `error` event on `game` is handled and reported as usual and is not emitted again, so a faulty listener cannot loop; an error in a thread that listener starts is emitted like any other. The event changes nothing the script's own handling does: the failing statement, the handler and the host diagnostic are as they were without it.

## Objects

```
class CName : CBase, COther {          // "struct" = class with public default
public:
    method CName(a, b) { m_field = a; } // constructor with its body in the class
    method ~CName() { clean(); }        // destructor
    method operator+(rhs)              // any operator except -> and .
    method operator[](i)
    method operator=(rhs)              // replacement for the plain handle store
    method operator$()                 // declared conversion operator; never consulted
    method virtualThing() = 0          // pure virtual (class becomes abstract)
private:
    var m_field                        // "var" declares a member inside a class
    var m_data[]                       // empty brackets declare a growable member array
    m_array[10]                        // fixed-size member array
}
method CName::CName(a, b) { m_field = a; }   // an out-of-class body is also accepted
obj = CName(1, 2);  obj->method();  obj->release();   // release() runs destructor and frees
```

Terms used below: a **class** is a set of members and methods; an **object** is a live instance named by a small number, its **handle**; a **member** is a stored field and a **method** is a callable definition; a **base** is a class another class inherits from; **dispatch** is choosing which method definition a call runs.

### Syntax (OOP-1, OOP-2, OOP-3)

* **A method body may be written inside the class** (the form used throughout the sample corpus) or as a body-less prototype in the class with a separate `method CName::CName(…)` definition outside; the two forms may be mixed. — legacy behaviour (R2-Q16 to R2-Q19). **OOP-1** covers the class, method and member declarations; **OOP-2** covers the two method-body forms, constructors, destructors and operator methods; **OOP-3** covers `this`, object values and `->` access. The §9.12 ruling groups OOP-1 to OOP-9 with entry 3.6's class-and-object rules.
* `var name` declares a member field; `var name[]`, with empty brackets, declares a member array that grows as it is assigned. `m_array[10]` declares one with an initial size.
* `this` names the current object inside a method; it is an ordinary object value that may be used and indexed, and `this[i] = …` reaches the object's `operator[]` like any other indexed assignment.

### Assignment between objects (OOP-4)

* An ordinary assignment stores the right-hand value, including its object handle and type, into the left-hand variable; afterwards both variables name the same object and no member is copied. — legacy behaviour (R2-Q16).
* If the left-hand variable currently holds an object whose class defines `operator=` taking one parameter, that method runs instead, with the left object as `this` and the right value as its argument, and the plain store does not happen; a class with no such method stores the handle silently. — legacy behaviour (R2-Q16).
* There is no copy constructor: a one-parameter constructor runs only when an object is built by name (`Cls(a)`), never as part of an assignment. Assigning a fresh construction to a variable that is unset or holds a non-object is a plain handle store. — legacy behaviour (R2-Q16). The earlier "copy constructor" wording is dropped, since neither the corpus nor the reading logic has one.

### Object lifetime (OOP-5)

* `release()` runs the destructor of the object's **own** class, and only if that class declared one; base-class destructors never run and there is no chaining. — legacy behaviour (R3-Q2, R2-Q17).
* **Reawakened rule — free after the destructor.** When the destructor returns (or at once, when the class has none), the object's members and its handle are freed. Legacy freed an object only when its class had no destructor, and otherwise left it alive; freeing it keeps state bounded, keeps snapshots small, and makes the handle table the whole of the object state.
* `kill(obj)` removes the variable name only: it runs no destructor and frees nothing at that moment. — legacy behaviour (R2-Q17).
* **Reawakened rule — unreferenced objects (R-34).** When no global, frame local, operand, member of another object or reachable closure cell names an object's handle, that object is freed at the end of the tick in which it became unreferenced, in a fixed order, and no destructor runs. Two objects that name each other are never freed. The object pass repeats until it frees nothing more, so an object that only a freed object named goes in the same tick: dropping a dictionary frees the dictionaries nested in it with it (entry 19.3). A cell that only a freed object named still goes in the next tick's pass, as the language spec rules (FUN-8). A closure cell counts only while a script can still reach the cell itself: the same end-of-tick pass first frees every unreachable cell, so an object that only such a cell named is freed in that pass ([the language spec](rpgcode-language.md#keywords-and-structure), FUN-8, entry 18.6). *In plain terms:* once nothing in your game can reach an object or a closure's private variable any more, the engine forgets it at the end of that tick, so a script that makes objects or functions all day does not fill the save. *Precisely:* every tick ends with one pass that frees the unreachable closure cells first and then the unreferenced objects, after the engine's `time` phase (the phase list of [the main loop](main-loop-and-startup.md) gains no phase of its own), and it is the same pass, in the same order, whether the full engine or the script-only host runs the tick. <!-- OWNER: R-34 — Proposed ruling (pending owner review): the pass runs once per tick after the `time` phase in the engine as well as in the script-only host, cells then objects. Evidence: the script host ran it and `createEngine` did not, so an object or closure cell made by a running game stayed in the state for ever and handle numbers (which depend on the handle table) differed between the two hosts. Rejected alternative: a tenth phase in the AD-26 list, which the phase-list test pins as the immutable order and which a collector does not need, as it reads only the VM state. --> *Legacy facts:* 3.1 kept members as global variables named `<handle>::<member>`, used a background collector that woke every ten minutes, and never ran destructors (R2-Q17); a deterministic per-tick pass replaces the timer because a wall clock cannot be snapshotted, and the format spec previously said objects were never collected.
* **Reawakened rule — what names an object (R-34, entry 19.5).** *In plain terms:* an object is kept while anything a running script can still reach holds it: a variable, a function paused in the middle of a call, the object a method is running on, or a stored function that remembers it. *Precisely:* the roots of the unreferenced-object pass are the global table and every closure cell still left, and in every thread's frames each frame's locals, operands and return value, the object a method, constructor or destructor frame runs on (its `this`), a wait's stored reply, and the object named by a reference that an operand or a by-reference parameter slot holds (`&obj->field` handed to a function names `obj`). A callable names its receiver wherever the callable sits, so a callable that is a member of a kept object names its receiver, and the receiver counts as named by that member even when the holder is only kept by a cycle: the pass never frees the receiver of a callable that a kept object holds, so a save taken after the pass loads. *Known limit:* an explicit `release()` (OOP-5) frees its object at once and leaves every callable that names it as receiver dangling; calling one is a catchable `object.invalid`, and loading a save that holds one is refused as `restore.callable-receiver`. *Evidence:* a cycle of two class instances that nothing else named, one of them holding `q.f` (a callable whose receiver is the dictionary `q`), lost `q` in the pass, and the next save was refused on load. *Rejected alternative:* counting only object values as incoming edges, which is what left that save unloadable.
* At program end (`end()`, or falling off the program's end) the program's frames are dropped and its objects are freed by the same pass; no destructor runs. — legacy behaviour (R2-Q17).
* **Reawakened rule — handle numbers.** A new object takes the smallest number that is not in the handle table and is greater than the table's size. With an empty table that is 1; with handle 1 live and handle 2 free, the next is 2; with handle 1 free and handle 2 live, the next is 3. The numbering rule is legacy behaviour (R3-Q2); the Reawakened part is that it needs nothing but the current handle table, because our always-free `release` keeps every freed handle out of it, so a restore allocates the same next number.

### Where a name resolves (OOP-6)

* Inside a method, a variable name is looked up in this order, first match wins: an explicit `:name` global; a parameter; a member field of the current object's class (its own and inherited, any visibility); then a frame local or, failing that, the global of that name. — legacy behaviour (R2-Q18).
* An unqualified call `f(...)` resolves in this order: a built-in; inside a method, a method of the current object's class with that name and parameter count (an implicit `this` call); a script function of the program or its includes; a plugin that claims the name; otherwise the unknown-call error. — legacy behaviour (R2-Q18). (A `file.`-qualified call is the one exception and reaches that file's own definitions first; see the module rules above.)
* **Reawakened rule — the environment table (FUN-8, entry 18.5).** At run time the lookups above are one table with one entry above them: the running scope's own symbol — the variable of that name a read would reach from the running frame (a local of that frame, else the global), when it currently holds a callable value — runs instead of everything below, which is how a script intercepts or replaces a command. A member field of the current object is not part of that entry; a callable stored in a member is called through its object (`obj.f(...)`). Below it the table keeps the legacy order for a built-in, a script function and a plugin command; the VM's own commands (the module directives and `bindingOf`) are answered before the table and are not part of it. Reading a variable is never this lookup. The full rule, `bindingOf`, and the way a captured local's cell is shared with its creating frame are in [rpgcode-language.md](rpgcode-language.md#keywords-and-structure) under FUN-8. <!-- OWNER: OOP-6 — 2026-10-18, entry 18.5. -->
* **Proposed ruling (pending owner review; entry 18.5) — where the implicit `this` method sits.** Today's VM consults the implicit method of step 2 only after the built-in, the script-function and the plugin lookups all find nothing, so a script function or a plugin command of the same name and parameter count is reached where legacy reached the method. The running scope's callable binding that entry 18.5 introduces is looked up before all of them, the method included. * The compile-time binding of a built-in also decides this order: a script method named like a built-in is never called at a compile-bound call site (R-35), and a definition that shadows a built-in raises a warning. The rule is stated in [rpgcode-functions.md](rpgcode-functions.md).
* `this` is available inside a method as an ordinary local named `this`, and `this->x` need not be written. — legacy behaviour (R2-Q18).
* Reaching a non-public member or method from outside its class is an error; the access levels are under OOP-9. — legacy behaviour (R2-Q18).

### Operator dispatch (OOP-7)

* The first operand decides: when it is an object, the interpreter looks in that object's class for `operator` plus the operator's symbol, taking exactly one parameter for a binary operator and none for a unary one; only the left operand is consulted, and the parameter count tells a unary form from a binary one. A missing method is a runtime error except where a rule below gives a fallback. — legacy behaviour (R2-Q19).
* `a == b` and `a ~= b` use `operator==` and `operator~=`, and fall back to comparing the handles when the method is missing. `a = b` uses `operator=`, else a plain handle store. `a[i]` uses `operator[]`, else a plain element variable. A compound assignment (`+=` and the rest) calls its own method (`operator+=`) and does not fall back to the plain binary method. — legacy behaviour (R2-Q19).
* `a[i] = v`: `operator[]` is consulted first on `a`; when it returns a reference, the store goes through that reference and `operator=` runs only if the referenced variable currently holds an object, and otherwise the value is stored directly. — legacy behaviour (R2-Q19).
* `->`, the ternary, call-style `()` and any string-or-number conversion operator are never dispatched; a `$` or `!` after a name is a sigil (the `operator$` and `operator!` declarations are never consulted for a conversion). — legacy behaviour (R2-Q19).

### Inheritance and construction (OOP-8)

* Only the constructor of the class named in the construction call runs; a base constructor never runs before or after it, and there is no base sub-object, so a derived constructor assigns inherited members itself. — legacy behaviour (R3-Q1).
* A derived class's own method (same name and parameter count) beats a base's; when several bases define the same name and parameter count, the earliest-written base wins. — legacy behaviour (R3-Q1).
* A call on an object uses the object's **actual** class, not the declared type of the expression. There is no syntax to call a method's base version; a call is a plain name and resolves to the override. — legacy behaviour (R3-Q1).
* **Reawakened rule — the transitive order.** A class's methods and members are its own definitions plus those of its ancestor classes. The ancestors are collected by a walk that takes each base list in declaration order and uses a class only the first time it is met; the class's own definition wins, and between two ancestor definitions of the same name the one met first in that walk wins. This is deterministic and independent of class names, replacing the legacy order that depended on how the class names happened to sort (R3-Q1, inferred for the transitive case).
* A method declared `= 0` is pure virtual and makes its class abstract. — legacy behaviour (R3-Q1). **Reawakened rule:** constructing an abstract class is a catchable runtime error of the invalid-object class in the failure table in [errors and threads](rpgcode-errors-and-threads.md).

### Access labels (OOP-9)

* A `class` body starts `private`; a `struct` body starts `public`; a member with no label takes the current access; the `public` and `private` labels switch it for the rest of the body. — legacy behaviour (R3-Q1).
* `protected` is not a word of the language. — legacy behaviour (R3-Q1). **Reawakened rule:** the loader rejects it with a located diagnostic, because a file that uses it is not valid 3.1 and ignoring it would quietly change a program's meaning.
* Access is checked at each access, at run time, and a blocked access is a catchable runtime error. An access from outside any method, or from a method running on a different class, needs `public`; a method of the same class may also reach `private`. — legacy behaviour (R3-Q1).
* The check compares class identities, not instances: any method of class `C` may reach the private members of any `C` object. — legacy behaviour (R3-Q1).
<a id="oop-10"></a>
### Dictionary objects and legacy classes on one storage (OOP-10) — Reawakened rule

**What it does for a game author.** A dictionary is a bag of named values you make on the spot, without declaring a class: `{ name: "Health Potion", healAmount: 50 }`. It is an object like any other. You pass it around, read and change its fields, store functions in it, and it is saved with the game. Classes you wrote the old way (`class` … `method`) work exactly as before; they are now just a kind of object built on the same storage.

**The rule, precisely.** The status "parses but has no runtime storage" of an earlier release is withdrawn: entry 19.3 built the storage for dictionaries (literals, member read and write, `kill` of a field, collection and save/restore) and entry 19.5 put legacy classes on it. Receiver binding is OOP-11.

```rpgcode
potion = {
    name: "Health Potion",
    healAmount: 50,
    use: (target) => {
        target.hp += this.healAmount;
    }
};
```

* **One storage for every object.** A dictionary literal creates an object in the same handle table that legacy class instances use (the `objects` list of the `vm` state section, `packages/core/src/script/state.ts`). A dictionary is an object with no class; its fields are its members. There is no second object runtime. *Evidence:* `lower.ts:292` refuses a dictionary literal only because that storage did not exist yet. *Rejected alternative:* a value-typed map stored inside a variable, which cannot be shared by two variables and so cannot back `this`, listeners or emitters.
* **Literals.** A key is a bare identifier or a string literal; the value is any expression, a callable included. Evaluating the literal creates the object, evaluates the values in written order, and gives the new handle. A repeated key keeps the last value.
* **Access.** `obj.key`, `obj->key` and `obj["key"]` are the same read and the same write (a write to a missing key creates it). `kill(obj.key)` removes the key ([`kill`, SEM-1](rpgcode-language.md#kill-1)). Every member of a dictionary is public: access labels (OOP-9) apply to classes only.
* **Assignment and equality** follow OOP-4 and OOP-7: assigning copies the handle, `==` compares handles unless a class defines `operator==`.
* **Legacy classes sit on the same storage (entry 19.5).** A legacy `class` instance is an object in the same handle table whose members are the declared fields of its class, tagged with its class and with the program that declares it. The 3.1-observable behaviour of OOP-1 to OOP-9 does not change; the legacy `<handle>::<member>` global naming is a 3.1 storage fact, not something to reproduce. Giving every object the one saved shape below changes the saved form of a class instance; entry 19.5 found no recorded golden state that holds a live class instance, so no golden is re-recorded (G5). This follows the initiative principle that 3.1 is a compatibility layer, not the model ([ADR 0009](../../adr/0009-compatibility-layer-not-the-model.md)). *Rejected alternative:* keep two object stores and make a class a different kind of thing; every later feature (emitters, hydration, receivers) would then need two implementations.
* **What a class instance holds (entry 19.5).** Its `members` are the declared fields of its class and of its ancestors, found by the OOP-8 walk and all set to the unset value when the object is made: a field that a class and an ancestor both declare is one member (the nearest declaration), a fixed array `m_array[10]` contributes the elements `m_array[0]` to `m_array[9]`, and a growable `var m_data[]` contributes the one member `m_data`, its elements joining the object as they are first written. Its `keys` list them in that order: the object's own class first, then each ancestor in the walk order, each class's fields in declaration order; members written later are appended as they are first written, as for any object. *Why the ancestors' fields are there:* the saved object then shows every field it has whichever constructor ran, and reading an inherited field nobody assigned still gives the unset value, exactly as before. *Rejected alternative:* make only the class's own fields at construction and let inherited ones appear on first write, which leaves the saved object depending on which constructor ran.
* **What is not saved (entry 19.5).** The class's methods, its constructor and destructor, its ancestors and the access label of each field are the class's declaration, not the object's data. The object names its class and the program that declares it; each use finds the declaration in the class table of the running program (a program's table holds its own classes and its included ones, MOD-1) and walks the ancestors by the OOP-8 rule, so a save holds data and names and never behaviour, as in OOP-12. If the class is not in that table when a method is called, the call is a catchable runtime error (`object.invalid`) and the object's data stays; a load never refuses a save for it. *Rejected alternative:* store the access labels with each object, which saves a copy of the class's declaration in every instance and lets the copy disagree with the program.
* **Two class identities, two jobs (entry 19.5).** *In plain terms:* when you call something on an object, the engine uses what the object really is; when it decides whether you may touch a private member, it starts from the class whose method is running. *Precisely:* the symbols a method finds on its object (which method an explicit call `obj->f()` or `obj.f()` runs, which `operator` method answers, whether a class is abstract, and inside a method the bare field name and the bare call `f()` of OOP-6) are found through the object's own class, the `className` of its record, wherever the object value came from, `this` inside a method an ancestor defined included (OOP-8: a call uses the object's actual class). So inside a method of `Base` a bare `step()` reaches the override of a `Kid` object, as `this->step()` does, and a bare name that only `Kid` declares as a field is that field. A bare name keeps the OOP-6 order (an explicit `:name` global, then a parameter of the running method, then a field of the object's class, then a local or a global), so a parameter shadows a field of the same name whichever class declares the field, and a by-reference parameter, or a parameter that a closure with no receiver captures, keeps shadowing it (a closure bound to an object, by `bindThis` or as a stored method, reads a field of its receiver before a captured name, as before this entry). The order of the lookup tiers (OOP-6, FUN-8) does not change. Access (OOP-9) is decided from the class of the running method, the class that defined it, which is an ancestor when the method is inherited and which the frame carries for that purpose; OOP-9 says how it is compared and this entry does not change it. The two are different information and are never merged. *Evidence:* inside a method that class `A` defines, on an object of class `C : A` that overrides `operator+`, `this + x` ran `A`'s `operator+`, because the object value carried the name of the defining class, and a bare `step()` in `Base` ran `Base`'s `step` for a `Kid` object although `this->step()` ran the override; and a field shadowed a parameter of the same name in the class that declared both, against OOP-6 (`method set(v) { return v }` returned the field). *Rejected alternative:* find the symbols through the class of the running method, which is what made those calls and names resolve to the ancestor; and letting a field only the object's class declares shadow a parameter, which breaks every method an ancestor wrote with a parameter of that name.
* **One set of rules per kind of object, one code path (entry 19.5).** An object with a class follows OOP-7 to OOP-9 as written: only declared members, access labels, `obj[i]` through `operator[]` or an element variable. An object with no class follows the dictionary rules above: any key, always public, `obj["key"]` the same as `obj.key`. Both kinds share the same member read, member write, call and collection; the only difference is whether the record names a class.
* **Calls through a name (entry 19.5).** `obj->name(args)` and `obj.name(args)` are the same call (EXP-7). For an object with a class it runs the method of that name and parameter count found by the OOP-8 walk (`release()` is the built-in of OOP-5); when the class has no such method, a callable stored in a member of that name is called with the object as its receiver (OOP-11); otherwise it is a catchable `object.invalid` ("method not found"). For an object with no class the member must hold a callable (`callable.not-callable` otherwise). In the dot form the name before the dot is found like any bare name (OOP-6): a parameter of the running method first, then a field of the object it is running on, then a local or a global, so `eng.get()` inside a method reaches the same `eng` as `eng->get()` (no further tier is added); inside a closure the qualifier of a `file.name()` call is never captured (FUN-8), so there `eng.get()` and `eng->get()` can differ. *Evidence:* before this entry `a.get()` on a class instance did not run its method, because the dot form was read as a file call (MOD-2), while `a->get()` did, and a field `eng` was not seen by `eng.get()` for the same reason. *Rejected alternative:* keep dot calls dictionary-only, which leaves one call with two meanings depending on how the object was made.
* **`kill` of a field (entry 19.5).** `kill(obj.field)` and `kill(obj->field)` remove the field from an object of either kind (KILL-1); `kill(obj["field"])` removes the key of a dictionary, while on a class instance `obj["field"]` is the element variable of OOP-7, not the field, so it does not remove the field. On an object with a class the removed field stays declared: it reads as unset afterwards and writing it again puts it last in `keys`. Before this entry `kill(obj->field)` did nothing on a class instance.
* **Proposed ruling (pending owner review; entry 19.1) — reading a key that is not there.** The read gives the unset value, like a missing array element (ERR-2, "sparse arrays"); it is not an error. *Evidence:* the arrays row of the failure table, and `obj["key"]` is already the array-style form. *Rejected alternative:* a catchable runtime error, which makes the common "is this key set yet" test need a handler.
* **Proposed ruling (pending owner review; entry 19.1) — enumeration order.** Keys are enumerated and saved in the order they were first written; removing and re-adding a key puts it last. *Rejected alternative:* sorted key order, which hides the order an author wrote and makes a save differ from a replay that wrote keys in another order only for display.
* **How it is stored (entries 19.3 and 19.5).** Every object is one record in the `objects` list with these fields: `handle`; `className` (the class's folded name, or `""` for a dictionary); `program` (the reference of the program that declares the class, `null` exactly when `className` is `""`); `members` (a plain JSON object); and `keys` (the member names in enumeration order, each member exactly once). `keys` is saved because a JSON object does not keep an order a script can rely on (a key such as `"2"` is always listed first) and the state hash sorts keys. A literal compiles to `newObject`, then each value and an `initMember` in written order: the object is made first, so a nested literal's handle is the next one after its parent's. Every object keeps its place in the one handle table and the one end-of-tick pass ([OOP-5](#object-lifetime-oop-5), R-34). **Loading a save.** `restoreGameState` checks every record against that shape and refuses a save with a record that does not match, as `restore.shape` naming the place (for example `vm.objects[0].keys`): a `handle` that is not a distinct positive whole number, a `keys` list that is missing, repeats a name or does not name each member exactly once, a record with a class whose `program` is not a program reference, or a record with no class whose `program` is not `null`. A save written before entry 19.5 that holds a class instance has no `keys` for it and is refused the same way: the `vm` section keeps schema version 5 and no step migrates it, because the product has no released saves to protect ([ADR 0009](../../adr/0009-compatibility-layer-not-the-model.md)). *Rejected alternatives:* a version bump with a step that adds `keys` to every class instance, a shim whose only user would be a save no player has; and an optional `keys`, absent on class instances, which leaves two shapes of object for every reader and validator to tell apart.
* **Proposed ruling (pending owner review; entry 19.3) — key spelling.** A key written as a bare name is folded like every name (LEX-10), so `{ Name: 1 }` stores `name` and `obj.Name` reads it; a key written as a string keeps its case, as an array index does (SEM-5), so `obj["Name"]` is a different key from `obj.Name`. *Evidence:* the lexer folds a bare name before the parser sees it; SEM-5 keeps an index key's case. *Rejected alternative:* folding string keys too, which would make `d["Health Potion"]` and `d["health potion"]` one entry and so cannot hold names that differ only by case.
* **Proposed ruling (pending owner review; entry 19.3) — what a key can be.** A number key is written with six significant digits (`d[1]` is the key `"1"`, as an array index is). A key that is anything else (an object, a callable) is a catchable runtime error (`object.invalid`) rather than a silent key `"0"`. *Rejected alternative:* converting it with the usual string rule, which collapses every object to the same key.

### Auto-bound receivers, `this` and `bindThis` (OOP-11) — Reawakened rule

**What it does for a game author.** When you take a function out of an object (`potion.use`), the function remembers which object it came from, so `this` inside it still means that object even if you store it somewhere else and call it later. A function that was never part of an object has no `this`.

**The rule, precisely.**

* **Auto-binding on member access.** The step IR has `get_member_bound { name }`, the ruling's `OP_GET_MEMBER_BOUND` ([ADR 0004, decision 8](../../adr/0004-script-ast-step-ir-and-plugins.md)). A `.` or `->` read of a member that holds a callable pushes a new callable record with the same `def` and `captures` and `receiver` set to the object's handle (a read of a non-callable member is unchanged). The compiler emits it for every such read; it is not simulated later.
* **Object/file call precedence.** A call written `d.f()` first checks whether `d` is a live object. When it is, the call is `d->f()` of OOP-10 (an object with a class runs its method of that name; a dictionary invokes its callable member) using OOP-11 receiver binding. Only when no object binding exists does the legacy `d.prg` file-qualified fallback apply (MOD-2). This is the same explicit-object-over-implicit-file principle as PKG-4's namespace rule; the rejected file-first alternative would let an asset silently hijack an object method.
* **Preserved receiver on tear-off.** The bound callable is an ordinary value: storing it, passing it or returning it keeps its receiver.
  ```rpgcode
  cb = potion.use;
  cb(player); // 'this' remains potion
  ```
* **Standalone lambdas.** A lambda made outside an object has `receiver = null`, and inside it `this` is `null`; reading a member of that `null` is a catchable runtime error like any member read of a non-object.
* **Explicit rebinding with `bindThis`.** `bindThis(fn, obj)` returns a new callable with the same `def` and `captures` and `receiver = obj`; `fn` is unchanged. A first argument that is not a callable, or a second that is not an object handle, is a catchable runtime error with a located diagnostic.
* **Legacy methods are unchanged.** `obj->method(args)` on a legacy class still runs the method with `this` set to `obj` by OOP-3 and OOP-6, and `obj.method(args)` is the same call (OOP-10, "Calls through a name"); the implicit-`this` method step keeps the place 18.5 flagged.
* **Proposed ruling (pending owner review; entry 19.1) — a callable that already has a receiver keeps it.** Member access binds only a callable whose receiver is `null`. So `b.f = a.method` followed by `b.f()` still runs with `this = a`, which is what "tear-offs keep it" requires; `bindThis` is the one way to change a receiver. *Rejected alternative:* always rebind on member read, which would make a stored tear-off lose its object the moment it is read back through another object.
* **Proposed ruling (pending owner review; entry 19.1) — a receiver stays alive.** A callable's `receiver` handle is a root of the end-of-tick collection pass (R-34) for as long as the callable is reachable, so `this` never names a freed object. *Evidence:* entry 18.6 left "what keeps a receiver's object alive" to this entry (ADR 0004 decision 8, known limits). *Rejected alternative:* a weak receiver that becomes `null` when the object is freed, which turns a saved callback into a silent failure that differs between a replay and a restore.

### Host-provided object types and hydrated methods (OOP-12) — Reawakened rule

**What it does for a game author.** Some objects come from the engine or a package rather than from your script: a party member, a sound you are playing. You use them like any object (read fields, call methods, listen for their events), and they save and load like any other data. You never see how.

**The rule, precisely.**

* **An object whose type the host or a package provides saves as data only.** Its record holds its fields and a type name. It never holds a closure, a callable for a method, or any code. Its methods are supplied when the game is loaded, by **hydration**: the engine looks the type name up among the installed packages and attaches the methods the package defines, as actor behaviours are hydrated by name. *Reason:* a save must be plain JSON (G1), and a package's code is not part of a save, so a package update changes behaviour without a stale save. *Needed by:* Epic 20 (actors) and Epic 21.5 (Media voices).
* **A type that is not installed** is a catchable runtime error with a located diagnostic when a method of it is first called, never a refused load. The object's data stays.
* **A method of a hydrated type is a bound callable** (OOP-11): reading `voice.stop` gives a callable whose receiver is the object, and `this` works inside it.
* **Every object has the emitter methods (OWNER, Jensen 2026-10-19).** `on`, `off`, `once`, `emit` and `emitCancelable` ([EMIT-2](#emit-1)) are host-provided methods hydrated onto every object, a dictionary and a legacy class instance included, so nothing for them is stored in a save. The rule below applies to them: an author's own data field named `on` shadows the method.
* **Proposed ruling (pending owner review; entry 19.1) — a data field and a method with the same name.** The data field wins on read, and hydration never overwrites a saved field. *Rejected alternative:* the method wins, which lets a package update silently hide data a game saved.
* **Engine-phase cancelable emits** (an emit with no script thread to park) are ruled with entry 21.1; see [EMIT-11](#emit-11).
