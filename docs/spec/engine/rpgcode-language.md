# RPGCode: language and execution

RPGCode is the scripting language of every game event. This page describes the language as the 3.1 engine actually accepts and runs it, including the quirks existing games may depend on, and states where this rebuild deliberately differs. The built-in commands are listed in [rpgcode-functions.md](rpgcode-functions.md). Four sibling pages cover one area each: [modules and objects](rpgcode-modules-and-objects.md), [errors and threads](rpgcode-errors-and-threads.md), [values, scope and conversion](rpgcode-runtime.md), and the [older dialects](rpgcode-dialects.md).

<a id="e-90"></a>
**E-90 Language.** The language surface is the subject of this page and its four siblings: dynamic values, arrays and maps, functions with overloading and references, classes with multiple inheritance, operator overloading, destructors, includes and implicit includes, redirects, error handlers, plus the legacy syntax the frontends accept. Every feature named there is a parity requirement.

**How to read this page.** A plain paragraph says what Toolkit 3.1 does. A block that opens with the words **Reawakened rule** is a deliberate addition or difference of this project, written beside the legacy behaviour it changes ([ADR 0007](../../adr/0007-docs-spec-is-the-normative-specification.md), decision 2). Where such a rule is a *departure* — a case where Toolkit 3.1 behaved differently and a game written for 3.1 could notice — the block says so and gives the reason. Rule ids such as LEX-2 and STX-4 are stable labels that code, tests and plans cite.

## Programs and encodings

A program is a `.prg` file. Its byte layout is in [../formats/rpgcode-program.md](../formats/rpgcode-program.md). The loading rules are:

- **Source text** is single-byte ANSI text (Windows-1252 on Western systems), with CR/LF or LF line endings.
- An **empty file** (0 bytes) is valid, empty program: it loads and does nothing.
- A file whose **last line has no final newline** is valid; that last line is still a statement.
- A file whose **first byte is `0x00`** is a pre-compiled program, not source text. Supporting it is optional; rejecting it with a clear message ("re-save the source") is allowed.
- A source program loads and runs exactly what it contains.

**PRG-2.** These loading rules are settled by the 3.1 corpus: all 10 sample files load, and none starts with `0x00`.

## Lexical rules

| Topic | Rule |
|---|---|
| Statement end | newline or `;` |
| Line continuation | `_` at the end of a line |
| Comments | `//` and `**` to end of line; a line starting with `*`; `/* … */` |
| Legacy marker | a leading `#` on a command is ignored (Toolkit 2 syntax) |
| Identifiers | letters, digits and `_`, may start with digits if they contain a letter or `_`, optional leading `~`. **Case-insensitive** (lower-cased). A trailing `!` (number) or `$` (string) is ignored, so `x`, `x!` and `x$` are the same variable. |
| Strings | `"…"`, no escape sequences |
| Numbers | decimal, double precision |
| Booleans | `true`, `false`; `null` |

The rules behind the table, with the id each carries:

* **Case (LEX-10).** Keywords, identifiers and built-in names are compared and stored after ASCII lower-casing (`A`–`Z` only). The fold covers keywords, variables, labels, class and member names, function and built-in names. It does **not** cover string contents or map keys written as strings, and no locale-sensitive operation is ever used. Include file names are matched case-insensitively by the asset resolver, not by lower-casing the program's text. <!-- OWNER: LEX-10 — alternatives: lower-case only variables (leave keywords fixed), or lower-case everything including path text. Decided: ASCII lower-case for names, resolver handles paths. -->
* **Numbers (LEX-2).** A number token is `digits [ . digits ] [ e [ + | - ] digits ]` (`12`, `1.5`, `1e+6`): the longest run of characters with that shape. A run that starts with a digit but does not fit (`2x`, `1e`) is an **identifier**, not a malformed number. <!-- OWNER: LEX-2 — alternatives: make `2x` an error, or reserve `e` as the only exponent letter. Decided: longest-match, else identifier, because identifiers may legally start with a digit. -->
* **Reserved literals (LEX-9).** `true` = 1, `false` = 0 and `null` = 0 are reserved, matched case-insensitively; a variable may not be called `true`, `false` or `null`.
* **Strings (LEX-8).** A string is `"…"`, single-line. There are no escape sequences, a string cannot contain `"`, and a string cannot contain a newline; an unterminated string is an error at the end of its line. Non-ASCII bytes inside a string or comment decode as Windows-1252. <!-- OWNER: LEX-8 — alternatives: treat the bytes as raw/opaque, or as Latin-1. Decided: Windows-1252, the editor's ANSI code page. -->
* **Sigils.** A trailing `!` (numeric) or `$` (string) directly after an identifier is a legacy type sigil and is ignored: `x!`, `x$` and `x` are the same variable everywhere, including in parameters, array names and assignment targets.
* **`~` has three roles (LEX-4).** `~a` is bitwise NOT, `a ~= b` is "not equal", and `~Name` is a destructor name, recognised only directly after `method` or `::`.
* **`!=` and the sigil (LEX-3).** Toolkit 3.1 has no `!=` operator. `!` after a name is the numeric type sigil, so in 3.1 `if (opt!=1)` reads as "assign 1 to `opt!`": the assignment's value is the value assigned, so the `if` tests 1, is always true, and `opt` becomes 1. Games written that way were silently wrong under 3.1 (round 5, Q3). A `!` or `$` followed by anything but `=` is still a sigil, so `x! = 1` is `x = 1` with the sigil ignored. `operator!` and `operator$` are single operator names, not a name plus a sigil.

  **Reawakened rule — a deliberate departure from 3.1.** Adjacent `!=` is read as "not equal", a second spelling of `~=`. A `!` immediately followed by `=` is always the operator; only that adjacency decides it. `x!=1` is therefore `x != 1`, where 3.1 performed an assignment and tested its result. This is an edge case, and it is kept because the sample corpus contains an adjacent `if (opt!=1)` whose 3.1 reading is almost certainly not what the author meant; a compatibility warning may be added when a `!=` site is compiled. <!-- OWNER: LEX-3 — alternatives: (a) keep `!=` out of 3.1 and require `~=`; (b) always read `!` as a sigil so `x!=1` cannot be parsed. Decided: adjacency rule, which reproduces both corpus forms (`x! = 1` spaced, `if (opt!=1)` adjacent). -->
* **Statement end.** A statement ends at a newline or a `;`; the semicolon is optional. A block header is not a statement until its `{` (see the brace rule under keywords and structure).
* **Line continuation (LEX-1, LEX-5).** A `_` that is its own token (whitespace before it) at the end of a line continues the statement onto the next line, optionally with a `//` comment after the `_`. An `_` that is part of an identifier or number (`foo_`) continues nothing. A continued line is not "the first non-blank line", so a leading `*` on it is an operator, not a comment. <!-- OWNER: LEX-1, LEX-5 — alternatives: require `_` to hug the preceding token, or count a continued line as first-non-blank. Decided: standalone `_` token (all 6 corpus uses have the space) and no comment on a continued line. -->
* **Comments.** `// …` to the end of the line; `/* … */` (may span lines); legacy `* …` when `*` is the first non-blank character; `** …`. In a legacy Toolkit 2 file `*` may also start a trailing comment after a complete statement ([older dialects](rpgcode-dialects.md)).
* **`#` lines (LEX-6).** `#include` is the one directive read in 3.1 source; it is matched case-insensitively and `#` may be separated from `include` by whitespace. Any other leading `#` is a legacy command prefix and is ignored on that line. A `#` that is not at the start of a line is not special. Unquoted legacy arguments such as `#Mwin(Hello there)` are not 3.1 syntax and belong to the legacy frontends ([older dialects](rpgcode-dialects.md)). <!-- OWNER: LEX-6 — alternatives: reject every other `#` line, or accept `#Command` in 3.1 too. Decided: ignore other `#` lines (existing rule), `#Mwin` forms dialect-only. -->
* **Board constants (LEX-7).** Board constants and engine constants both appear as names. Engine constants fold into the compiled program. A board constant does not: the compiled code names the constant and reads its value from the board the program runs on, so a compiled file does not depend on which board loads it and the program cache can key on the file alone. <!-- OWNER: LEX-7 — alternatives: (a) bake board constants at compile time and add the board's constant set to the cache key; (b) resolve every board constant at run time (as above). Decided: (b), because it keeps a compiled program valid across boards and matches compile-from-text plus cache-by-file. -->
* **Unknown characters (LEX-11).** A character that belongs to no token — `@`, a backslash, or a `$` with no identifier before it — is a **lexical error**, reported with file and line. A legacy dialect frontend may accept the characters its own syntax uses (Toolkit 2.x uses `@` for a blank Message-Window line). <!-- OWNER: LEX-11 — alternatives: silently ignore an unknown character. Decided: error, so a typo cannot be swallowed; no corpus file contains one. -->

## Keywords and structure

- **Methods:** `method name(a, b) { … }` (also `function`), `return value`. Parameters prefixed with `&` are passed by reference.
- **Control flow:** `if (c) { } elseif (c) { } else { }`, `while (c) { }`, `until (c) { }`, `for (init; cond; step) { }`, `switch (x) { case 1: … default: … }`. **Braces are mandatory.** In the original engine `if`, `elseif`, `else`, `while` and `until` are built-in functions, not keywords; they must be followed by `{`.
- **Labels and jumps:** `:label` lines, `branch(:label)`.
- **Classes:** `class Name : Base1, Base2 { public: var x; method f() { } private: … }`; `struct` is a class with public members. Objects are created with `Name(args)`, members accessed with `obj->member`. Operators can be overloaded with methods named `operator+` etc. The detail is in [modules and objects](rpgcode-modules-and-objects.md).
- **Includes:** `include "file.prg"` compiles another program into this one.
- **Redirects:** `redirect(old, new)` makes calls to command `old` go to method `new`. **It takes effect at compile time** and only affects code compiled afterwards.
- **Error handling:** `on error goto :label`, `on error resume next`, `resume next`. The detail is in [errors and threads](rpgcode-errors-and-threads.md).
- **Scope:** variables are created on first use. Plain names are global unless a local of that name exists (or the reverse after `autolocal(true)`). A leading `:` forces a global. `local(x)` / `global(x)` declare explicitly.

The program shapes, with the id each carries:

```
if (expr) { … } elseif (expr) { … } else { … }
while (expr) { … }
until (expr) { … }                   // check first; loop until expr is true
for (init; cond; step) { … }         // any of the three parts may be empty
switch (expr) { case v: { … }  default: { … } }   // no fall-through
function name(a, b, &byRef) { … return expr; }   // "method" is a synonym
inline function f(x) { … }           // "inline" is a hint only
:label                               // label (used by error handling / branch)
```

* **Braces are required (STX-1, STX-4).** Every block body is written `{ … }`; a brace-less body (`if (x) stmt`) is not 3.1 syntax. A newline is allowed between a block header and its `{`: the brace may be on the header line or the line after it. A block header is not a complete statement until its `{`. <!-- OWNER: STX-1, STX-4 — alternatives: (a) require the brace on the header line (the old literal reading, which fails 6 of 9 sample programs); (b) allow brace-less single-statement bodies. Decided: brace on either line, brace-less bodies not allowed. -->
* **`}` ends the statement before it (STX-6).** A statement immediately before a closing `}` needs no `;` or newline. <!-- OWNER: STX-6 — alternative: require `;`/newline before `}`. Decided: `}` terminates, so `{ x = 1 }` is well-formed. -->
* **`else` (STX-3).** `else` may be written on the closing `}` line or on a later line; `else if` (two words) is accepted as a synonym of `elseif`. <!-- OWNER: STX-3 — alternative: allow `else` only on the `}` line, and reject `else if`. Decided: both positions, and `else if` accepted. -->
* **`case` and `default` (STX-2).** A case value is a full expression. The colon is optional: `case (v):`, `case (v)` and `case v:` are the same label. `default` may take an optional colon. Blocks do not fall through. <!-- OWNER: STX-2 — the corpus uses the colon-less `case (1)` form and never uses `default`; alternatives: make the colon mandatory (the old text) or accept both (decided). -->
* **`for` parts (STX-4).** The three parts are separated by `;` and each may be empty (`for (; cond; )`); those `;` are separators, not statement terminators.
* **`until` (SEM-2)** checks its condition **first**, then loops until the expression is true.
* **Parameters (FUN-1).** A parameter is `[Type] name [&]` — an optional class name, then the name, then an optional `&` for by-reference. The type is documentation only: it is not checked at run time and takes no part in choosing an overload. Overloading is by **parameter count** only. <!-- OWNER: FUN-1 — alternatives: (a) use the type in overload choice and check it; (b) require the type to name a real class; (c) ignore it (decided). The corpus has `method clone(CArray rhs)` but no evidence of a type check or a type-keyed overload. -->
* **No default values (FUN-5).** Default parameter values, variadics and declared return types do not exist in 3.1, and an overload never matches on type.
* **`inline` (FUN-6).** `inline` has no effect beyond its hint.
* **`return &lvalue` (FUN-3)** returns a reference, so a function call can be an assignment target; any lvalue is allowed — a variable, an index (`return &a[i]`), or a member access. <!-- OWNER: FUN-3 — alternative: restrict `return &` to a plain variable. Decided: any lvalue, because the corpus returns `&m_data[idx]`. -->
* **Labels (STX-5)** are scoped to the function (or program) that contains them; `branch(:label)` jumps within that scope and never crosses a function boundary. A label may also be passed as an argument (`branch(:label)`, `setErrorHandler(:label)`). <!-- OWNER: STX-5 — alternatives: program-wide labels, or labels that `branch` can cross out of a function. Decided: function/program scope, no crossing. -->
* **`end()`, `done` and `stop` (FUN-7)** end **the program whose code is running**, immediately and whatever the call depth: every pending function frame of that program is abandoned. Functions from included files are part of the including program, so `end()` there ends the including program. `run(prg)` ends the calling program *before* it starts the new one, so when the `run()` program calls `end()` the whole chain is finished and the rest of the game keeps running. (Reviewed extraction fact R2-Q20, `docs/provenance/facts-round-2.md`; it replaces the earlier ruling that a `run()` program returns to its caller. How a thread's own `end()` behaves is part of the thread rules.)
* **A bare identifier** on its own line is treated as a zero-argument call (legacy `end` → `end()`).
* **`method` and `function` (FUN-4)** are interchangeable, and neither is legacy; `returnMethod` is the Toolkit 2.x return spelling ([older dialects](rpgcode-dialects.md)).
* **Lambdas and first-class callables (FUN-8) — Reawakened rule.** Arrow syntax produces an expression evaluating to a callable value (`Value.Callable`):
  - Full parameter block form: `(a, b) => { stmt; return a + b; }`
  - Expression body form: `(a, b) => a + b`
  - Single parameter shorthand: `x => x * 2` (parentheses optional when exactly one parameter).
  - Zero parameter form: `() => { ... }` (empty parentheses required).
  A lambda is an expression producing a first-class value, not a statement declaring a global or local function name: `fn = (x) => x + 1` declares nothing. What a **call** of that name does is the environment table under "Calling a name" below; in particular an integer assignment (`castint = 99`) never shadows a command, which is ruling R-35 unchanged.
  Calling syntax `callee(arg1, arg2)` applies to any expression evaluating to a callable value, including variables, parameters, dictionary members (`obj.fn()`), and array elements (`handlers[i]()`).
  Built-in `bindThis(fn, obj)` returns a new callable value explicitly bound to `obj` as its receiver (see [OOP-11](rpgcode-modules-and-objects.md#oop-11)). <!-- OWNER: FUN-8 — 2026-10-18 ruling: arrow lambdas as first-class expressions, distinct from command namespaces; auto-bound this on member access with bindThis(fn, obj) for explicit rebinding. Ruled in full by entry 19.1 (OOP-11). -->
  **Captured variables.** A lambda body that reads a name it does not itself declare, and that is not one of its parameters, uses that name from the scope where the lambda value is created. If the name is a **local of the creating function** (a parameter, a declared local, or a name an enclosing lambda captured), the closure captures it into a **cell**, the closure's storage for that name, and the lambda's own reads and writes go to the cell. A closure therefore keeps its own state between calls. If the name is **not** a local of the creating function, it is a global (or an unset name), and it is **not captured**: every call of the closure reads and writes the live global, so an assignment made anywhere else is visible inside the lambda and the lambda's assignment is visible everywhere. **A captured local's cell is that local's storage.** *In plain terms:* the closure and the function that made it share one variable, so a change made on either side is seen on the other. *Precisely:* from the moment the callable value is created, the creating frame's variable and every closure that captured that name read and write the one cell, so an assignment the frame makes after creation is visible inside the closure, an assignment the closure makes is visible in the frame, and a later closure built by the same frame for the same name captures the same cell. One cell exists per creating frame per captured name, so two separate runs of the same code never share a cell. **A by-reference parameter is the exception**: its slot is an alias of the caller's variable, which a cell cannot stand in for, so a captured by-reference parameter keeps a by-value copy in the closure's own cell and the frame's alias and the cell then diverge. <!-- OWNER: FUN-8 — 2026-10-18, entry 18.5: the captured local's cell is shared with the creating frame, replacing the by-value copy 18.4 shipped (the plan for 18.5 owns this). Rejected alternative: keep the private copy, which would hide an assignment the frame makes after creation from the closure — the behaviour the shared-cell ruling calls wrong. Proposed ruling (pending owner review): the two edges the ruling leaves open. (1) A later closure from the same frame for the same name shares the first closure's cell (one cell per frame per name, as a function-scoped variable behaves in most languages), rather than taking a fresh cell per closure. (2) A by-reference parameter is captured by value, because the cell would have to replace the alias and the caller's variable would stop seeing the callee's writes; the alternative, capturing the caller's variable itself, would make a closure outlive and write through a reference whose frame is gone. -->
  **What is captured.** Only a plain variable reference is captured — a read (`x`), an assignment target (`x = …`), a compound assignment target (`x += …`), or the name of a plain-name call (`g(args)`, which reads the variable `g` to see whether it holds a callable; see "Calling a name" below). Never captured: a parameter (it shadows the outer name), a name written with an explicit scope (`local(x)`, `global(x)`), `this`, the name of a `file.name(...)` call, and an array element (`a[i]`, `a[0]`), because an element's index may be a run-time expression; element names keep their ordinary scope resolution for now. <!-- OWNER: FUN-8 — 2026-10-18, entry 18.5 (Proposed ruling, pending owner review): a plain-name call is a capture site. 18.4 captured variable loads only, so a closure that called a local callable of its creating function by name (`original(file)` in the example below) found nothing once the creating frame had returned, and a script had to spell the call `(original)(file)` to dodge the rule. Rejected alternative: keep calls out and document the parenthesised spelling. A name that is not a local of the creating function costs one `""` entry in the handle's `captures` and nothing else. -->
  **Calling a name: one environment table.** *In plain terms:* when your script calls `name(...)`, the engine looks `name` up in one list, from the top, and runs the first thing it finds. Your own variables are at the top of the list, so a script can put its own function in place of an engine command; everything below them behaves exactly as in 3.1, and a script that never stores a function in a variable behaves exactly as it did. *Precisely:* a call written as a plain name — `f(args)` — is resolved each time it runs, takes no ticks of its own, and the first entry that matches runs:

  1. **the running scope's own symbol** — the variable `f` that a read of `f` reaches from the running frame (a local of that frame, which includes a parameter and a captured name; failing that, the global), when it currently holds a callable value. A script intercepts, wraps or replaces a command by assigning a callable to its name (`mediaPlay = myMediaPlay`): every later plain-name call of that name from a scope that reaches that variable runs the callable. A global binding is reached from every frame that has no local of that name, and lasts until the variable is set to something that is not a callable or is killed. A local binding is reached from its own frame and from closures that captured it, and ends with its frame; a function the frame calls does not see its caller's locals, exactly as for any variable read. A variable of that name that holds anything else — including a local that hides a callable global — is not a binding, and the call falls through to entry 2.
     *Layers a package registers (entry 19.8).* The same entry also offers the top layer that `registerPlugin` registered for `f`, after the scope's own variable and before the built-in: it is part of this entry, held in the running game's layer table and not in a variable or in a save, so the table still has the four entries and `resolveCall` is unchanged. See [MOD-4, how the layers are held](rpgcode-modules-and-objects.md#registerplugin-layers-entry-198).
  2. a **built-in** engine command named `f` (R-35).
  3. a **script function** of the program or its includes with that name and that number of arguments (FUN-1, MOD-1).
  4. a command a **plugin** claims (MOD-4).

  A call the table cannot match is the legacy `unknown.command` failure, naming the name, at the call site. The table only chooses what runs: the chosen callable runs like any other call (a new frame on the same thread, the same step budget, and a wait inside it parks the thread). It works on names, not on commands, so `mediaPlay` and its alias `midiPlay` are two names and a wrapper installed on one does not intercept calls spelled with the other. A wrapper is a callable, so it takes exactly the arguments its parameters name (FUN-1) and a call with another count fails with the callable's arity error ([errors](rpgcode-errors-and-threads.md)); to wrap a command that takes an optional argument, wrap it for the argument count your script uses.

  **Calling into a package: `namespace.name(args)` (FUN-8, entry 19.7; PKG-4).** *In plain terms:* a package's name (or the namespace its manifest gives it) in front of a command name runs that package's own version of the command, whatever later packages have put on top of it; the plain call `name(args)` still runs whichever package is last in the plugin list. *Precisely:* the table above is the unqualified call. A qualified call whose qualifier is a package namespace, and does not name a live object ([modules and objects](rpgcode-modules-and-objects.md), MOD-2), skips entry 1 and the three below it and runs the layer of `name` that package supplies; the layer's `next` reaches the layer below the package. The call is resolved each time it runs from the effective manifest, so it adds nothing to a save; a package the manifest no longer lists has no namespace and the call is `unknown.command` naming `namespace.name`, as it is for a name the package does not supply. Two packages that supply one name raise one `command.overridden` warning when the registry is assembled and none per call. The full rule, and what happens when `namespace.prg` also exists, is [PKG-4](rpgcode-modules-and-objects.md#pkg-4).

  **Only a callable reassigns a name.** *In plain terms:* storing a number or text in a variable named like a command never changes what the command does — `castint = 99` leaves `castint(4.75)` meaning the engine's command. Only storing a function does. *Precisely:* an assignment whose value is not a callable does not touch entry 1, so ruling R-35 is unchanged and, because 3.1 has no callable values, every 3.1 program calls exactly what it did before. Reading a name is never this lookup: `x = castint` reads the variable `castint` (an unset name reads as `""`/0), so a read never yields a command. The VM's own commands — the module directives `include`, `redirect`, `killRedirect` and `killAllRedirects` ([modules and objects](rpgcode-modules-and-objects.md#redirects)) and `bindingOf` below — are answered before the table and are not part of it, so assigning a callable to one of those names does not intercept it. `#redirect` itself stays what it was: a name substitution applied while the program is parsed (R-42..R-44), before any call reaches the table, so a redirected name is looked up under its new spelling. <!-- OWNER: FUN-8 — 2026-10-18, entry 18.5 (Proposed ruling, pending owner review): the four-tier lookup (redirect, script function, built-in, extension) is replaced by this one table, and the running scope's callable binding moves above the built-in (18.4 had it below every tier). Rejected alternatives: leaving the scope binding last, which cannot intercept a built-in; materialising a symbol-to-handle entry for each of the ~300 built-in names in the saved state, which changes the shape of every save for no behaviour a variable does not already give; lowering `#redirect` to a run-time assignment, which would make a 3.1 redirect depend on run-time scope state (R-42..R-44 make the table run-wide and substitute in textual order on text parsed after the call); and a per-name stack of bindings with the replaced binding passed to the wrapper as a trailing argument, which needs a second place to store the current binding beside the variable, an arity rule that sometimes appends that argument, and would disagree with `kill`, `local`/`global` and reads. -->

  **Reaching what a name ran before you replaced it — `bindingOf(name)`.** *In plain terms:* `bindingOf("mediaPlay")` hands you, as a value you can keep in a variable, whatever a call of `mediaPlay` would run right now. Ask for it before you replace the name, keep it, and call it from inside your replacement: the replacement does its extra work and then passes the call on to the original. Because each replacement asks for what is installed at that moment, several scripts can wrap the same command and every one of them still runs. *Precisely:* `bindingOf` takes one argument, the name as a string — a computed string or a parameter works, a bare variable name does not, and an argument that is not a string fails with `builtin.bad-arg`. It folds the name (LEX-10) and resolves it from the calling scope exactly as a plain-name call would at this moment: if the scope's own symbol (entry 1) holds a callable, a copy of that callable value is the answer; otherwise the answer is a callable that runs the first of a built-in command of that name, a script function of that name (the program that is running first, then every program compiled so far) or a command a plugin claims, in that order (R-35). Such an answer is a handle that always runs that binding — through entries 2 to 4 only, never through entry 1 — so a later reassignment of the name does not change what the handle runs. A call through a handle with a number of arguments the binding does not accept fails as a direct call of that binding would: a command raises its own arity error, and a script function raises the callable arity error ([errors](rpgcode-errors-and-threads.md)). When nothing of that name exists the call fails with `unknown.command` at the `bindingOf` call site, so a mistyped name is reported where it was written. `bindingOf` changes no variable, takes no ticks and does not wait; a `file.func` call site is not reachable this way. A wrapper must not ask for its own binding from inside its own body: there the answer is the wrapper itself and the call recurses. Ask before the assignment and keep the answer where the wrapper can reach it — a global, or a local of the installing function that the wrapper captures.

  ```
  function wrapMediaPlay() {
    local(original)
    original = bindingOf("mediaPlay")        // what mediaPlay runs now: the engine's own command
    mediaPlay = (file) => {                  // intercept it
      mwin("Now playing " + file)
      return original(file)                  // ...and pass the call on
    }
  }
  wrapMediaPlay()
  mediaPlay("battle.mid")                    // shows the line, then plays the song
  ```

  Calling `wrapMediaPlay()` a second time stacks a second wrapper: its `bindingOf` returns the first wrapper's callable, so the line is shown twice, outermost wrapper first, and then the song plays.   **Saving, loading and tidying up closures — entry 18.6.** *In plain terms:* a saved game keeps every function you stored in a variable, every closure's private variables, and a function that was paused in the middle of a `wait` or `sleep`. After loading, all of it carries on exactly as if the game had never been saved. If a save is damaged, or names a function the game no longer has, the game refuses to load it and says where the problem is, instead of loading a half-working game that fails later. The engine also throws away a closure's private variables once nothing can reach them any more, so a script that makes a new function on every pass of a loop does not make the save grow for ever. *Precisely:*

  * **What is saved.** A callable is the plain record `{ type: "callable", def, captures, receiver, owner? }` wherever it sits: a global, a frame local or operand, an object member, a cell, or a frame's return value. `owner`, when present, is the package name that owns the callable's definition; it is copied when a callable is bound or stored. `vm.cells` holds the cells by id; `vm.cellSeq` is the number of the last cell id issued, so the next cell is `cell` followed by `cellSeq + 1`, and the counter never goes back, so an id is never reused after its cell is freed. A frame slot redirected to a cell keeps `ref: "cell:<id>"`. A frame parked inside a closure's call (a `wait`, a `sleep`, a request) is an ordinary frame of its thread and is saved with the thread. `vm.cells` and `vm.cellSeq` are absent until the first lambda value is made, so a state with no closure in it is the state it was before callables existed. The saved form is canonical, so two identical runs save identical bytes.
  * **Where a definition is found after loading — `vm.defOwners`.** Compiled programs are not saved; a load rebuilds them from their references. A callable names its definition only by `def`, and a function stored in a global can outlive the program that made it (a start-up program that installs a wrapper and ends), so the save also records the owner: `vm.defOwners` maps each `def` that a live callable names to the reference of the program that defines it. The entry is written when the callable is made, by `load_fn` for a lambda and by `bindingOf` for a script function; the first owner recorded for a `def` stays, and a callable that names a built-in or plugin command has none because the load rebuilds the command table from the manifest. `vm.defOwners` is absent until the first callable is made. A call through a callable looks for its `def` in the running program, then in every compiled program, then in the recorded owner, which it compiles at that moment if it is not compiled yet, so a restored game resolves a handle whose program has ended even when nothing ran the load-time check; a recorded owner that changed since the save is not an owner and the call fails with the located `callable.unknown-def`.
  * **Checking a save on load.** *In plain terms:* the game checks that every function in the save is whole, that every private variable it points at exists, and that the game still has the function it names. *Precisely:* the check runs in two stages and any failure is a typed `ScriptError` (a stable `code`) whose message names the place in the save, such as `vm.threads[0].frames[1].locals.n.ref`; nothing is repaired or skipped, and no game starts from the save. These are load-time failures, so a script's error handler never sees them ([errors](rpgcode-errors-and-threads.md)).
    1. `restoreGameState` checks the shape with no program to hand: every value in the `vm` section is a number, a string, an object handle or a whole callable record; every `captures` entry, every frame slot or operand reference of the form `cell:<id>` and every wait resume reference names a cell that is in `vm.cells` (a `captures` entry of `""` is the live-global marker and names none); `vm.cells` and `vm.cellSeq` are both present or both absent, every cell id is `cell` followed by a positive whole number with no leading zero, and no id is greater than `cellSeq`, so the next id cannot collide; `vm.defOwners` maps each `def` to a program reference.
    2. `verifyRestoredHandles` runs after the host has rebuilt its services: it compiles every frame's program and every `vm.defOwners` entry, then checks each callable against the definitions it can find (a script function or lambda, or a command): the `def` must be defined, and the number of `captures` must equal the number of names the definition captures (a command captures none), and each owner must define the `def` it is recorded for. A program whose source has changed since the save (`restore.source-changed`) is skipped by this stage, as its thread restarts from source on its next turn; so is a program whose frame carries an older `ir`, because that thread also restarts from source ([save-game.md](../formats/save-game.md#save-compatibility-and-instruction-versions-owner-ruling)). A save from a newer instruction version never reaches this stage: the whole save is refused with `restore.ir-mismatch`. A `def` that only a skipped program defined is reported as unknown. A state with no callable and no `vm.defOwners` entry in it is not checked, and no program is compiled for it.

  * **Tidying up cells.** *In plain terms:* a closure's private variable is kept for as long as some function, variable, paused call or object can still reach it, and is thrown away at the end of the tick in which it stops being reachable. *Precisely:* in the end-of-tick pass that frees unreferenced objects (R-34), and just before the objects are freed, every cell not **reachable** is removed from `vm.cells`. The roots are the global table; every frame's locals (a slot's value, and the cell its reference names when the slot is redirected to one), operands, return value and wait resume references; and the members of every object in the handle table. From a root a cell is reached through a callable's `captures`, through a `cell:` reference, and through the value of a cell already reached. Reachability, not counting, decides it, so a recursive local lambda, whose cell holds a callable that captures that same cell, is freed once nothing outside it names it. The cells still left then count as roots of the objects pass, so an object that only a dead cell named is freed in the same pass, and a cell that only a freed object named is freed in the next tick's pass. `vm.cellSeq` is never lowered, and the `vm.defOwners` entries of definitions no reachable callable names are dropped in the same pass. A script cannot read an unreachable cell, so the pass changes nothing it can observe; it runs in a fixed order and removes the same cells on every machine. A state with no cell and no `vm.defOwners` skips the pass at no cost.

### Values and variables

* **Dynamic typing.** A value is a number (a double), a string, a dictionary object, or a first-class callable (`Value.Callable`). Mixing in `+` concatenates (`"Hello " + 32` → "Hello 32"`). Object handles are numbers or dictionary references. First-class callables are plain serializable data records (`{ type: "callable", def: string, captures: string[], receiver: string | null, owner?: string }`). A callable evaluates to truthy; converting to string yields `"[Function: <def>]"`. [Values, scope and conversion](rpgcode-runtime.md) settles comparison and conversion.
* **No declaration needed; scope defaults to global (SEM-4).** `local(x)` / `global(x)` select scope explicitly, and `autoLocal(true)` makes new variables local to the current function or program. The full scope rules are in [values, scope and conversion](rpgcode-runtime.md).
* **Declare and assign (FUN-2).** `local(x) = v` and `global(x) = v` declare the variable in the chosen scope and assign it in one statement; this is the ordinary form for a new local (for example in a `for` initialiser) and it uses the reference-return rule above. `local(x)` on its own declares the variable and leaves it unset. <!-- OWNER: FUN-2 — alternatives: make `local(x)` alone an error (must be assigned), or have it return the variable's value. Decided: it declares and leaves unset, matching an unset variable's `""`/0 read. -->
<a id="kill-1"></a>
* **`kill` (SEM-1, KILL-1) — Reawakened rule.** *What it does for a game author:* `kill(x)` removes a variable you made, so it reads as unset again; `kill(obj.field)` removes a field from an object. The engine's own names are not yours to remove: a name the engine controls (such as `music`, `HP!` or `tkDIR_N`) cannot be killed, and trying is a runtime error you can catch with your error handler; the name and its value stay exactly as they were. *Precisely:* `kill(x)` unsets a variable; `kill(a[i])` unsets one array element; `kill(a, b, …)` unsets several in one call; `kill(obj.field)` and `kill(obj->field)` remove that field from an object of either kind, and `kill(obj["field"])` removes that key from a dictionary (OOP-10; on a legacy class instance `obj["field"]` is the legacy element variable of OOP-7, not the field, so it does not remove the field); `kill(obj)` removes the variable only (OOP-5). `kill()` deletes **only storage the script owns**: a real global, a frame local, a captured closure cell's variable and an object field. Whether `kill(a)` on a whole array differs from unsetting it element by element is a binding question settled by the entry that implements the built-ins (unchanged). **Names the engine controls are never killed** (system-controlled names): (1) the compile-time `tk*` constants (`tkMV_`, `tkVT_`, `tkPRG_`, `tkDIR_`, `tkMD_`), (2) the engine virtual variables listed under "Virtual variables" below (`music`, `gametime`, `playerx[i]`, `playerhandle[i]`, `boardskill` and the rest, plus the additions `threads[i]` and `ambientRed`, `ambientGreen`, `ambientBlue`) and (3) actor stat aliases (`HP!`, `Level!`, any `.tem`-named stat of a party member or another actor). `kill()` on any of them is a **catchable runtime error**, located, with code `kill.system-owned` (ERR-2 gains that row, see [errors and threads](rpgcode-errors-and-threads.md#err-2--which-failures-are-errors-and-which-are-catchable)); the value and the engine link are untouched, and the error is also emitted as the game `error` event ([EMIT-9](rpgcode-modules-and-objects.md#emit-1)). This supersedes the earlier ruling "a located diagnostic and no-op" and the earlier actor-epic wording "kill resets the stat to its `.tem` default". *Evidence:* the 3.1 behaviour of the engine-backed names is the broken link recorded under "Virtual variables" below, which is a defect and not a feature a game can depend on. *Rejected alternatives:* (a) reproduce 3.1, where touching the name severs it from the engine for the session, which makes engine state depend on what a script did to a variable; (b) a located diagnostic and a silent no-op, which an author's handler cannot see and which hides a mistake. **Proposed ruling (pending owner review; entry 19.1) — `tk*` constants and several arguments:** the lexer substitutes a `tk*` constant before parsing, so a `kill` whose argument was a substituted constant raises the error when the call runs, not while loading, so that it is catchable; and `kill(a, b, c)` checks every argument first and deletes none of them when any is system-controlled, so a failed call changes nothing. *Rejected alternatives:* a load-time diagnostic (not catchable, and the ruling says catchable); deleting the owned arguments left of the failing one, which leaves a half-done call. <!-- OWNER: SEM-1, KILL-1 — Jensen, 2026-10-19 (epic-rpgcode-platform Notes: `kill()` deletes only storage the script owns; system-controlled names, `tk*` constants, engine virtual variables and actor stat aliases, give a catchable runtime error `kill.system-owned`, a new ERR-2 row; `kill(obj.field)` removes the key; 3.1 is a compatibility layer, not the model, ADR 0009). Entry 20.4 builds the alias kill error. -->
* **Arrays and maps.** `a[0]`, `a[1][2]`, `m["key"]`. Any expression can be an index, multi-dimensional arrays are allowed, and arrays are sparse.
* **Bare identifier index (EXP-1).** An index written as a bare identifier (`a[i]`) is a variable lookup: `i` is evaluated as a variable. The legacy Toolkit 2.x form, where an unquoted word is taken as a string key (`m[key]` meaning `m["key"]`), is not 3.1 syntax and is handled by the Toolkit 2.x frontend ([older dialects](rpgcode-dialects.md)).
* **Unset variables** read as `""` / 0. The full rule is in [values, scope and conversion](rpgcode-runtime.md).

### Compatibility notes

1. **Adjacent `!=` is read as "not equal" here, not as 3.1's assignment** (see LEX-3 above) — a deliberate departure.
2. **No short-circuit evaluation (R-40).** `&&`, `||` and `?:` evaluate all operands.
3. **Reading a variable truncates its number to an integer.** `x = 1.5; y = x + 0` gives `y = 1`. Literals and intermediate results keep their fractions. (Inferred from the code, not observed.)
4. **Strings are true unless they equal `"off"`** (case-insensitive), so `""` is true (R-39). This is the truth test for a condition; note that it differs from the plain numeric truthiness the older §9.16 used.
5. **Numbers convert to text with 6 significant digits.** The full algorithm is in [values, scope and conversion](rpgcode-runtime.md).
6. Arrays are not containers: `a[i]` is just a variable whose name is `a[<value of i>]`. `a[1]` and `a["1"]` are the same.
7. `++x` followed by a binary operator can mis-parse in the original grammar; write `(++x) == y`.

## Execution

- Each program is compiled once per session and cached by file name. **Edits to a program during play are not picked up** (R-38c).
- A **blocking** program (started by a trigger, the menu, the start-up program, or `Run`) runs to completion before the game continues; the window stays responsive. See [errors and threads](rpgcode-errors-and-threads.md) for what a blocking command does inside a thread.
- An error in a built-in either jumps to the active `on error goto` label, is ignored (`on error resume next`), or shows an "RPGCode Error" message box; **execution then continues with the next statement** (R-38c). `Debug(on)` turns error and warning messages on or off (`Debugger(text)` shows a message).
- Compile errors are reported when the program is first loaded.
- **Error line numbers (R-38a).** A report names the exact line of the failing statement.

  **Reawakened rule.** Reports carry the exact line, with no offset. *Legacy fact:* 3.1 prepends a dummy first line before compiling and compensates for it, so syntax errors came out exact; two declaration errors — a method defined twice with the same parameter count, and a call to a class method that does not exist — came out one line too high, an unmatched brace came out approximate, and a runtime error was approximate and probably exact (round 5, Q5). Since a script cannot observe the offset, reporting the exact line is the safest reading and nothing depends on the old off-by-one.

<a id="e-91"></a>
**E-91 Program cache.** Parsed programs are cached by file name, so re-running one is cheap.

<a id="e-98"></a>
**E-98 Debugging.** A debug window shows runtime error messages ("near line N") that name the file and the line; `Debugger(text)` writes to it, and a debug toggle (`Debug(on)`) turns error and warning output on or off. Which line a message names is the R-38a rule above.

## Threads

A thread is a whole program run in the background, a slice of instructions per frame ([main-loop-and-startup.md](main-loop-and-startup.md#timing)), while the game keeps playing.

- Created by board threads, by an item's "multitask" program, or by `Thread(file, persistent)`. If `file` does not exist in `Prg\`, the text itself is compiled as code.
- Non-persistent threads belong to the current board and are destroyed when the board changes. Persistent threads survive board changes.
- `ThreadSleep(thread, seconds)` pauses a thread; `ThreadWake(thread)` wakes it.
- **Threads do not pump window messages.** A blocking command (`Wait`, `Delay`, `Prompt`…) inside a thread freezes the whole game until it completes.
- A finished thread stays registered until it is killed or its board is left.
- Threads are saved with their full execution state ([../formats/save-game.md](../formats/save-game.md#program-state-inside-each-thread-field-46)).

The sleep unit, the per-thread `source`/`target` handles, the preemption budget and the blocking-command rule are in [errors and threads](rpgcode-errors-and-threads.md).

<a id="e-93"></a>
**E-93 Threads.** Board threads (they die on board exit), persistent threads (`Thread(file, true)`) and item threads (they die with the item). The operations are sleep (timed or indefinite), wake, query the remaining sleep, kill, get id, and `TellThread(id, code)` to run code in the thread's context. A thread whose program reaches its end finishes, and loops must be explicit.

<a id="e-46"></a>
**E-46 Item multitask program.** Runs as a thread for as long as the item is on the board and active; `source` and `target` are the item.

## Objects and memory

Objects are numeric handles. Their members are stored as global variables named `<handle>::<member>`. A collector runs every 10 minutes and removes the members of objects no longer referenced by any variable; destructors are **not** called by it. Those are legacy facts; this rebuild replaces the wall-clock collector with a deterministic per-tick pass, and the class and object rules are in [modules and objects](rpgcode-modules-and-objects.md).

## Virtual variables

The engine exposes 44 read-only variables that mirror engine state (R-37):

| Names | Meaning |
|---|---|
| `playerx[0..4]`, `playery[0..4]`, `playerlayer[0..4]` | tile position and layer of party member *i* |
| `playerhandle[0..4]` | name of party member *i* |
| `boardtitle[1..8]` | the current board's layer titles |
| `constant[0..10]` | the current board's constants |
| `music` | the music file playing |
| `gametime` | seconds played |
| `boardbackground`, `boardskill` | the current board's battle background and skill |
| `cnvrendernow` | canvas handle of the script overlay: 0 until `rendernow(true)` first creates it, then the same handle whether or not it is switched on |

**Compatibility note (legacy fact):** assigning to a virtual variable in the original engine breaks its link to the engine for the rest of the session.

<a id="virt-1"></a>
**Reawakened rule — writes to system-controlled names (VIRT-1).** *What it does for a game author:* the engine's own names keep working after you touch them. Writing to a name the engine lets you change (the ambient light, a character's stat such as `HP!`) changes the engine; writing to one it does not (such as `music` or `gametime`) is a runtime error you can catch, and the value stays. *Precisely:* the 3.1 quirk above is **not** reproduced. A write to a system-controlled name (the virtual variables above, `threads[i]`, `ambientRed`, `ambientGreen`, `ambientBlue`, and actor stat aliases such as `HP!` and `Level!`) either **writes through to the engine** where the name is writable (the ambient light levels, and actor stat aliases, which write to the actor's own stat), or is a **catchable runtime error**, located, with code `assign.read-only` (an ERR-2 row) where it is read-only; the value is unchanged and the link never breaks. Read-only are the 44 names of the table above and `threads[i]` (**Proposed ruling, pending owner review; entry 19.1:** the thread table is read-only; *rejected alternative:* writable, which would let a script edit another thread's state outside the thread operations). If a 3.1 game is found to depend on the broken link, the compatibility layer handles it case by case ([ADR 0009](../../adr/0009-compatibility-layer-not-the-model.md)); nothing in the core is built for it. `kill()` on these names is `kill.system-owned` ([KILL-1](#kill-1)). *Evidence:* R-37 lists the 44 as read-only; ruled names `ambientRed` etc. are assigned in existing games (owner ruling U2, 2026-10-15). *Rejected alternatives:* reproduce the broken link; silently ignore a read-only write. <!-- OWNER: VIRT-1 — Jensen, 2026-10-19 (epic-rpgcode-platform Notes: a write to a system-controlled name writes through where writable, e.g. `ambientRed`, or is a catchable runtime error `assign.read-only`; the link never breaks; 3.1 is a compatibility layer, not the model). Entry 20.4 builds the alias write path. -->

**Reawakened rule.** Two engine-backed names that the legacy engine also had are kept as additions here, because existing games use them and `docs/spec` does not list them: `threads[i]`, the live thread table, and `ambientRed`, `ambientGreen`, `ambientBlue`, the ambient light level (call `forceRedraw()` after assigning one). They are marked as additions, not as part of the 44 read-only set, so an implementer can tell which names come from the legacy specification. (Owner ruling U2, 2026-10-15.)

**Reawakened rule — the name `game`.** `game` is a third engine-backed addition: it reads as the game emitter, an object any script can listen on and emit on (`game.on("error", fn)`, `game.emit("quests.questDone")`). It is not one of the 44 read-only variables and is not a value the legacy engine had. The rules are [EMIT-19](rpgcode-modules-and-objects.md#emit-19) and [EMIT-20](rpgcode-modules-and-objects.md#emit-20).

<a id="e-92"></a>
**E-92 Variables.** One global namespace that persists across programs and boards and is included in saves; locals are per call; the engine-backed "virtual" variables in the table above are read and written through the engine (party positions, board data, ambient light, game time).

<a id="e-15"></a>
**E-15 Board constants and titles.** The current board's constants and layer titles are exposed to scripts (`constant[0..10]`, `boardtitle[1..8]`) and are also substituted as named constants, under the board-constant rule (LEX-7) in the lexical rules above.

<a id="e-87"></a>
**E-87 Game time and steps.** The total play time in seconds and the total step count are exposed to scripts (`gametime`) and are saved with the game.

The lexer substitutes 24 named constants before parsing:

| Name | Value |
|---|---|
| `tkMV_PAUSE_THREAD` | 1 |
| `tkMV_CLEAR_QUEUE` | 2 |
| `tkMV_PATHFIND` | 4 |
| `tkMV_WAYPOINT_PATH` | 8 |

| `tkVT_BKGIMAGE` / `ALL_LAYERS_BELOW` / `FRAME_INTERSECT` | 1 / 2 / 4 |

The `tkVT_*` (vector types), `tkPRG_*` (program activation types) and `tkDIR_*` (directions) values match the board-file and movement values in this spec.

**Special handles.** `"target"` and `"source"` refer to the entity currently acting or acted upon: the item being talked to, the fighters in a battle move, the sprite that owns the thread. Many sprite functions also accept a party handle (a character name), a party index, or a board item slot number. The per-thread lifetime of the pair is in [errors and threads](rpgcode-errors-and-threads.md).

## Plugin commands

A call that matches neither a built-in nor a method of the program is offered to the loaded RPGCode plugins when the program is compiled. At run time the call is passed to the plugin **as rebuilt source text**: numbers formatted, strings quoted (not escaped), and variables passed **by name** so the plugin can read and write them through the callback interface ([plugins-and-battle.md](plugins-and-battle.md)).

## Open questions

These follow from the migration and are recorded here rather than silently decided. Each is owned by the entry named, and none is a rule yet:

1. **ADR 0004, decision 1** still says Toolkit 2.x used `< … >` block delimiters. It did not: `< … >` with `then` is Toolkit 1.x, and Toolkit 2.x uses `{ }` ([older dialects](rpgcode-dialects.md)). The ADR needs correcting.
2. **The architecture spine's `Deferred` list** still carries the per-tick budget and the legacy seconds-per-step conversion as unruled. The settling rules are in [errors and threads](rpgcode-errors-and-threads.md); the spine line should be marked done, keeping the budget's *number* provisional.
3. ~~**AD-7's `ProgramRef`** has no field for a program's ordered run-time include list.~~ Settled by entry 3.8: a program reference carries an optional `includes` list (folded references, in the order `include()` added them), omitted when empty.
4. ~~**AD-7's compiled-program cache key** must cover the redirect table in force at compile time.~~ Settled by entry 3.8: a program reference carries an optional `redirects` table, and the cache key is the source (text, or path and source hash), the instruction version (`ir`), the include list and the redirect table.
5. **AD-10's `GameState`** carries no VM-step counter, while a snapshot "step" is defined as one VM instruction ([errors and threads](rpgcode-errors-and-threads.md)); the entry that adds per-step snapshot comparisons must place that counter or fold it into the time section.
6. **The `system.prg` role and the ownership map** are recorded in [modules and objects](rpgcode-modules-and-objects.md) and [rpgcode-functions.md](rpgcode-functions.md); the epic and architecture documents that name an owner should be checked against them when their entries are planned.
7. **An importer warning for `FileInput`.** Read lines correctly is the rule ([values, scope and conversion](rpgcode-runtime.md)); the only files whose behaviour changes are data files with LF-only lines or no final newline. Whether the importer should warn about those is open, and nothing is built for it.
