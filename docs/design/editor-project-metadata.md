# Shared project organization and friendly names

Status: owner direction, amended 2026-11-18 by the [connected native format design](native-authoring-format-set.md); exact contract fields and lifecycle behavior still require specification and verification.

Creators can organize assets in the Game drawer using optional groups within each asset category. Each asset has at most one group in its category; ungrouped assets remain directly under the category. This organization does not move files. Group nesting and the result of deleting a group are not yet decided.

Native documents own their optional **friendly name** and short description; individual scene placements, regions and interactions own theirs within the scene, keyed by their local identities. Project data owns grouping and the presentation of programs and standalone media whose formats do not provide these native fields. It does not duplicate presentation already owned by a native document. A name for a board interaction describes that interaction, not necessarily the program it references. Existing game data remains authoritative for behavior and references; editor annotations must not become competing copies of those references or replace game-visible names. Changing a friendly name does not rename a file or change game behavior.

Descriptions are discoverable on hover or keyboard focus on a name. Provide equivalent screen-reader and touch access and a place to edit them. Contextual actions distinguish editing a friendly name from renaming a file; file rename must not silently break references. Show underlying filenames when useful. The program editor itself remains governed by its real host and language contracts; the interactive mockup is not its implementation specification.

A legacy project without metadata still opens and runs. Names fall back to existing asset information or filenames, with exact precedence to be specified. Metadata belongs to the shared project, not one user's preferences. The recommended native project root is `.tkrproj`; the [project-contract story](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/3234) must specify it before implementation. Do not build a permanent project sidecar duplicating native document fields. Define how metadata survives supported moves and renames, deletion and external changes. Direct legacy editing remains available; native-only annotations on contained legacy board elements require explicit conversion to a scene with suitable identities, not a guess that a shifting slot is an identity. Failure and ambiguous identity must not silently attach metadata to the wrong object.

Cross-category labels are permitted as a possible future secondary view, not committed work. Long-form design thoughts belong in a separate space if one is created; descriptions here are short explanations. The [connected editor mockup](connected-editor/README.md) illustrates the workspace and connections, not a completed implementation.
