# ADR 0004 — Unified Script AST, Step IR, and Deterministic Plugin Event Infrastructure

* **Status:** Accepted
* **Date:** 2026-10-11
* **Context documents:** [architecture-options.md](../architecture-options.md), [spec/README.md](../spec/README.md), [guardrails.md](../guardrails.md), [0001-typescript-core.md](0001-typescript-core.md)

## Context

Legacy RPG Toolkit 3 had two major architectural bottlenecks in extensibility and scripting:

1. **Native Win32 DLL Plugins:** Subsystems like menus (`menuPlugin`) and battles (`fightPlugin`), along with arbitrary community extensions, were implemented as Win32 DLLs called via raw string dispatch on unrecognized script tokens. This model breaks cross-platform execution (web, mobile, macOS, Linux), cannot be sandboxed, violates rule **G2** (core touches no OS APIs), and prevents serializing mid-tick game state (**G1**).
2. **Two Incompatible Scripting Dialects:** The project must support legacy game worlds spanning two eras:
   * **Toolkit 2.x:** Line-oriented BASIC-style scripts (`#Command` syntax, bare text lines treated as dialogue boxes, unquoted string arguments, variable sigils `$` and `!`, `< >` block delimiters, and `#Fbranch` jumps without return; formerly assumed to be subroutine call stacks, corrected in facts-round-6 Q8).
   * **Toolkit 3.x:** C-style block expressions (`{ }`, `//` comments, dynamic variants, C++ style class declarations, operator overloads, and explicit string quotes).
   Forensic analysis confirmed that a 100% mechanical source-to-source file conversion from TK2 to TK3 is impossible without lossy heuristics or broken script logic. Modifying a user's legacy `.prg` files on disk is unacceptable.
3. **Core Engine Constraints:** Under **G1** (VM is an explicit step machine with plain JSON state) and **G3** (strict determinism), script execution and event handling must never rely on asynchronous Node `EventEmitter`s, Promises, or microtasks. Mid-tick state must remain fully serializable for save games and headless golden replay (**G5**).

## Decision

1. **Three-Tier Script Lowering Pipeline:**
   Script execution is separated into three distinct layers:
   * **Dialect Frontends:** Independent parsers for TK2 and TK3 produce an identical **Unified Semantic AST**. TK2 scripts are parsed under non-destructive TK2 grammatical rules (bare lines $\rightarrow$ dialogue, unquoted words without sigils in commands $\rightarrow$ strings, `< >` $\rightarrow$ blocks) without modifying files on disk.
   * **Lowering to Step IR:** The compiler lowers the Unified AST to a flat, linear array of serializable step instructions (`StepIR`: `OP_PUSH`, `OP_CALL`, `OP_JUMP`, `OP_YIELD`, `OP_RETURN`). The runtime VM never interprets AST nodes or source syntax during game loops; it steps through IR instructions.
   * **Runtime Dispatch:** When `OP_CALL` executes, the VM resolves the command name through a unified Command Registry.

2. **Dogfooded Standard Library as Plugins:**
   The core RPGCode built-in library (~280 functions across dialogue, graphics, audio, movement, and math) implements the `PluginDefinition` interface. Core commands and community extensions share the exact same runtime contract:
   ```typescript
   export interface PluginDefinition {
     id: string;
     version: string;
     commands?: readonly BuiltinSpec[]; // { name, aliases, params, call } — AD-8
     decoders?: readonly AssetDecoder[]; // ordered format contributions — AD-31
     subsystems?: {
       battle?: BattleSubsystem;
       menu?: MenuSubsystem;
       dialogue?: DialogueSubsystem;
     };
   }

   ```
   **Amended by [ADR 0024](0024-plugin-data-contributions.md) (2026-11-09, Proposed).** `PluginDefinition` gains one optional plain-data field, `contributes`: one entry for each native data contract the plugin extends, with the plugin's schema, current data version, migration operations and `renamedFrom` for its block on that contract. Nothing else in this interface changes, and the core still loads no plugin code.
   `BuiltinSpec` may also carry optional plain-data documentation metadata: `doc.summary` and `doc.behaviour` are required together when present, with optional source-order `examples` (strings or `{code, caption?, result?}` records), multi-valued lowercase-kebab `groups`, `returns`, `throws`, `see`, `since`, `replacedBy` targets (`{kind: "command", name}` or `{kind: "syntax", text}`), `reason`, `access`, `waits`, `effects`, `todo`, `author`, `license`, orthogonal `tags` (`legacy`, `alias`, `deprecated`, `obsolete` or `experimental`) and runner-specific `support` entries. A support entry has level `full`, `partial` or `none`; partial and none entries require a non-empty note, and runner ids are non-empty lowercase kebab-case strings. `experimental` conflicts with `obsolete`, and `deprecated` plus `experimental` is invalid. Deprecated or obsolete commands require both a replacement target and a plain-language reason; command replacement names resolve against the registered command set. `see` entries resolve either to a registered command or to an existing `docs/spec/<path>#<anchor>`. `access` defaults to `public`; `internal` entries remain in the projection but are hidden from documentation/help consumers. `waits.kind` includes `host-request` for a continuation waiting on an external request, alongside deterministic per-thread wait kinds; `effects` describe emitted effect kinds, while `todo` is explicit follow-up metadata. `ParamSpec.doc`, when present, is an object with a summary plus optional unit, tags (never `alias`), support, prose `default` (the value used when omitted), `ifOmitted` (what happens when an optional/output parameter is omitted), numeric `range` (`min?`, `max?`, `note?`, with min ≤ max), enum values, type and since. These fields do not alter arity, coercion or by-reference binding. Documentation is registration metadata only: it is never passed to a handler and never enters `CommandResult`, `CommandView`, `GameState`, `VmState`, effects, snapshots, save data, input logs or state hashes.
   The core exposes a pure `commandDocumentation` projection over the ordered resolved plugin list. It copies only immutable plain data, preserves plugin and declaration order, and emits the canonical spelling plus one entry per alias. Alias entries retain the canonical name and automatically carry the `alias` tag; they do not acquire `legacy`. An explicit `alias` tag on a canonical spelling is invalid. Missing transitional documentation is represented by explicit `null` values in the projection. Optional plugin-level `doc` metadata contains a summary, owned group declarations (`id`, display name and summary) and required plugin ids; requirements resolve against the resolved list. Projection emits plugin documentation and access flags as plain data, does not collapse overridden layers, and retains no handlers or runtime state. `BuiltinSpec` and plugin docs use no JSDoc parser at runtime; consumers may map these fields to JSDoc/TSDoc concepts.
   `decoders` is an optional ordered contribution to the asset pipeline. The
   plugin assembly layer starts with the core decoder set and layers plugin
   definitions in manifest order. A plugin's own duplicate decoder id or
   extension is rejected as a programmer error; across plugin layers, the later
   plugin wins and emits exactly one `decoder.overridden` warning per replaced
   claim, naming the previous and replacement plugins. Replacing an id replaces
   that decoder and its remaining claims. Dispatch remains extension-first; for
   magic headers, layers are scanned from latest to earliest while decoder order
   within each layer is preserved. The low-level `createAssetRegistry`
   registration API remains strict for direct callers and rejects every
   duplicate.
   No command has private backdoors into the VM.

   A `CommandHandler` is a pure function `(view, args, next) -> { value, out?, effects?, wait? }`, which the shorthand `{ out, effects, wait? }` abbreviates to the parts beyond a plain return. It reads a read-only view of the world and never mutates state: `value` is the call's result (`null` when the command has none), `out` carries by-reference outputs as `[index, Value]` pairs the VM writes back to the caller's variables, `effects` are plain-data records the VM drains to the section owners that apply them, and `wait` parks the calling thread (AD-9). `next` is the definition the same name has in the layer below. A handler may call `next` and adjust its result, or ignore it and replace the command; where no lower layer defines the name, `next` returns the empty result (`value: null`, no `out`, no `effects`, no `wait`) and emits one `command.no-next` warning. Each name is therefore a stack of layers (command middleware), not a single winner. A repeated name or alias is an **override, not an error**: the later layer runs first and its `next` reaches the earlier definition, and the registry emits exactly one `command.overridden` warning naming the previous and replacement plugins. The only rejection is one plugin repeating a name or alias *within itself*, which assembly refuses naming the plugin. The language constructs themselves (control flow, assignment, labels, calls, returns) are `StepIR` ops and are not in the command chain, so they can be neither removed nor wrapped.

6. **One Contract, Composition, No Trust Tiers (for now):**
   Documentation discovery follows manifest order but is independent of dispatch assembly: it receives the ordered resolved plugin definitions and preserves every layer, including overridden lower layers, so provenance remains inspectable without changing the effective handler. The projection is plain data only and does not expose handlers, effects, waits or state references.

   Plugins are extensions of the application and are not gated. First-party packs, the TK2 compat plugin, domain modules and game-shipped plugins all use the one `PluginDefinition`. A manifest (an ordered list of plugin entries, plain data) selects and orders them; the engine ships a default manifest of its useful packs, in the same format a game or user edits, and anything in it may be removed, disabled, reordered or added to. The built-in `core` pack is pinned at the bottom of the chain: it can be wrapped but not removed. Manifest order is layer order: where two plugins define the same command name or alias, the later entry's handler runs first and reaches the earlier one through `next`, and registration emits exactly one `command.overridden` warning naming both. The host resolves manifest ids to code and hands `PluginDefinition` values to the registry; core loads nothing (**G2**). Plugins remain bound by **G1** (plain-data state, no Promises in script threads), **G2** (external effects go through host requests) and **G3** (deterministic): these are correctness rules, not permission checks. A less-trusting model may be added later by extending manifest entries; it needs no change to the plugin contract.

3. **TK2 Compatibility Plugin (`@tk-reawakened/plugin-tk2-compat`):**
   Legacy TK2-specific commands (`#Mwin`, `#Prompt`, `#Item`, legacy `#Fbranch` jump alias, and integer `WalkSpeed` frame rate adapters) are encapsulated within a dedicated compatibility plugin. When a TK2 project loads, the TK2 plugin activates automatically. The core VM remains clean of legacy heuristics.

4. **Deterministic Event & Lifecycle Bus:**
   Engine event handling operates through a synchronous, priority-ordered event queue stored directly in the serializable world state (`world.eventQueue`):
   ```typescript
   export interface EngineEvent<T = unknown> {
     type: string;        // e.g. "board:entity_moved", "battle:turn_start"
     tick: number;        // Deterministic engine tick counter
     sourceId?: string;   // Entity or script thread ID
     payload: T;          // Plain JSON-serializable data
   }

   export interface PluginEventHook {
     event: string;
     priority: number;    // Deterministic execution order
     handle(event: EngineEvent, context: StepContext): void;
   }
   ```
   * Events are pushed during game ticks and drained deterministically before frame draw lists are emitted.
   * Plugins can subscribe to engine events or emit new custom events into the tick pipeline.
   * Because the event queue is plain data in the world state, any mid-tick snapshot or save file preserves in-flight events with zero state loss (**G1**, **G3**).
   * **Amended by entry 19.1 (2026-10-19, owner).** The event bus is the first-class emitter model and is asynchronous: a plain emit is queued, a cancelable emit parks the emitting thread until the listeners ran in registration order, and one bus serves RPGCode and TypeScript plugins with no synchronous side door. "Synchronous, priority-ordered" and `world.eventQueue` above are superseded, and delivery order is emit order then registration order instead of `priority`. The rules are EMIT-1 to EMIT-11 in [rpgcode-modules-and-objects.md](../spec/engine/rpgcode-modules-and-objects.md#emit-1); the G1 check is written in AD-32. The "Node EventEmitter" rejection under "Alternatives considered" still stands for host-closure emitters: the emitter here is plain-JSON state, not Node's.

5. **Typed Subsystems Emitting Draw Lists (G4):**
   Heavy domains previously relegated to Win32 DLLs (battle engines, custom menu systems) are modeled as typed subsystem interfaces (`BattleSubsystem`, `MenuSubsystem`). Subsystems tick deterministically and emit `DrawCommand` lists and audio cues, allowing complete system replacements (e.g. Turn-based vs. Active Time vs. Tactical Grid) while remaining 100% renderer-agnostic.

7. **Async at the Boundary (modern JavaScript lives in the host):**
   `core` has no Promises (**G1**), but plugin authors and the engine's own packs still need asynchronous work (file I/O, `fetch`, decoding). This decision adds no mechanism of its own; it states how plugins use the ones AD-5, AD-8, AD-9 and AD-17 already define:
   * **Requests and replies are AD-5's.** A command that needs something external asks for it through an AD-17 request. Every request is **blocking** (time freezes: `advance` returns `loading` and consumes no ticks, so no thread moves) or **stream** (never touches state). Its reply is an input event, `asset { reqId, bytes }`, `blob.loaded` and so on, recorded in the canonical input log with its tick, so replay and restore are deterministic. There is no per-thread asset wait.
   * **Per-thread waits are AD-9's.** A command that must park one thread returns a `wait` of an AD-9 kind (`sleep`, `blob`, `input.key`, a plugin's own kind). Other threads keep ticking; the wait's `poll` resolves it.
   * **Continuation.** A command that needs its reply to finish names a continuation command and plain-data arguments in its result's `then`; the reply value is prepended. It is a named command, never a closure, so it survives save and restore.
   * **Host side.** The host performs the request with ordinary `async`/`await` and delivers the reply as an input. Promises never cross into `core`.
   * **Script side.** To an RPGCode author the call blocks. For a request that freezes time the whole engine waits (`loading`); for an AD-9 wait only that thread does.

   A reply that never arrives must not hang the game. For a **frozen request** ticks do not advance, so the timeout lives in the host: its timer delivers a failure reply (`bytes: null` for an asset) as an ordinary input, which is recorded like any other. For a **per-thread wait** the timeout is a tick count in the wait payload, as `sleep`'s `until` is, layered like a test runner's timeout: engine default, plugin manifest `options`, the wait's own value, then the harness override; zero means no limit. On expiry the thread resumes with an error result and a located diagnostic its error handler can catch. Separately, the VM detects a **deadlock**: every live thread is parked on another parked thread and no reply is outstanding. It reports the stuck threads and what each waits on, and in headless runs and goldens it is a hard failure.

   Illustrative example (names are provisional until entry 3 fixes the contract):

   ```typescript
   // Plugin: shows the first line of a game file.
   export const notes: PluginDefinition = {
     id: 'example.notes',
     version: '1.0.0',
     commands: {
       // Step 1: ask the host. Plain data only; no await, no closure.
       showNote: (view, [path]) => ({
         out: {},
         effects: [],
         request: { kind: 'asset', key: { area: 'files', path } },
         then: { command: 'showNote.done', args: [path] },
       }),

       // Step 2: runs when the reply input is applied. `bytes` was prepended.
       'showNote.done': (view, [bytes, path]) => ({
         out: {},
         effects: [{ kind: 'dialogue', text: firstLine(decodeText(bytes)), source: path }],
       }),
     },
   };
   ```

   ```typescript
   // Host side: ordinary modern JavaScript.
   host.handle('asset', async ({ key }) => {
     const res = await fetch(resolveUrl(key));
     return new Uint8Array(await res.arrayBuffer());
   });
   ```

   Rules that keep this safe: a result needed inside one command invocation is split into request and continuation, or provided by the host as a synchronous lookup it can answer from memory; the headless harness scripts replies as inputs, so plugin tests need no host. A small helper that builds the request-and-continuation record, and a test helper for scripted replies, belong with entry 3.
8. **First-Class Callables, Serializable Step Closures, and Pure-RPGCode Middleware (Epic 18):**
   To enable modular feature libraries (such as custom HUDs and battle engines) written directly in RPGCode without requiring native TypeScript plugins or global symbol monkey-patching:
   * **Callable Values (`Value.Callable`):** Callables are first-class values represented as plain serializable data records:
     ```typescript
     export interface CallableValue {
       type: 'callable';
       def: string;              // Deterministic program definition ID (e.g. "items.prg#lambda_1")
       captures: readonly string[]; // IDs of captured environment cells
       receiver: string | null;  // Object ID for 'this', or null
     }
     ```
   * **Step IR Instruction Extensions:**
     - `load_fn { def, captures }` (the ruling's `OP_MAKE_CALLABLE`): pushes a new callable record referencing static definition `def` and capturing cell IDs.
     - `call_indirect { argc }` (the ruling's `OP_CALL_INDIRECT`): dynamically invokes the callable value pushed below its `argc` arguments, evaluated from a primary expression.
     - `newObject` and `initMember { key }` (entry 19.3, OOP-10): a dictionary literal is `newObject` (makes an empty dictionary in the handle table and pushes its handle), then each value expression followed by `initMember`, which pops the value and writes it to the dictionary below it.
     - `get_member_bound { name }` (the ruling's `OP_GET_MEMBER_BOUND`, entry 19.4): reads a member and, if the value is a callable with no receiver, binds its `receiver` to the object it was read from.
   * **Step-Machine Closure Serialization (G1):**
     Lexical captures are stored as explicit environment cells in game state (`vm.cells`). Mid-tick snapshots, save files, and golden replays serialize active closures and suspended `next` frames as plain JSON without relying on opaque host closures.
   * **Auto-Bound Receivers:**
     Property access `obj.method` produces a callable bound to `obj`, eliminating JavaScript-style detached-receiver pitfalls. Explicit rebinding is provided by the built-in `bindThis(fn, targetObj)`.
   * **Pure-RPGCode Middleware (`registerPlugin`):**
     The native TypeScript plugin middleware architecture (`CommandHandler` chaining through `next`) is dogfooded in RPGCode via `registerPlugin(pluginDefinition)`. RPGCode scripts wrap engine commands cleanly in an onion pipeline without polluting or colliding with global variables. **Status (entry 18.7, Proposed ruling, pending owner review): `registerPlugin` is the designed route and is not built; the layered wrapping this epic ships is the environment-table mechanism of the amendments below, with its evidence in the entry 18.7 amendment.**
   * **The environment table, symbol reassignment and `bindingOf` (Amendment, entry 18.5, 2026-10-18; Proposed ruling, pending owner review):**
     The four-tier lookup skeleton (decision AD-8's redirect / script function / built-in / extension tiers, of which the redirect and script-function tiers were stubs in `registry.ts`) is replaced by **one environment table** with one resolution function, `resolveCall`. A plain-name call `f(args)` resolves in this order, first match wins: (1) the running scope's own symbol — the variable `f` that a read of `f` reaches from the running frame (a local of that frame, else the global), when it currently holds a callable value; (2) a built-in engine command; (3) a script function of the calling program (name and parameter count, MOD-1); (4) a command a plugin claims. Reading a name is **not** this lookup: it reads the variable, so `x = castint` never yields a command and an unset name still reads `""`/0. The VM's own commands (the module directives `include`, `redirect`, `killRedirect`, `killAllRedirects`, and `bindingOf`) are answered before the table and are not part of it. The table is **not materialised**: its bottom layers are the assembled command registry and the program's functions, read where they already live, and the only storage a reassignment needs is the variable that holds the callable (`vm.globals` or a frame's locals), so no save shape changes. *Rejected alternative:* a symbol-to-handle entry per built-in name (about 300) in `vm`, which changes every save's shape and adds nothing a variable does not already give.
     * **Reassignment takes a callable only.** Storing a callable value in a variable whose name is a command's therefore reassigns that name *for calls from a scope that reaches the variable*, which is how a script intercepts, wraps or replaces an engine command. An assignment whose value is not a callable does not touch entry 1, so `castint = 99` leaves `castint(4.75)` meaning the command: ruling R-35 is preserved bit for bit, and since 3.1 has no callable values every 3.1 program resolves exactly as before. The scope is the running frame's locals and the global — the same variable a read would reach — so a function does not see its caller's locals (the 18.4 implementation walked every frame on the thread, which made a local binding visible to every function called under it and disagreed with variable reads; it is corrected here). *Rejected alternatives:* a per-name stack of bindings in `vm.env` with the replaced binding passed to the wrapper as a trailing argument (the shape `registerPlugin`'s `next` uses for native middleware), which needs a second storage for the current binding beside the variable (so `kill`, `local`/`global` and reads would disagree with the call), an arity rule that appends the extra argument only when the wrapper's definition accepts it, and a save-schema field for the stack; and dynamic scoping of local bindings, which would let any caller's local reroute a callee's calls.
     * **`bindingOf(name)`** is the ruled way a wrapper reaches what a name ran before it was replaced. It takes the name as a string, resolves it from the calling scope exactly as a call would at that moment, and returns a callable value: the scope's own callable when entry 1 holds one (unchanged), otherwise a handle that always runs the first of a built-in, a script function (the running program first, then every compiled program), or a plugin command of that name. A callable handle resolves **through entries 2 to 4 only, in that order** (an engine command first, then the compiled definitions), so a handle runs the binding it names and a later reassignment does not change it. Nothing of that name is `unknown.command` at the `bindingOf` call site; a non-string argument is `builtin.bad-arg`. Because each replacement asks for the binding in force at that moment, wrappers stack. A wrapper must ask *before* its assignment and keep the answer (asked from its own body the answer is itself, and the call recurses). *Rejected alternatives:* reading the name as a value, which yields the unset global `0` before the replacement and the wrapper itself after it; an engine-only form that skips the scope's callable, which makes two scripts that wrap the same command bypass each other; a bare-variable form `bindingOf(mediaPlay)`, which reads the variable first (creating the unset global) and cannot tell a name from a string value; and making a read of a command name yield its handle, which would change the value every 3.1 program reads from such a name.
     * **Captured locals share one cell with their creating frame (G1).** When a lambda captures a local, the local's storage *becomes* the cell in `vm.cells` (the frame's slot is redirected to it), so the frame and every closure that captured that name read and write the same slot: an assignment the frame makes after creation is visible inside the closure and an assignment the closure makes is visible in the frame, and a later closure built by the same frame for the same name captures the same cell. One cell per creating frame per captured name; two runs of the same code never share one. A by-reference parameter is the exception — its slot aliases the caller's variable, so it is captured by value into the closure's own cell. A plain-name call is a capture site (the call reads the variable it names), so a closure can call a local callable of its creating function (`original(file)`). *Rejected alternatives:* keeping 18.4's by-value copy, which hides later frame assignments from the closure; a fresh cell per closure, which makes two closures of one frame disagree about one variable; and leaving calls out of capture analysis, which forces the spelling `(original)(file)`.
     * **Object methods keep their place.** The implicit `this` method step stays where the VM applies it (after the built-in, script-function and plugin lookups), which departs from OOP-6's legacy order; aligning it is a legacy-fidelity change of its own and is not made here. It is flagged in [the modules and objects spec](../spec/engine/rpgcode-modules-and-objects.md#where-a-name-resolves-oop-6).
     * **Callable reassignment and `registerPlugin`.** MOD-4 says plugins register explicitly rather than overwriting global variables. The table does not contradict it for plain values, but a callable stored under a command's name now does take effect; the spec's MOD-4 bullet is amended to say so and to keep `registerPlugin` (entry 18.7) as the explicit, layered route that does not depend on reassignment.
     * **`#redirect` stays parse-time.** The legacy redirect keeps its run-wide `vm.redirects` table and its compile-time name substitution (R-42..R-44); it is not lowered to an environment assignment. Evidence: the table is run-wide and the substitution takes effect in textual order on text parsed after the call, and `withRedirects` folds the table into every compiled `ProgramRef`; a run-time assignment would make a 3.1 redirect depend on run-time scope state and interact with `run()`, `tellThread` and a restore's recompile.
     * **Save format.** A reassignment lives in `vm.globals` (or a frame's locals) as an ordinary value, so it is already plain state and needs no new section field; a closure's `captures` cells are `vm.cells`, as in 18.4, and a frame slot redirected to a cell is an existing `cell:` reference. Save validation, versioning and collection of callable values are entry 18.6's, in the amendment below.
   * **Saving, validating and collecting closures (Amendment, entry 18.6, 2026-10-18; Proposed ruling, pending owner review):**
     Callable values, `vm.cells`, `vm.cellSeq` and the frames parked inside a closure's call already serialise as plain JSON (G1); this entry makes them survive a restore and a long run. The user-facing statement is in [the language spec](../spec/engine/rpgcode-language.md#keywords-and-structure) (FUN-8, "Saving, loading and tidying up closures"); the rulings, with their evidence and rejected alternatives, are:
     * **A handle's owner program is saved: `vm.defOwners` (optional `{ [def]: ProgramRef }`).** Compiled programs live outside state and a restore rebuilds only the programs its frames name, so a callable stored in a global whose creating program has ended resolved to no definition after a restore (measured: `f = (x) => x * 2` stored by a program that then `run`s another one that sleeps, snapshot while it sleeps, restore: `callable.unknown-def`, where the original run gives `6`). `load_fn` records `frame.program` against the lambda's `def`, and `bindingOf` records the defining program of a script function; the first owner recorded stays; a command handle has none. A restore compiles the owners with the frames' programs before it checks handles. *Rejected alternatives:* a `ProgramRef` in every handle (changes the ruled `CallableValue` shape and repeats an inline program's text in every copy); saving every compiled program's reference (grows for ever, records programs that never made a callable); rebuilding the owner from the `def` text (impossible for `<inline>`, blind to includes and the redirect table the program was compiled with).
     * **Two-stage validation, both typed and located by their place in the save.** `restoreGameState` checks shape with no program (malformed handle, a handle's `captures` entry, a frame slot's or operand's `cell:` reference or a wait's resume reference naming a missing cell, `cellSeq` absent or lower than an existing id, a malformed id, a bad `vm.defOwners` entry); `verifyRestoredHandles` runs after the host has rebuilt its services and checks each handle against the definitions of the compiled programs and the command table (unknown `def`, capture count different from the definition's). Codes: `restore.callable-malformed`, `restore.cell-missing`, `restore.cell-seq`, `restore.callable-unknown-def`, `restore.callable-captures`, and `restore.shape` for the rest. They are `restore.` failures: load-time, never caught by a script. *Rejected alternative:* leaving a bad handle until the call that uses it (the 18.4 behaviour), which reports `callable.unknown-def` at a call site that has nothing to do with the cause, possibly hours after the load.
     * **Cells are collected by reachability, in the object pass.** `collectObjects` took every cell's value as a root and nothing removed a cell, so a lambda made on every pass of a loop leaked one cell per pass (measured: 100 lambdas made in a loop left 100 cells and 99 of them unreachable). The end-of-tick pass now first removes every cell not reachable from the globals, the frames (locals, operands, return values, wait resume references) and the members of the objects in the handle table, through callables' `captures`, `cell:` references and live cells' values; then the unchanged object pass runs with the remaining cells as its roots. A cell kept only by an object that this pass frees goes in the next tick's pass, as an object chain already does one link per tick. The pass is skipped when `vm.cells` and `vm.defOwners` are both absent, so a game with no closure behaves exactly as before. *Rejected alternatives:* reference counting (a recursive local lambda's cell is referenced by its own value and would never be freed); leaving cells for ever (the leak); one combined object-and-cell fixpoint loop (it would free an object chain in one tick where R-34 frees one link per tick, changing the observable timing of 3.1-compatible programs).
     * **`vm.cellSeq` only grows.** A freed cell's id is never issued again, so an id names at most one cell over a whole run and a stale reference cannot silently read another closure's variable. *Rejected alternative:* reusing the lowest free id, which makes a saved id depend on when the pass ran.
     * **No schema or compiler bump.** The `vm` section stays at version 5 and `COMPILER_VERSION` at 2. Evidence: `cells` and `cellSeq` were added by 18.4 as optional fields without a bump and `defOwners` follows them, so no state without a closure changes; entry 18.5 changed `FunctionInfo.captures` only and emitted no different op, so a saved instruction offset still lands on the same op; the only shape that changed, a lambda handle's `captures` count, is refused explicitly by `restore.callable-captures`; and `schema.vm` is part of every state hash, so a bump re-records every script, scene and closing golden for no migration benefit. *Rejected alternative:* `SCHEMA_VERSIONS.vm` 5 to 6, with a migration step refusing a v5 save that holds a callable or a cell, which would also refuse saves whose handles are valid under the current rules.
     * **Known limits, not changed here.** A `def` of an inline program is `<inline>#lambda_N`, so two inline programs that define a lambda of the same number share a `def` (the running program's definition wins, then the first compiled program that defines it); file programs are unambiguous. A handle's `receiver` is validated for shape only (`string` or `null`): no instruction makes a non-null receiver yet (`bindThis` and the auto-bound member access are not built), and what keeps a receiver's object alive is for the entry that adds them to rule.
   * **Middleware libraries in pure RPGCode, and `registerPlugin` (Amendment, entry 18.7, 2026-10-18; Proposed ruling, pending owner review):**
     The epic's last entry proves the 18.5 mechanism end to end with authored RPGCode libraries (`packages/core/test/fixtures/plugins/`) and pins one in the headless script golden (`synthetic-11-middleware`); the user-facing recipe is [Writing a middleware library today](../spec/engine/rpgcode-modules-and-objects.md#writing-a-middleware-library-today-entry-187). The tests run them under the VM, the script host and the engine: interception, chaining to the engine through `bindingOf`, the order of four stacked layers, removing a layer, a wrapper that waits for ticks and for a key (with a by-reference parameter), a save at every tick including inside a wrapped wait, and two identical runs. Every earlier golden is unchanged.
     * **Done and not done.** Done: callable reassignment of a command's name, `bindingOf` chaining and stacking, shared closure cells, save/restore and collection of all of it (entries 18.2 to 18.6) and the libraries above. **Not done: the `registerPlugin(pluginDefinition)` command named in this decision's middleware bullet is not built, and it is not part of this epic.** Evidence: (1) the plan of entry 18.7 and its `tickets.toml` verify line ask for "multi-plugin middleware fixtures ... demonstrating chained command wrapping" with "3+ plugins wrapping the same built-in", and nothing in either asks for a registration command; (2) the epic's "Done when" list item 4 states the route as reassigning a global symbol and saving the original handle, and no item mentions `registerPlugin`; (3) no entry of the epic implements it, while `registerPlugin` is named only in the rulings entry (18.1, D-11) and in the forward references added by 18.5 and 18.6; (4) it needs rulings that were never made: how `next` is supplied to a command interceptor (18.5 rejected passing the replaced binding as a trailing argument, because it needs a second storage for the current binding beside the variable and an arity rule that appends the extra argument only when the wrapper's definition accepts it), what `commands` is when it holds many names and how its entries are ordered against reassignment, whether a plugin's layer is saved in `vm` or rebuilt at start-up (MOD-4's lifecycle bullet says rebuilt, the 18.5 mechanism saves it), and how `name` identifies a plugin for removal. Inventing those here would be unreviewed language design. *Rejected alternative:* implementing `registerPlugin` now as sugar over the 18.5 table (a built-in that loops the `commands` dictionary and runs `bindingOf` and a reassignment for each), which would settle the four rulings above by whatever the implementation happened to do. *Proposed:* a later ticket, outside epic 18, rules the four points and builds `registerPlugin` over the table; until then the spec marks MOD-4's `registerPlugin` text as designed, not built.
     * **Known limits seen while writing the libraries, not changed here.** A wrapper takes exactly the arguments a call passes: the arity of a call follows the lambda's own parameter list (measured: `mwin("a", 1)` against a one-parameter wrapper, `mwin("a")` against a two-parameter one and `mwin()` all give `callable.arity`), so a command with optional arguments needs a wrapper written for the call shapes the game uses. A parameter the command writes back must be declared `&` in the wrapper or the value stays in the wrapper. `kill(name)` removes every layer under a name at once (see the spec recipe).
   * **Platform epic amendment (entry 19.1, 2026-10-19, owner).** The two items 18.6 and 18.7 left unbuilt are ruled and MUST be built by Epic 19: `OP_GET_MEMBER_BOUND` and the receiver rules (OOP-11, entry 19.4: a callable's receiver is a collection root, a callable that already has a receiver keeps it, `bindThis` rebinds) and `registerPlugin` (MOD-4, entry 19.8: a thin layer over the 18.5 environment table, never a second dispatch mechanism). Dictionary objects (OOP-10) are the object storage under both. Packages (name, version, namespace, declared host requests) share the one plugin manifest of decision 6 ([PKG-1](../spec/engine/rpgcode-modules-and-objects.md#pkg-1)); the trust baseline is [ADR 0008](0008-rpgcode-packages-and-trust-baseline.md). The statements above that `registerPlugin` "is not built" describe the state at entry 18.7 and are superseded by the Epic 19 entries.
   * **Receivers built (Amendment, entry 19.4, 2026-10-19).** `get_member_bound { name }` is emitted for every `.` and `->` member read; a callable that already has a receiver keeps it, a receiver-less one is copied with the object's handle, and a standalone lambda has `this` unset. `bindThis(fn, obj)` is a core command that returns a rebound copy and never changes the original. A callable's receiver is a root of the object collection and is checked when a save is restored, so the statement in the 18.6 amendment that no instruction makes a non-null receiver is superseded. Spec: [OOP-11](../spec/engine/rpgcode-modules-and-objects.md#oop-11).
   * **`registerPlugin` built (Amendment, entry 19.8, 2026-10-19).** Decision 8's `registerPlugin(pluginDefinition)` exists: a dictionary of commands whose interceptors take `(args..., next)` registers ordered layers, and the wrapper of each layer is a callable the VM defines (`plugin.layer:<id>`). The layers are held in the running game's layer table, not in `GameState`, per the owner's MOD-4 point 3 (package layers are rebuilt at start-up and are not saved); a call reaches them through the one environment table, as part of its first entry, so `resolveCall` gains nothing and there is no second dispatch mechanism. The layer table is rebuilt by running package start-up on a fresh state before a restore (`runPackageStartup`). The save record of package names and versions waits for the package loader (PKG-7). Spec: [MOD-4, how the layers are held](../spec/engine/rpgcode-modules-and-objects.md#registerplugin-layers-entry-198).

## Consequences

**Positive**
* **Clean-room separation:** The core engine remains modern TypeScript without legacy syntactic clutter.
* **100% backward compatibility:** 1990s and 2000s legacy games run directly from disk without destructive source conversion.
* **Ecosystem parity:** Third-party modders build plugins using the exact same API used by the engine's standard library.
* **Save/replay safety:** Event hooks and custom events cannot cause non-deterministic desyncs or un-saveable closure states.

**Negative / risks, with mitigations**
* *IR Lowering overhead:* Compiling AST to Step IR introduces a small compilation step. **Mitigation:** IR is cached by source hash (`ProgramCache`, E-91); compilation occurs at asset load time.
* *Plugin execution budget:* Malicious or buggy plugins could loop indefinitely. **Mitigation:** VM step machine enforces a maximum step budget per tick; commands must yield cooperatively.
* *Plugin collisions:* Command layers stack in manifest order and the later layer runs first, with `next` reaching the one below; a repeated name raises one `command.overridden` warning. Decoder layers use the same later-plugin-wins rule and emit one `decoder.overridden` warning per replaced id or extension. A plugin repeating its own command or decoder claim is rejected, while direct `createAssetRegistry` registration remains strict.
* *Untrusted plugin code:* Plugins are ungated, so a game-shipped plugin runs with the engine's authority. **Accepted for now; refined by [ADR 0008](0008-rpgcode-packages-and-trust-baseline.md)**, which records that RPGCode packages are trusted because the VM contains them and that native TypeScript plugins are author-installed only. The seam for a stricter model is the manifest entry (see decision 6); the engine rules G1 to G3 still bind every plugin.

## Alternatives considered

* **Raw AST Interpretation:** Stepping an AST tree directly at runtime. Rejected: tree-walking state is bulky to serialize in save states; linear IR simplifies VM step serialization.
* **Node EventEmitter:** Using asynchronous event emitters. Rejected: violates **G1** and **G3**; asynchronous microtasks cannot be deterministically serialized or replayed.
* **Destructive File Transpilation:** Forcing users to convert TK2 scripts to TK3 files before running. Rejected: forensic research showed lossy conversions that break user scripts.
