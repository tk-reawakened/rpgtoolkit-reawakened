# ADR 0041 — Blocked-step repeat distance, program-driven end-of-step processing and the path-query contract

* **Status:** Accepted by the owner (Jensen), 2026-11-21
* **Date:** 2026-11-21
* **Context documents:** [R-64](../spec/engine/movement-and-collision.md#r-64), [E-42](../spec/engine/movement-and-collision.md#e-42), [R-65](../spec/engine/movement-and-collision.md#r-65), [R-63](../spec/engine/movement-and-collision.md#r-63), [party steps](../spec/engine/movement-and-collision.md#reawakened-party-steps), [`playergetpath`/`itemgetpath`](../spec/engine/rpgcode-functions.md#r-69), [live blocking thread](../spec/engine/rpgcode-errors-and-threads.md#reawakened-live-blocking-thread), [Round 17 facts](../provenance/facts-round-17.md), [Round 18 facts](../provenance/facts-round-18.md), [ADR 0040](0040-tile-step-precheck-queues-and-linked-edge-preflight.md), [ADR 0007](0007-docs-spec-is-the-normative-specification.md)
* **Tickets:** [#1281](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1281), [#3315](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/3315)

## Summary

1. A counted blocked player direction-style tile step ([R-64](../spec/engine/movement-and-collision.md#r-64) item 2) adds one step's worth — 32 px in tile mode — to the repeat distance of every step-activated repeat program whose area the **attempted destination** overlaps, on any contact. A repeat program the attempted destination does not overlap has its counter reset exactly as a normal step that leaves the area does (E-42). Pressing into a wall can therefore re-fire a repeat program, once per blocked press. This resolves ambiguity 6 of PR #3311 (the proposed ruling recorded as P-19) in favour of legacy.
2. End-of-step processing — the party step counter, step-activated programs and items, repeat distances and the random-battle test — runs for **both completed and blocked** counted steps only while no blocking script is alive; it never runs during an ordinary (non-thread) program's synchronous turn, and it does run for thread or multitask-driven movement exactly as in free-roaming. Reawakened deliberately does **not** adopt legacy's per-frame program and encounter tests during main-loop pathfinding. This resolves ambiguity 3 in favour of R-64's existing wording and makes the predicate exact.
3. `playergetpath` and `itemgetpath` match the legacy contract: the one-argument form returns the number of queued entries **including** the point being walked toward (idle 0); the four-argument form writes the entry's point as `floor(value + 0.5)` whole pixels, with index 0 the active step's target; a negative or out-of-range index writes nothing and raises nothing; any other argument count is the standard catchable wrong-count error; neither command waits or mutates movement. Under R-65 a direction entry's reported point is computed at call time and can change after an earlier blocked step, a deliberate departure from legacy's fixed point; Reawakened also saves the queue with entry kinds where legacy lost it.

## Context

[R-63 to R-66](../spec/engine/movement-and-collision.md#r-63) settled the tile-step destination precheck, the composition of a blocked step and the linked-edge preflight ([ADR 0040](0040-tile-step-precheck-queues-and-linked-edge-preflight.md)). Their implementation in PR #3311 and the reviews around it recorded six open ambiguities. Two of them are decided here because Round 18 answers them.

The first is **ambiguity 6, proposed ruling P-19**: does a counted blocked step add distance to a step-activated repeat-distance program? R-64 item 2 grants the tile to the party remainder and names the step-triggered programs, item activations and random-battle check, but says nothing about repeat distance. The movement oracle encoded the conservative answer (0 px), leaving authors unable to rely on either behaviour. [Round 18](../provenance/facts-round-18.md) records the original engine's answer: the blocked step runs the same finished-move processing and adds one step's worth to a repeat program only when the attempted destination overlaps its area, otherwise it resets the counter (`docs/provenance/facts-round-18.md:23-35`, from source). It also records that pressing into a wall can re-fire a repeat program once per blocked press.

The second is **ambiguity 3**: which movement sources suppress end-of-step processing. R-64 item 2 already says a non-threaded program driving the player synchronously suppresses it. Round 18 spells the three cases out (`docs/provenance/facts-round-18.md:37-43`, from source): an ordinary program suppresses; a thread or multitask program counts as free-roaming; a main-loop pathfinding walk runs the tests on every frame. The first two agree with R-64 as written; the third is a legacy quirk Reawakened should not copy. What was missing was an exact, deterministic predicate that names the state the engine can test.

Separately, issue [#3315](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/3315) found that `playergetpath` and `itemgetpath` do not implement the contract the original command offers: they require four arguments, return 0/1 rather than the queue count, write zeroes for a missing index, and their specification rows are one line each. Round 18 records the contract (`docs/provenance/facts-round-18.md:49-62`, certain for entry 0 and for the unchanged point, from source for the rest), and R-65 already changed what a direction entry means. This ADR records the contract before the code follows it (G7, [ADR 0007](0007-docs-spec-is-the-normative-specification.md)).

## Decision

1. **Blocked steps feed repeat distance (R-67).** On a counted blocked player direction-style tile step, one step's worth — 32 px, the same 8192-unit contribution R-64 item 2 gives `party.stepRemainder` — is added to the repeat distance of every step-activated repeat program whose region the attempted destination overlaps, on any contact. A repeat program the attempted destination does not overlap has its counter reset exactly as E-42 resets it when a normal step leaves the area, so it is armed to fire on the next overlapping step. Reaching `distanceRepeat` fires the program and resets its distance to zero, as after any firing. The distance is part of end-of-step processing and so obeys R-68. Pixel movement has no counted blocked player step in Reawakened (R-64 is tile-only), so it adds nothing; if a later ruling extends counted blocked steps to pixel movement, the worth added is the pixel step size (R-62), as legacy did.
2. **End-of-step processing needs a free main loop (R-68).** End-of-step processing runs for completed and blocked counted steps exactly while no blocking script is alive. The exact predicate is a live blocking thread — a thread of kind `blocking` whose status is not `finished`, whether ready, running or parked in a global wait. This is the `blocking`-program half of the test the held-direction rule calls "a blocking script owns the key queue". A background, board or item thread is never a blocking script, even while parked in its own movement wait, so thread- and multitask-driven movement counts as free-roaming. Legacy's per-frame program and encounter tests during main-loop pathfinding are deliberately not adopted: Reawakened keeps per-completed-step processing.
3. **Path-query contract (R-69).** `playergetpath(handle)` returns the queue count including the point being walked toward (idle 0). `playergetpath(handle, index, &x, &y)` returns the same count and writes the entry's point as `floor(value + 0.5)` whole pixels; index 0 is the active step's target, or the first queued entry when no step is active. A negative or out-of-range index writes nothing, raises nothing and leaves both variables untouched. Any argument count other than one or four raises the standard catchable wrong-count error and writes nothing. Neither command waits or changes movement. A linked waypoint vector is not a queue; a copied one is queued and counted in full once per cycle. Under R-65 a direction entry's reported point is its computed destination at call time, so it can change after an earlier blocked step; legacy kept the point fixed as first computed. This is the required consequence of R-65, not a new choice. Reawakened saves and restores the queue with entry kinds where legacy lost it. The 3.1 item command's missing-handle message says "player not found"; only the message text is kept.

## Ruling 1 — a counted blocked step adds one step's worth to repeat distance

**Approved ruling (owner: Jensen, 2026-11-21).** A blocked step that the player spends walking into a wall still counts as a step for programs that fire every so many pixels, so a program in front of the player can fire again — and because the attempted destination is what is tested, pressing into a wall can set it off once per press.

**Lands in.** `docs/spec/engine/movement-and-collision.md` — new R-67, the E-42 amendment, R-64 item 2 cross-reference and evidence, and the party-steps rule's item 5 cross-reference; `_bmad-output/initiative-rpgtoolkit-reawakened/epic-movement-triggers/story-independent-movement-oracle-and-authored-fixtures-plan.md` (P-19 recorded as settled); `_bmad-output/backlog/bug-tile-movement-destination-collision.md` (record); this ADR.

**Evidence.** Round 18: a blocked step ends immediately but still runs the finished-move processing at the attempted position, and one step's worth is added — 32 in tile mode (`docs/provenance/facts-round-18.md:23`, `:25-27`, from source); a destination outside the area resets instead of adding, and the program is left ready to fire (`:28`, from source); a repeat program re-fires once per blocked press, with 32 px or less firing every press and 64 px every second press (`:30-35`, from source). E-42 states the reset-on-leaving rule ([E-42](../spec/engine/movement-and-collision.md#e-42)). R-64 item 2 is the counted-step anchor and already tests the step at its intended destination (`docs/provenance/facts-round-17.md:78-81`, certain).

**Rejected alternative.** Add nothing, as proposed ruling P-19 recorded. It contradicts the legacy finished-move processing, which was traced in every branch, and makes a repeat program in front of a wall impossible to author deliberately. Equally rejected: test the player's standing position instead of the attempted destination; legacy tests the destination, and a player standing outside the region could never fire the program it is trying to walk into.

**If ruled otherwise.** Restore P-19's zero contribution, delete R-67 and the E-42 amendment, and accept that a counted blocked step neither advances nor re-arms a repeat program.

## Ruling 2 — end-of-step processing needs a free main loop

**Approved ruling (owner: Jensen, 2026-11-21).** Stepping into a wall is counted only when the game, not a script, is running the player: a program that walks the player itself skips the step counter, step-on programs, repeat distance and random battles, while a walking NPC's own thread is ordinary game movement and counts like free roaming. Pathfinding walks count once per step, not once per frame.

**Lands in.** `docs/spec/engine/movement-and-collision.md` — R-64 item 2 amended in place, new R-68, party-steps item 5 cross-reference; `_bmad-output/backlog/bug-tile-movement-destination-collision.md` (implementation follow-up); this ADR.

**Evidence.** Round 18's movement-source table (`docs/provenance/facts-round-18.md:37-43`, from source): an ordinary non-thread program's blocking movement never runs the finished-move processing, blocked or not (`:41`); a thread or multitask program behaves like free-roaming, including re-firing (`:42`); a main-loop pathfinding walk runs the program and encounter tests on every frame, each adding a whole step's worth (`:43`). Round 17 records the same suppression for a synchronously driving program, and that thread-driven movement runs in the main loop and counts (`docs/provenance/facts-round-17.md:78-81`, certain). The predicate is the `blocking`-program half of the [held-direction rule](../spec/engine/display-input-audio.md#reawakened-held-direction-movement), whose test is "a blocking program is alive, or any thread holds a global wait"; the [live blocking thread](../spec/engine/rpgcode-errors-and-threads.md#reawakened-live-blocking-thread) rule defines the thread kind.

**Rejected alternative.** Use the full script-ownership test (any thread's global wait). A background thread parked in its own movement wait would then suppress its own step, contradicting the thread/multitask row that says such movement counts. Also rejected: adopt legacy's per-frame pathfinding tests. They make the encounter rate and repeat firing depend on the advance cadence rather than on distance walked, and they contradict the per-completed-step rule the party counter is built on.

**If ruled otherwise.** Keep the per-frame pathfinding tests, or treat thread-driven movement as suppressed; both contradict Round 18's table and would need their own owner ruling.

## Ruling 3 — the path-query contract

**Approved ruling (owner: Jensen, 2026-11-21).** Called with just a character or item, these commands say how many destinations are waiting, including the one it is walking toward right now, so a character standing still reports 0; called with an index and two variables, they write that destination's whole-pixel point and leave the variables alone when there is no such destination.

**Lands in.** `docs/spec/engine/rpgcode-functions.md` — the `playergetpath` and `itemgetpath` rows and new R-69; `docs/spec/engine/movement-and-collision.md` — R-65 item 4 cross-reference; `_bmad-output/backlog/bug-tile-movement-destination-collision.md` (follow-up); this ADR.

**Evidence.** Round 18: with one handle the commands return the entry count, with an index and two variables they write the point rounded to whole pixels, and an index past the end writes nothing (`docs/provenance/facts-round-18.md:49-52`, from source); entry 0 is the point being walked toward and the count includes it (`:54`, certain); a linked waypoint path reports 0 (`:56`, from source); a reported point never changed after a blocked step in legacy (`:58-62`, certain); the queue is not saved and is lost on load (`:85-89`, certain). E-22 distinguishes a copied waypoint vector from a linked one ([E-22](../spec/engine/movement-and-collision.md#e-22)). R-65 item 4 requires Reawakened saves to keep entry kinds. The 3.1 message text is carried from the owner-relayed contract on #3315.

**Rejected alternative.** Keep an absolute pixel on a direction entry so its reported point never changes; R-65 rejects that conversion because a direction queued after a blocked step would then cross the obstacle the block protected. Also rejected: keep the current 0/1 result and write zeroes for a missing index — that is the drift #3315 reports, and it silently overwrites a caller's variables.

**If ruled otherwise.** Restore the absolute direction point, the 0/1 result and the zero-write for a missing index, and accept both the wall-crossing behaviour and the silent variable overwrite.

## Day-one rules

- Land the specification before the code: #1281 (R-67, R-68) and #3315 (R-69) implement these anchors, not their own reading of the facts.
- Test the attempted destination, never the standing position, for a counted blocked step's program, item, repeat and battle checks.
- Use one predicate for suppression — a live `blocking`-kind thread — and use it for completed and blocked steps alike. A `movement` wait held by a background thread is not a blocking script.
- Keep the path-query commands read-only. They must not clear, start, stop or rewrite a queue, and a missing index must leave the caller's variables untouched.
- Round the written point half-up with `floor(value + 0.5)`; never truncate.

## Consequences

- A wall becomes a usable trigger surface: pressing into a repeat program now advances and can re-fire it once per blocked press. Games written for legacy get the behaviour the original engine had; games that relied on the new zero-distance behaviour will see a change, and the movement oracle fixture for P-19 must be re-recorded.
- The party counter, repeat distances and random battles all stop while a blocking script is alive, for completed steps too. Reawakened's current movement phase counts completed steps regardless; this is the follow-up in #1281.
- Pathfinding keeps the per-completed-step encounter rate. A legacy game tuned around the per-frame quirk will encounter less often than it did in 3.1.
- The path-query commands become useful for queue inspection in scripts. Their reported point for a direction entry can move after a block, which authors must read as "where this step will aim", not "a frozen destination".
- Risk: a program that presses into a wall repeatedly can fire a repeat program every frame while the key is held. Mitigation: this is the documented legacy behaviour and the reason the counted step exists; authors control it with `distanceRepeat` (values above 32 px fire less often) and by not placing repeat programs against walls.
- Risk: an implementation that keeps the reported point fixed for a direction entry would reintroduce R-65's wall-crossing bug. Mitigation: R-69 states the point is computed at call time, and #3315's regression tests assert it.

## Alternatives rejected

- **Add nothing for a blocked step (P-19).** Rejected in ruling 1: it contradicts the traced legacy finished-move processing and removes a trigger authors depend on.
- **Test the standing position for repeat overlap.** Rejected in ruling 1: legacy tests the attempted destination, and a player outside the region could never fire a program in front of a wall.
- **Use the full script-ownership test for suppression.** Rejected in ruling 2: a background thread waiting on its own movement would suppress its own step.
- **Adopt the per-frame pathfinding tests.** Rejected in ruling 2: they tie encounters and repeat firing to advance cadence rather than distance walked.
- **Freeze a direction entry's reported point.** Rejected in ruling 3: it is R-65's absolute-target conversion under another name.
- **Keep the 0/1 result and zero-write.** Rejected in ruling 3: it is the drift #3315 records and overwrites the caller's variables.

## Deferred

Whether a counted blocked pixel-movement step exists at all is left to R-64's tile-only scope; R-67 states what would be added if a later ruling extends it. The 3.0.x queue behaviour (relative direction codes, nothing readable by script) is recorded in Round 18 and remains legacy context, not a Reawakened rule. Pathfinding's per-pixel sprite re-tests (E-135, R-51) are unchanged. No change is made to `push`/`playerpath` queueing, to R-66's refused crossing (which is not counted and so feeds nothing), or to the movement event vocabulary beyond the existing counted-step fields.
