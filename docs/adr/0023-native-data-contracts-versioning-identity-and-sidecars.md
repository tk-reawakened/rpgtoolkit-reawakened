# ADR 0023 — Native data contracts: per-contract versions, path identity and plugin blocks

* **Status:** Proposed (owner decisions of 2026-11-08, recorded for approval; ticket 27.1 / [#1800](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1800)). Amended with the owner's file-name ruling of 2026-11-09 (decisions 6, 8 and 11), and again the same day with the owner's plugin-block rulings (decisions 4, 5, 6, 7, 8 and 11 amended, decision 12 added; the plugin-side contract is [ADR 0024](0024-plugin-data-contributions.md)); still Proposed. The owner's 2026-11-08 ruling that plugin data lives in separate documents linked both ways is **superseded**. The **shape** of decision 5 (a contract's own fields at the top level beside the stamp, with `pluginData` as the one open dictionary) is **recommended and awaiting the owner's choice**: on 2026-11-09 he proposed a `core:` wrapper and is weighing the flat shape. The wrapper is recorded under Alternatives considered. This file keeps the old words in its name so that existing links hold.

## Context

[ADR 0005](0005-independent-product-v1-and-native-format.md) permits a native format and leaves open "schema versioning and migration policy". Research #1778 and #1799 compared notations on real recovered games and found that the layout of a document and the identity rules decide how well it survives Git far more than the notation does. In every notation tested, two branches that added the same ID merged cleanly and silently produced a duplicate.

The owner's direction is that formats are like API definitions: logical contracts, not editor screens. A contract needs a version that says what shape to expect, a name that cannot silently collide, and a place for plugin data that the core never has to interpret. This ADR records those rules. The normative text is [spec/formats/native-contracts.md](../spec/formats/native-contracts.md).

## Decision

1. **Each logical contract has its own semantic version** (`MAJOR.MINOR.PATCH`). There is no project-wide version number and no manifest of versions. Each document carries its own stamp. A plugin block carries a version of its own as well (decision 7), and there is still no project-wide registry of any of these versions.
2. **Version 1.0.0 of a contract is a promise,** honored from the release that publishes it. Before that a contract is pre-release (`1.0.0-pre.N`) and free to change.
3. **The rules are those of an API contract.** MINOR adds properties or features compatibly. PATCH fixes bugs or clarifies the contract. MAJOR breaks the contract between the editor and the engine.
   * Tightening a schema is MAJOR only when the looser rule was intended and files in use relied on it; otherwise it is a bug fix.
   * A change to what a field means is a break only when it changes the field's shape; otherwise it is a bug fix.
4. **Version strings.** Three parts always. The pre-release is dotted (`1.0.0-pre.12`), which supersedes the earlier `-pre-####` spelling because dotted numbers sort numerically with no padding. A `+build` suffix is allowed as debug evidence only and is ignored by the engine and by version precedence.
    A plugin block's `version` is written in the same form.
5. **A native document's top level is the stamp, the contract's own fields and `pluginData`** (shape **recommended, awaiting the owner's choice**; see Alternatives considered). The **stamp** is identity: required `contract` and `version` as the first two keys, optional `tags` and `metadata`. The contract's own fields, the **core fields**, are well defined at the top level beside the stamp, are listed on the contract's page, and are **closed**: an unknown key at the top level is an error. **`pluginData`** is the one open dictionary (decision 7). The **reserved top-level keys** are `contract`, `version`, `tags`, `metadata` and `pluginData`, plus the core fields of each contract. The top level admits exactly the contract's core fields and the reserved keys and nothing else, and a plugin id may not be one of them. The core (the engine and its tools) reads only the stamp and the contract's own fields, and a plugin reads only the block under its own id. `tags` and `metadata` hold no timestamps or per-save values. A missing or unreadable stamp is an error, never a guess.
6. **A document's ID is its path, extension included** (`clips/walk.tkranm`): authored, stable, lowercase, ASCII-only folding (the extension folds too, so `.TKRANM` is `.tkranm`), compared without regard to case, with `/` between parts; an empty or `.` part is dropped. The file system lookup picks the entry whose casing matches. Two paths that fold to the same ID are an error naming both. Because the extension is part of the ID, a clip and an actor can both be named `guard` (`guard.tkranm` and `guard.tkract`). Owner ruling of 2026-11-09; it settles the earlier open questions on the extension and the separator.
    A plugin id (decision 7) is not a document ID: it names a plugin, is not a path, and is never folded or rewritten by a rename.
7. **Plugin data lives in the document it belongs to, in plugin blocks** (owner ruling of 2026-11-09). The `pluginData` key of a document is a mapping from plugin id to a block. A block has exactly two keys: its own `version` (the version of that plugin's data on that contract, in the form of decision 4) and `data` (a mapping). **The core checks only the envelope:** the id is well formed ([PKG-2](../spec/engine/rpgcode-modules-and-objects.md#pkg-2), which allows qualified ids such as `com.example.weather`, and refuses the reserved keys of decision 5), the version parses, `data` is a mapping, an id appears once, and the block is self-contained. The core never interprets `data`. **The plugin owns what is inside:** its schema, its version and its migration, declared per contract in its definition ([ADR 0024](0024-plugin-data-contributions.md)). Unknown keys inside `data` are tolerated, never reported and never dropped. Data newer than the plugin is read for the keys the plugin knows. A block whose plugin is absent is preserved as written, neither validated nor run. The contract is not part of the block's key: the document that holds the block already names its contract, and a copy of that in the key would be one more thing to drift. A block is valid only on a contract its plugin declares, which only a host with the plugin installed can check. A plugin never adds a core key: adding to a clip means adding a block to it, never a new top-level key. A block exists only at the top level of a native document: a legacy binary file and a non-document object, such as a scene placement or a clip frame, have none in this version. **Proposed, needing the owner's confirmation:** something a plugin defines that has its own identity, one that other documents refer to by ID, is a document of a contract the plugin defines and not a block, and is referred to one-way by ID. This replaces the 2026-11-08 ruling that plugin data lives in its own documents, named by the owner and by each plugin document, with a missing, one-way or mismatched link an error.
8. **A checker comes first.** It reports the classes the owner ruled: a missing or malformed stamp, a duplicate ID, two paths folding to one ID and, since the 2026-11-09 ruling, a **plugin block** whose envelope is wrong (problem kinds: container, id, duplicate, shape, version, data, boundary). It never repairs, and it never reports an unknown key inside a block's `data`. It reads only native documents, the files with a registered extension; legacy files are neither read nor reported. **Retired by the 2026-11-09 ruling:** the three link classes (plugin document with no owner, owner link with no back-link, mismatched link): with plugin data inside the owning document there is no second document to link. **Proposed, needing the owner's confirmation:** a further class, extension and contract disagree, which names the path, the extension, the registered contract and the contract the stamp names. It is not one of the ruled classes and was added with decision 11. **Flagged for the owner:** with the extension in the ID, a duplicate ID can arise only from a path listed twice or two spellings of one path (a directory walk cannot produce either), so that class is now a special case of two paths folding to one ID; it is kept as ruled until the owner decides whether to keep it separate. Checks that need a plugin (a schema error on a known key, a block on a contract the plugin does not declare, a note that a plugin is absent, older or newer) are host-side, run only when the plugin is installed, and are not part of this checker ([ADR 0024](0024-plugin-data-contributions.md)). A tested rename tool follows, so moving a document rewrites every reference to its ID in one step, or changes nothing.
9. **How the first contracts are shaped.** The item, NPC and enemy family is redefined into the logical contracts the research supports, and the board's placement is separated from its definition. Animation clips, tile layers, skills and effects are translated with small corrections. The animation clip is the first contract to reach 1.0. The 1:1 importer output is a test oracle, is never published as 1.0 and is never the native format.
10. **Not promised.** A lossless migration of every legacy game, or that every game runs. The research counted 1,200 candidate files the current decoders refuse ([#1772](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1772)).
11. **File names: one custom extension per kind, prefix `tkr`.** Each contract has one extension, `.tkr` and a short lowercase ASCII kind code of three or more letters (**owner ruling of 2026-11-11, [#1839](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1839)**: exactly three letters before; the owner's direction is that the length is not fixed, so that `.tkrtile` and `.tkrpack` of [ADR 0019](0019-tkr-authoring-formats.md) are valid), unique per contract, held in a registry table in the spec and in `packages/native-data` (a test fails when the two differ). Today the registry holds `.tkranm` for `animation-clip`; a new kind's extension is added with its contract, and none is reserved in advance. The extensions are new and are never the classic legacy ones (`.anm`, `.brd`, `.tem`, `.itm`, `.ene`, `.tst`): a registered `tkr` extension marks a native document, a classic extension marks a legacy file read through the compatibility layer, and a legacy file and a native document with the same stem can sit in one folder. The content is YAML, the in-file stamp stays authoritative and mandatory, and the extension and the stamp's `contract` must agree; a mismatch is an error. A file whose extension is not registered is not a native document, and the checker ignores it. Editors and Git: the in-file modeline `# yaml-language-server: $schema=...` works with no association (the owner tested it), a project's `.gitattributes` maps `*.tkr*` to YAML (`linguist-language=YAML`, `text eol=lf`), and a VS Code extension and new-project template that ship these are future work, not built. Owner ruling of 2026-11-09; the evidence is in [findings/native-file-extensions](../findings/native-file-extensions/README.md).

    **Effect of decision 7:** a plugin block is not a document and has no extension, so data a plugin attaches to a native document needs no registry row. Only a contract that is a document of its own does.
12. **Closed core fields, an open plugin dictionary, and every writer preserves what it does not understand** (the two-rule model, owner ruling of 2026-11-09). The stamp and the contract's own fields are **closed**: an unknown key at the top level is an error, so a typo such as `colorKey` cannot pass for `colourKey`. `pluginData` is the one open dictionary, and inside `pluginData.<id>.data` the namespace is **open**: unknown keys are tolerated, never reported and never dropped. The asymmetry is correct because the line between closed and open follows the line of ownership. A closed schema is sound only where the checker owns the schema and so knows every key. The core owns the contract, and the plugin owns its block. The core cannot tell a typo inside a plugin's block from a key that a newer version of the plugin added, and a writer may be older than the data it reads, so the only safe rule there is to keep what you do not understand. That tolerance is safe only with a duty on writers: **every writer MUST preserve what it does not understand, byte for byte, comments included.** No code path regenerates a document that holds a block from a parsed tree. Every change is a splice into the original text. Bytes inside a block change only when that block's own plugin changes a key it owns. A new block is inserted at its sorted place and existing order never changes. A writer that cannot meet this for an edit refuses with a located error and never drops or reformats anything ([spec](../spec/formats/native-contracts.md#preservation)). This is a decision of its own, apart from decision 7, because it outlives any one shape of plugin data: it holds for every open region a contract will ever have.

### Relation to ADR 0005

[ADR 0005](0005-independent-product-v1-and-native-format.md) decision 3 says a native format would be "a major bump on the existing magic + major/minor header". This ADR refines that for native documents: they carry the stamp above, not the legacy binary header. Legacy files keep their magic and major/minor and are read through the compatibility layer ([ADR 0009](0009-compatibility-layer-not-the-model.md)). ADR 0005's text is unchanged; this ADR is the later and more specific rule for native documents.

## Consequences

* The checker, the rename tool and the first contract are built in epic 27 ([#1802](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1802)). Nothing is published as 1.0 by this ADR.
* The cost of a breaking change is a migration for every published contract, kept for as long as documents at the old version exist. The incentive is to get the tangled contracts (the actor family, scenes) right before they publish, and to let clean ones go first.
* Path identity makes a move or rename an identity change. It needs the rename tool, and by hand the checker names every reference that now points nowhere.
* A project can hold documents at mixed versions; upgrading migrates the ones that are behind.
* A plugin block versions independently of the core contract of the document that holds it, and of every other block. Each carries its own `version`, and its plugin owns the migration ([ADR 0024](0024-plugin-data-contributions.md)). Upgrading a block is explicit, one plugin and one document at a time.
* A document's kind is part of its ID, so changing the kind is a rename and rewrites every reference. The research found no evidence on whether that is a burden in practice.
* The kind is written twice, in the extension and in the stamp, and the two can drift. The stamp wins for loading; the proposed extension-and-contract checker class reports a disagreement.
* Editors do not know a `tkr` extension is YAML until told. The modeline and a `.gitattributes` mapping are the answer, and nothing in this change ships them.
* A misspelt `tkr` extension is not a registered extension, so that document is not read and not reported. Whether the checker should report one is open.
* Every writer of a native document must preserve what it does not understand (decision 12). That can be tested for our writers and cannot be tested for anyone else's. It was not needed while plugin data had a file of its own.
* Core data and plugin data share one file. A plugin tool that writes invalid YAML makes the whole document unreadable (reported as an unreadable stamp, never silently), and one that reformats changes the core's lines. Edits to different parts of one document can conflict in a merge, and a clean merge can leave two blocks with one id ([measured on single synthetic files](../findings/plugin-data-models/README.md#measured-git-merge-behaviour)).
* While a plugin is absent, a typo inside its `data` is invisible, and a block on a contract the plugin does not declare is not found. With the plugin present, a misspelt optional key is an unknown key and passes. That is the price of tolerating unknown keys.
* The rename tool reads only the reference fields that the core contracts name, so a reference **inside** plugin data to a renamed document is opaque to it and is left as written (open question below).
* Plugin data adds no extension and no registry row (decision 11). A plugin id names a plugin and is not a document ID.
* A document's top level is closed to the contract's own fields and five reserved keys, so a plugin has exactly one place to put data, and an error in a core field is located by a short path such as `frames[1].image`. A contract's own field can never be named `contract`, `version`, `tags`, `metadata` or `pluginData`.

## Alternatives considered

* **A single project-wide version number.** Rejected: one contract's break would force every document to move, and the number would say little about any one of them.
* **A manifest of versions beside the documents.** Rejected: it is a second copy of what each document already says, and the two can disagree. What a manifest could give, such as the lowest engine a project needs, is computed from the stamps.
* **A separate authored ID key inside each document.** Rejected: Git merges two branches that add the same ID cleanly (all 18 research runs did), so the duplicate is found only if a checker looks. With the path as the ID, the file system and Git report it.
* **Plugin data as a namespaced block inside the owner's document.** Rejected by the owner on 2026-11-08 and **superseded by the owner on 2026-11-09** (decision 7). The reasons given then were that separate documents (1) let the core and each plugin version independently, (2) keep plugin edits off the core's lines in a merge, and (3) make an absent plugin's data trivially safe to leave alone. Where each stands now, from the [measurements](../findings/plugin-data-models/README.md#measured-git-merge-behaviour): **(1) is achieved,** because each block has a version of its own and its plugin owns the migration. **(2) is not achieved:** on single synthetic files, two edits to adjacent lines of one document conflicted (both appending to one block, both appending a block at the end, an edit to the last core line against the `pluginData:` line), and one merge was clean and left two blocks with one id, which is why the checker reports a `duplicate`. **(3) is achieved only by discipline:** an absent plugin's block is safe while every writer follows decision 12, where a file boundary made it safe whatever the writer did. What the change buys, from the findings: no extra file per plugin per owner (200 actors and 5 plugins that all use data are 1,000 plugin documents under the old rule and none under blocks), no link classes, no registry row per plugin contract, and no second copy of an owner link.
* **Other homes for plugin data:** one project-level plugin-data document, one document per plugin, and a drop-in directory beside each owner (`guard.tkract.d/`). Compared in the [findings](../findings/plugin-data-models/README.md#the-models-compared) and not chosen: the first two put every plugin's edits in one hot file under one stamp for many plugin versions, and the drop-in directory keeps the file count of the old rule.
* **A `core:` wrapper namespace for a contract's own fields**, with the stamp and `pluginData` as its peers at the top level (`core: {canvas: ..., delay: ..., frames: [...]}`). Proposed by the owner on 2026-11-09, who is weighing the flat shape; **considered and not adopted here**, for five reasons. (a) It adds one nesting level to every core field and so to every schema, example, reader path and fixture, for a benefit that the closed or open rule already provides. (b) It collides in meaning with "core" as this repository already uses the word (the `core` package, the engine, "the core contract"), which invites misreading. (c) The formats that already solve this problem keep their own fields unwrapped beside exactly one open dictionary: Cargo's `package.metadata` table, which Cargo ignores and never warns about, Python's `[tool]` table in `pyproject.toml`, and glTF's `extensions` dictionary ([findings](../findings/plugin-data-models/README.md#what-the-evidence-showed)). (d) Error paths stay shorter, `frames[1].image` and not `core.frames[1].image`, which matters for the located reports the checker and the reader promise. (e) A later move of a field from the contract to a plugin is just as mechanical without the wrapper: `delay` becomes `pluginData.<id>.data.delay`, so the symmetry buys nothing concrete. **The one benefit, stated honestly:** with a wrapper, whether a field is core or plugin can be told from its depth alone. Choosing the wrapper later is a pre-release change for the clip, free while it stays at `1.0.0-pre.1`, and a MAJOR change after its 1.0.
* **`+build` metadata for provenance.** Rejected: it ignores precedence, allows only letters, digits and hyphens, and tends to change on every build, which is diff churn. Provenance goes in the optional `metadata` block.
* **A straight 1:1 translation of every legacy file as the native format.** Rejected: it would make the legacy shapes the model, against [ADR 0009](0009-compatibility-layer-not-the-model.md). Translation remains the importer oracle, and the tangled families are redefined.
* **Pre-release as `-pre-####`.** Superseded by the dotted form, which sorts numerically without padding.
* **`name.<kind>.yaml`, for example `walk.clip.yaml`.** Not chosen: the owner ruled for one extension per kind. The evidence for it was real: Bevy ships `scn.ron` and a `*.level.json` convention and looks loaders up by full extension; Jest, TypeScript (`.d.ts`) and Terraform (`.tf.json`) key on a suffix before the language extension; a final `.yaml` keeps generic YAML tooling working. The evidence against it: no first-party engine read uses it as its main scheme, Godot's `.kind.tres` is still an open proposal, multi-dot names have cost real bugs (Tiled #2149) and loader logic (Bevy), SchemaStore warns against generic `fileMatch` patterns, and no source read tested a `*.clip.yaml` glob in yaml-language-server. It also writes the kind twice, as the chosen scheme does ([games.md](../findings/native-file-extensions/games.md#3-option-comparison), [general.md](../findings/native-file-extensions/general.md#5-evidence-table)).
* **Plain `.yaml`, with the kind from the folder and the stamp.** Not chosen: the owner ruled for one extension per kind. The evidence for it: Kubernetes and OpenAPI carry kind or version inside plain YAML, GitHub Actions dispatches by folder, and Godot's `.tres`, Unity's `.asset`, GameMaker's `.yy` and Flax's `.json` keep the kind in the content; it needs no registry. The evidence against it: Godot moved `.shader` to `.gdshader` and its `.kind.tres` proposal lists the cost of a header-only kind, Unity's smart merge skips the generic `.asset` and `.mat`, a kind taken from a folder fails when a file moves, and schema matching needs per-folder globs or a modeline in every document ([games.md](../findings/native-file-extensions/games.md#3-option-comparison), [general.md](../findings/native-file-extensions/general.md#5-evidence-table)).
* **Reusing the legacy extensions (`.anm`, `.brd`, `.tem`, `.itm`, `.ene`) for the YAML documents.** Rejected, and this is the option the evidence speaks against most clearly: every case found of an extension kept across a format change needed a version header, a converter or content sniffing (Godot 3 to 4, GameMaker `.yy`, Unity), the clean changes tended to change the extension (`.shader` to `.gdshader`), Ren'Py shows a loader preferring a stale sibling of the same stem, and an extension keeps its operating-system association and its meaning for extension-keyed tools. A legacy file and a native document would also share a name in one folder, which the owner wants never to happen ([games.md](../findings/native-file-extensions/games.md#4-what-this-suggests-for-us), [general.md](../findings/native-file-extensions/general.md#6-what-this-suggests-for-us-with-honest-uncertainty)).
* **Reserving the other intended extensions in the registry now.** Not done, by the owner's ruling: only `.tkranm` is registered, and each further extension is added with its contract.

The evidence did not rank these options. The games report found no close analogue for a legacy binary format and a native text format sharing folders, and the general report counts custom extensions, new ones included, the weakest option on editor support. [The findings page](../findings/native-file-extensions/README.md) records what the evidence did and did not show, with each report's unverified list.

## Open questions

Deliberately not decided here (see [the spec's open items](../spec/formats/native-contracts.md#not-decided-here)):

* The layout contract, the schema technology and the YAML profile rules ([#1799](../findings/native-data-notations/README.md)).
* The standard `metadata` keys and the `tags` vocabulary.
* **For the owner to decide: references inside plugin data.** A rename rewrites the reference fields the core contracts name and cannot see a reference inside a block's `data`, which it leaves dangling and unreported. Two answers are candidates and **neither is chosen**: the plugin's definition declares which data paths are references and the host-side rename consults it; or the rename refuses when any value inside a block equals the old ID, which is the only one that also covers an absent plugin and can refuse a value that is not a reference.
* **For the owner to confirm:** that the envelope of a block is closed to `version` and `data` (the ruling tolerates unknown keys inside `data`; a misspelt `dat:` is reported as a missing `data`); the retirement of the three link classes; and the test for block against document in [the spec](../spec/formats/native-contracts.md#block-or-document), whose size bound has no measured value yet.
* The allocation of qualified plugin ids: PKG-2 allows them and reserves nothing by force; whether it should be enforced is open ([PKG-2](../spec/engine/rpgcode-modules-and-objects.md#pkg-2)). The details of the plugin-side contract, and its own open questions, are in [ADR 0024](0024-plugin-data-contributions.md#open-questions).
* The registry rows of the other kinds (actor, scene, item, enemy, tileset and so on): each is added with its contract.
* Whether the checker should report a file whose extension starts with `tkr` but is not registered; it is ignored now.
* A VS Code extension and a new-project template that ship the editor association, the modeline and the `.gitattributes` mapping: future work.
* **For the owner to confirm:** the extension-and-contract checker class (extension and contract disagree), and whether the duplicate-ID class stays separate from two paths folding to one ID.
* ID folding beyond ASCII, which other spellings of one path are one ID (only empty and `.` parts are dropped now), and what a loader does with a newer MINOR or PATCH of a core contract that it does not know. For a plugin block this is decided in decision 7: it is read for the keys its plugin knows.
* Composition against inheritance for the actor family: the owner prefers composition where possible; the contract is settled in 27.7.
* Whether a nested object may carry a door of its own. Not provided in this version; for a scene placement it is the decision of story 27.8 ([#1809](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1809)).
* Whether the plugin-present check shows an unknown key inside `data` as a hint (never an error, never dropped). Off in the proposal; the owner has not said.
* **For the owner to choose:** the flat shape of decision 5 against the `core:` wrapper he proposed (Alternatives considered); and whether a plugin id must avoid the core fields of every contract (a list that grows with each contract) or, as written, only the reserved keys of the contract of the document that holds the block.

## Notes

* **Direction (tentative, owner-stated, not a decision), 2026-11-09:** Jensen: "eventually there may not be any 'core' items in a sense. every field will likely have a plugin / extension they are driven by." Long term, game-semantic fields may move from core contracts into plugin namespaces, and the core shrinks to what cannot be plugin-owned. Nothing moves today and no existing contract changes because of it; none of the decisions above depends on it, and none is weakened by it. A field's move stays mechanical with the flat shape (`delay` becomes `pluginData.<id>.data.delay`). The criterion that was proposed for what must stay in the core, the risks, and what would have to be true before any field moves are in [the shrinking core](../findings/plugin-data-models/README.md#the-shrinking-core).
* **Proposal considered (owner-stated), 2026-11-09:** Jensen: "there will be a set of core shared fields that identify the document. We could even setup a special 'namespace' for core that is toplevel. That way we can make those 'core' properties beyond the identity." Read as a top-level `core:` mapping beside the stamp and `pluginData`. This ADR recommends the flat shape instead and records the wrapper under Alternatives considered; the owner is weighing the two and has not chosen. Where the flat shape differs from the wrapper reading, nothing else in the rulings above changes.
* **Naming of the open dictionary, 2026-11-09:** Jensen found `plugins` not descriptive and floated `metadata`, `extensionData` and `pluginData`. This ADR uses **`pluginData`**. It says what the key holds, it matches the plugin vocabulary of this repository ([ADR 0004](0004-script-ast-step-ir-and-plugins.md), [PKG-2](../spec/engine/rpgcode-modules-and-objects.md#pkg-2) and `PluginDefinition`), and camelCase is already the spelling of the contract's keys (`colourKey`). The entries inside it keep exactly `version` and `data`: the outer key names the category, and the inner keys name the version and the payload. Rejected: **`plugins`**, because it is imprecise (the key holds data and not plugins) and it collides with the retired link-list field of the same name (the `--plugins-field` option and its fixtures), so old fixtures and help text would read ambiguously. **`metadata`**, because it is unavailable: it is already a reserved stamp key that means provenance the engine never reads, and reusing it would merge two different meanings. **`extensionData`** and **`extensions`** (glTF's word), because this ADR uses "extension" for a *file* extension (`.tkranm`) throughout, and reusing the word for plugin data would make it ambiguous in the documents that define the extension registry.
