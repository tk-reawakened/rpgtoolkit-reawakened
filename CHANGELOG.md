# Changelog

## Unreleased
- Story 12.2 adds a project-retained tileset browser and explicit active-board brush painting (#1713). The browser keeps source, scroll position and brush selection synchronized across mounted views, opens from the board with L, and routes selection and context actions without editing source files; unavailable source editing and bitmap placement are explained. Tileset bitmap previews resolve single-tile `.gph` cells, accept optional `Tiles\\` reference prefixes while preserving nested path identity (`Tiles/foo.gph` remains distinct from `Tiles/Tiles/foo.gph`), and resolve `.tan` cells through nested first-nonempty frames; they use the canonical doubled 32px texture for 16px detail tiles, and animation speed is shown in the documented milliseconds per frame. Atlas textures are decoded once per source per load, source identity uses core ASCII path folding, and VS Code webview updates send field-level patches that preserve concurrent changes and unknown session fields. The bounded browser list restores after asynchronous loads, and keyboard-opened menus receive focus and return it on Escape. Browser and actual packaged VS Code web host proofs verify existing document lifecycle scenarios alongside board switching, explicit painting, save/reopen, and retained brush behavior.

- The editor now has one document lifecycle, proved by one conformance suite on both hosts (story 11.3, [#1701](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/1701); [ADR 0022](docs/adr/0022-shared-editor-authoring-contracts.md) D3, D14). `editor-model` compares the file with what it last read or wrote before every save, so another program's change found by that comparison is never written over: the save fails, both versions are kept, and the view offers "Save my version" or "Use the version on disk". The comparison and the write are separate host calls, so a change that lands between them is still replaced unseen ([#2207](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/2207)), and Save As has the same gap at its destination ([#2238](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/2238)); [proposed ADR 0030](docs/adr/0030-save-check-and-write-are-two-steps.md) asks the owner how to resolve it. A clean document follows the file where the host watches, and says so when it cannot. Revert returns to the saved revision or reloads a changed file, and refuses when an edit was accepted after the choice was made ([#2189](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/2189)); Save As writes a new identity without re-keying the source. `createDocumentWorkspace` gives the browser and desktop hosts one model per document identity (two names differing only in case are refused and both named), undo and redo by `editId`, save all with a result per document, and close and revert that ask first; the browser page gains Undo, Redo, Save as, Save all, Revert and Close, and asks its browser before closing the page with unsaved work. The VS Code provider gains Save As, revert, change handling and a `dialogs` surface, and declares `fileWatch` on the desktop build only. `tools/editor-vscode-test/test/host-conformance.test.ts` runs the same thirteen cases against the browser host, VS Code desktop and VS Code for the Web, and `tools/browser/tests/editor-lifecycle.spec.ts` drives the page's own controls in Chromium. The vscode.dev proof now also shows a hidden webview losing nothing, a cancelled close keeping its work, and that VS Code's `files.autoSave` reaches `saveCustomDocument` — the measurement [ADR 0022](docs/adr/0022-shared-editor-authoring-contracts.md) D11.6 owed. The title field no longer keeps a discarded draft after the document's title changes underneath it ([#2188](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/2188)).

- The engine gains a read-only debug view and an expression reader (entry 10.10, [#950](https://github.com/tk-reawakened/rpgtoolkit-reawakened/issues/950); [TOOL-8](docs/spec/engine/rpgcode-tooling.md#tool-8), rules P1 and P2 approved by the owner on 2026-11-11). `Engine.debugView()` returns plain data — the tick, each thread with its kind, status, wait and frames, **every frame's own locals** read through its slot's reference, the innermost frame's locals at the top level and the global table — copied out, so mutating it cannot reach the VM and the state hash does not move. `Engine.evaluate(expression, threadId, frameDepth?)` parses exactly one expression, refuses a statement, a write, a lambda, a dictionary and any call outside a closed list of 25 pure, non-waiting built-ins, then runs it on a copied thread and global table under a command table that answers only those names; the cap is 1000 instructions, reported as `evaluate.budget`, and every other failure keeps the engine's own code. The new `dap` package is a transport-free Debug Adapter Protocol session over `runner-harness`'s scene fixture: breakpoints, threads, stack traces, scopes, variables, watches, continue and adapter-computed step over/in/out, with a stdio binary outside the public export.

The host can inspect recovery status and explicitly resume; board threads, entry instructions and item multitask threads wait until then. Changed or missing required board/entry assets refuse the launch without exposing partial recovered state. New candidates include required-asset fingerprints; older candidates without them are refused because asset compatibility cannot be established.


- Save restoration preserves object values and suspended method continuations after explicit release, including when a freed handle is reused by another class. Values retain a positive safe-integer handle and string class tag; comparisons continue to use handles. Object-member references and callable receivers still require live objects, and destructor continuations still require a live release handle.

- Load reports a saved program-reference compiler mismatch before validating a malformed schema or audio projection, and refuses malformed or dimension-mismatched surface base64 before committing restored state.

- Loading a battle save now warns when a fighter is on the wrong team. The entry stays in its original position and is skipped rather than silently fighting for the wrong side.

- The battle event contract is now regression-tested at its exact shape. The stock outcome test asserts that the actor-local `defeated` and its game-level `stock_battle.defeated` re-emission carry exactly the keys `cause` and `source`, with the attacking actor's id as the source; the authored no-stock custom fight program emits the same ruled detail and proves nothing re-emits it on the game; and the damage tests assert `beforeDamage`'s exact `source`, `target` and `damage` detail, that a listener's mutated amount is clamped at the owner's HP/SMP boundary, and that an item-origin action dispatches exactly one cancelable `beforeDamage`.
- A battle background whose picture is a tile bitmap (`.tbm`) now shows. The stock battle screen no longer blanks a `.tbm` background, and the engine turns the file's cells — each cell's tile with its tint — into one picture for `bitmap`, the `setimage*` family and a battle background, using the same tile readers boards already use. A `.tbm` whose tiles have not arrived yet keeps its draw queued until they do, and a broken cell is reported as an invalid asset instead of quietly leaving the flat colour. PNG, JPEG, BMP and GIF backgrounds keep their behaviour, and no golden frame changed.
- Battle participant statuses now end with the battle. Once the final outcome is selected, the core outcome adapter removes every status counter from both parties — enemies included — after that outcome's own handling, so the run, win and game-over programs still see the statuses recorded during the fight, and before it announces `battleEnded`. This covers the outcome codes the package or a custom program handles itself (1 and 3) as well as the automatic ones. Actors that took no part in the battle keep their statuses, a successful escape still lets later charged fighters of that pass tick their statuses first, and a party left at 0 HP by those ticks still loses instead of escaping.
- A battle's identifier is never handed out twice in one run. The number came from the live `battle` section, which loss cleanup clears before a game-over program runs, so a game-over program that started another battle received the first battle's number; the counter now lives in the saved `engine` section as `nextBattleId` (plain data, optional, no schema-version change). A save/restore continues a run's numbering, `reset()` starts a new run at 1, and a save written before the counter existed takes one past the active battle's `id`. A mid-battle save now carries the field, so `fixtures/save/battle-v2-mid.json` records it.
- The compiled-program cache remembers the program it answered for each reference object, so a repeated request no longer rebuilds that reference's cache key. An inline reference carries the whole program text and the VM asks for its frame's program on every instruction, so the battle rigs rebuilt an about 95 KB key per step. References are immutable, so a changed program still arrives as a new reference and compiles afresh, and each cache keeps its own memos, so separate caches and test rigs never share a compiled program. Measured on Node 24.21.0: the core-battle shard 108.8 s to 51.3 s, and 300 single-tick advances of a real battle 19.4 to 12.7 ms per tick.
- Battle UI refresh tests reuse one real battle per screen mode, restoring each changed value and checking its pixels before the next case. The six-tick refresh checks and duplicate-name pixel comparisons remain intact.
- Documented and tested how pre-vector boards handle oversized final tile runs: excess repetitions are discarded, following fields remain readable, and Reawakened warns about the overrun. The original applications did not issue that warning.
- Jensen approved the complete battle screen on 2026-10-28, including by-name revive targeting. It keeps the selected command visible while choosing a move, item, or target and highlights list entries across their column.
- Battle selection keeps the command label and active member name at exactly the same yellow; selected unavailable moves remain visibly dimmed with improved contrast, and the description header no longer exposes the background beneath its label.
- Using a stack in the battle Items list now spends that stack. Before, the "Special Potion" row spent the canonical "Potion" stack, and two non-canonical stacks of one item file healed the target but spent neither. `battleconsume` takes an optional stack `handle` (the `inventory.consume` request carries `handle`, `null` when none is named); the owner consumes exactly the named stack, and the battle screen checks the chosen stack still has a unit before it changes any stat.
- Loading a mid-battle save into a brand-new engine no longer fails to draw. The saved stance animations come back already loaded, so the engine now asks the host for their frame pictures on load, keeps each animation's saved frame and origin tick, and leaves an animation out of the drawn frame until its pictures have arrived instead of reporting `render.failed`.
- The battle UI cadence test now starts a real Fight and checks every fighter's own animation, frame and rendered pixel on every tick (idle and during the action) at 1-, 2- and 3-tick delays; one-tick-early and one-tick-late frames are rejected.
- The battle screen now redraws displayed fighter names, current and maximum HP and SMP, charge and fallen state within six ticks without another key press, idle or in any menu, while keeping one battle pass per tick. Golden draw-list hashes include the snapshot tick, so the merged redraw paths change them even when pixels match. Against the pre-merge golden, only `defeated.png` changes (charge-bar pixels at the recorded battle-loop step); the other four PNGs are unchanged.
- Battle menu redraws hide fighter pictures before publishing a list and restore them only after publishing its replacement, without restarting their animation timelines. Queued Escape presses keep the correct visibility through the intermediate list. Target-picker labels and the target message also refresh when a rename arrives with a cursor move, including changed duplicate-name suffixes.
- Not changed: custom logical resolutions below 640×480 still use the 640×480 layout numbers; this needs an owner decision (see the pull request).

- Script drawing (`setpixel`, `drawline`, `drawrect`, `fillrect`, `drawcircle`, `fillcircle`, `clear`, canvas blits) edits live pixel buffers kept outside saved state, and each command re-encodes only the span it can touch. Inside a thread phase the edits are held and written into the plain-JSON base64 snapshots when the phase ends, including after a thrown command or a debugger pause. Opaque, unscaled copies use clipped scanlines; translucent pixels keep their existing blend behavior, and a surface blitted onto itself reads its pre-blit pixels.
- Bounds are never narrower than what the draw routine can write: an infinite `fillrect` edge clips to the surface like the pixels it draws, and an unknown extent covers the whole surface. An unbounded edit is never narrowed by a later bounded one.
- Batching is off when effect appliers or script observers are installed, and stays on with a main file, package catalogue or phase registrations. Package, catalogue and main-file plugin code (commands, listeners, host-object member hooks and host-type emitter keys) is handed the state tree, so pending drawing is written out before any of it runs, and again when a layer it called through `next` returns; built-in commands never trigger that. Such code therefore sees exactly the snapshots eager drawing would give it, on the call and on any later callback that reads a retained view.
- Each surface keeps one indexed working buffer, so a batch that is closed no longer drops the buffer a newer batch took for the same surface state; two sections that reference one surface entry keep their own pixels until their own batch ends.
- State hashes remain the same FNV-1a hashes. Cached bitmap text avoids reserializing unchanged surface payloads, while per-block transitions can reuse exact hash work even when earlier state changes. Direct edits to bitmap text and metadata still invalidate the relevant cache.
- Canvas text uses the same batch-aware pixel writes as other surface drawing and reuses its raster-asset map; the surface hash cache also handles the render-now on/off flag without changing canonical hashes.
- Each block transition learns only the incoming low-byte value encountered during a hash. A different value requires another scan of that block, so one traversal does not prepare all possible values. The cache holds at most 2,048 blocks per game state: old blocks no longer in the current state are evicted first, and additional blocks use the ordinary hash path if all retained blocks are active. Cold, changing, or highly varied surfaces can still require substantial sequential hashing.
- Measured on Node 24.21.0 against `origin/main` (identical state hashes): 60 direct 640×480 drawing operations plus a complete state hash took about 2.5 s before and about 48–51 ms after in steady rounds (61–73 ms for the first, cold round); a frame of 60 `fillrect`s over four 640×480 canvases plus a hash took about 4.8 s before and about 88 ms (median) after; a tick that edits four high-entropy 640×480 surfaces while the state prefix changes took about 630 ms before and about 61 ms (median) after. The 50 ms budget for 60 direct 640×480 drawing operations plus a complete state hash is **not reliably met**: the cold first round exceeds it and steady rounds sit at its edge.
- Hashing shared inline program owners now reuses canonical fragments and lazily learned exact FNV transitions while checking each owner's current fields for direct edits. Non-ASCII, nested or unusually large owners use the ordinary hash path; newly encountered incoming byte lanes still need a full scan. The per-state cache retains at most 32 program fragments of at most 256 Ki characters each and discards inactive entries when full, so changing or varied workloads may receive less benefit.
