# Changelog

## Unreleased
- The fetched demo's `out.brd` return door is a **key-press** region, not a walk-on trigger. A packaged-game regression starts the real game, walks to the outside board, approaches the wall off-centre and presses Enter to return; no tile snapping is assumed. At `(144,176)` the player's `(-15,-15)`–`(15,0)` collision base overlaps the authored `(83,148)`–`(140,170)` region despite stopping at the house wall (#1274; `docs/spec/engine/movement-and-collision.md#e-41`).
- **Pixel-movement steps are 4 px (R-62).** A direction press moves 32 px in tile movement and 4 px in either pixel mode, so the mode no longer changes how the player walks and every pixel-mode step is exactly one R-50 advance. Previously the landed core stepped 8 px in mode 1 and 1 px in mode 2, mirroring the original's frame-rate-derived step; `pixelStep` is gone from the movement and input APIs. The movement oracle and its fixtures follow the same rule, and the party-step tests now accumulate eight 4 px moves instead of four 8 px ones (`docs/spec/engine/movement-and-collision.md#r-62`).
- **Pre-vector boards merge into greedy rectangles, as both original programs do.** The conversion rule was documented — and implemented — as one polygon per maximal horizontal run of same-type cells. The original routine (one implementation, reached by the engine directly and by the editor through `BRDVectorize`) grows each block down its column and then right over whole columns, so a 2×2 block of solid cells becomes one polygon rather than two. Covered area is unchanged, but the polygon count and the internal seams differ: over the 143 pre-vector boards of `fixtures/legacy` the converter now emits 2,667 polygons instead of 4,528, and 132 of the 143 boards change (`docs/spec/formats/legacy/older-binary-versions.md#board-minor-2-and-3-pre-vector`).
- **A wall slide turns the step and ends there (R-54 item 3).** A glancing step that slides now adopts the slid point as its target and completes on arriving, instead of continuing towards the original target; this is the legacy behaviour of retargeting the step, and it stops the engine from sliding repeatedly inside one step. The movement oracle was corrected to match, and the slide case now starts clear of the wall so the slide and the following head-on block are both exercised.
- A sprite animation frame whose picture is an ordinary image now samples the image's **own** pixels instead of the animation header's `width × height`, so a 64×32 frame canvas naming a 32×32 PNG draws the whole picture rather than reading past the decoded texture. The out-of-bounds blit failed the reference rasteriser, which aborts the rest of the frame, so later sprites vanished with it; header dimensions now size only the frame canvas and the anchor (`docs/spec/formats/animation.md#layout`, #1270). The `.tbm` picture branch shares the same rule, so the tile-bitmap fix above and this one are one code path.
- A tile-bitmap sprite frame now draws as the **one composed picture** the format defines, instead of being lowered to cell blits, so its later cells' overlap, its transparent colour and its `width · 32 × height · 32` bounds behave exactly as they do for a `bitmap`, a board image or a battle background. Composition is what makes a later cell that the frame's transparent colour keys out erase the earlier cell painted under it, and what clips a 64×32 isometric tile to a 1×1 picture's 32 pixels; independent cell blits can reproduce neither. A runner cannot compose a `.tbm` itself, so the core exposes the decoded picture through the new `engine.picturePixels(key)` accessor and the live browser/desktop texture provider falls back to it (`docs/spec/engine/runners.md#picture-pixels`); `docs/spec/formats/tiles.md#tile-bitmap-tbm` states that the composed picture is the unit, that a picture with no drawn tiles is a valid transparent picture, and the `blit` pipeline is written down as key-on-the-sampled-pixels then world tint then blend (`#blit-pipeline`). `SpriteFrame.cells`, its decoder and the extra per-cell draw stage are removed (`#1269`).
- Actors draw their walk/idle animation frames instead of the fallback marker rectangle. The engine now runs actor animation playback inside its existing animation phase (E-21), requests each character/item animation file and the pictures its frames name as ordinary assets before a tick uses them (E-54's shared, cached frames), and hands the current frame's tileset cell or picture to the compositor through `SpriteDraw.frame`, so the demo's player is drawn from `Misc/start/start_s.anm` frames `char.tst1`/`char.tst2` standing and walking on both boards (#1252). Two supporting fixes: an animation frame's image reference now reaches the resolver whole (`char.tst1`, not the bare tileset `char.tst`, which classified as a picture and dropped every tile frame — script animations with tile frames had the same gap), and a sprite frame that names a tile is blitted as that tile instead of the whole tileset strip (`packages/core/src/render/compose.ts`). A real Electron run of the demo package walks through the door and shows the character art at `out.brd` (previously the RGB 64,96,224 square). Regression: `packages/core/test/sprite-artwork.test.ts` (decoder tile references, the engine's tile blit and presented pixels, and the 0.15 s frame advance); reverting the phase, the draw-frame wiring or the tile-frame preference fails it. No golden or closing baseline changes: no committed scene draws an actor from an animation file. Board-item sprites still have no engine owner (#1253) and a GIF walk animation cannot draw yet (#1254). Review of #1252 added three frame-picture fixes: a frame that is a tile bitmap is requested and composed as an image instead of going through the tileset decoder that ignores `.tbm` (#1257); a tile frame is drawn at its tileset cell's own size, with the animation header sizing only the canvas and anchor, so a 64×32 frame naming a 32×32 cell no longer samples the adjacent cell or runs past the texture (#1258); and cached animation metadata re-requests a frame picture whose reply a save load or reset dropped by clearing the pending queue (#1259, latent — no committed regression, because no public flow drops such a reply deterministically). A second review round fixed two frame-kind dispatch bugs: a `.gph` frame is decoded by the tile owner instead of the image decoder, which refused it and stopped the game (#1261), and the live texture provider now expands `.gph` too; and a `.tbm` frame is drawn as its composed picture, which the core supplies to the runner (#1262, #1269). Regressions: the `.gph`/`.tbm` cases in `sprite-artwork.test.ts` and the live-seam cases in `packages/runner-harness/test/textures.test.ts`; the real Electron player draws both frames. A third review round pinned the bitmap picture's own semantics: a 16×16 `.gph` cell keeps its size (a quarter of a 32×32 cell) and a 64×32 `.iso` cell keeps its width (#1265); the frame's transparent colour keys the picture (#1266); and a bitmap with no drawn tiles is a valid transparent picture, not the fallback marker (#1267). The live WebGL2 renderer compared colour keys as exact floats, so any key other than 0/255 never matched and a keyed picture or cell showed its background (#1268); it now compares within half an 8-bit step, and a committed `colour-key-mid-tone` raster vector puts that decision on the browser conformance lane.
- Cursor-map selections now show a pointing hand in the live desktop, web and mobile players. The live texture lookup includes bundled images as well as game assets, and the bundled cursor-map graphic uses the existing hand artwork at 32×32 (#1260; `docs/spec/engine/rpgcode-functions.md#reawakened-default-cursors`).
- `winGraphic` now paints the message window's background image instead of only recording its name. The reference is resolved through the asset index like `setImage`'s pictures (`"mwin.jpg"` becomes `Bitmap/mwin.jpg`), fetched once, and drawn 1:1 inside the fixed 600 x 100 window at the window's translucency, under the text; before this nothing consumed the stored name, so the demo's intro message stayed black. A reference the index cannot answer reports one `asset.missing` diagnostic and keeps the colour background rather than stopping the engine, and a `winColor` after it changes only the colour. Measured on the built `fixtures/packages/demo.tpk` at 640 x 480: tick 30 (title) and tick 61 (board) draw no window, ticks 35-55 draw `bitmap/mwin.jpg` at `dst {x: 20, y: 0, w: 600, h: 100}` with alpha 128, and the frame pixels there are the picture's own blue tones blended 50% over black (#1243; `docs/spec/engine/rpgcode-functions.md#reawakened-message-window-image`). `pnpm closing`, `pnpm golden` and their baselines are unchanged.
- The desktop player now quits when its game window closes, on every platform including macOS. The Electron shell used to keep the application alive after its last window closed, so `pnpm desktop:run` stayed attached to a game with no window and the next run started a second copy; the player now quits through `app.quit()` on `window-all-closed` (the rule lives in `packages/runner-desktop/src/lifecycle.ts`) and the launcher exits with it (#1245; `docs/spec/engine/runners.md#desktop-shell`, `docs/spec/engine/main-loop-and-startup.md#e-06`). The measurement-only `--quit-after` flag is removed, because closing the window is now the only quit-on-close behaviour.
- `send` now names a position in the destination board's own coordinate mode: a board pixel on a board that sets `coordType`'s "Use pixel coordinates" flag (4), a one-based tile coordinate otherwise. Every target used to be read as tiles, so the shipped 3.1 demo's door — `send("out.brd", 112, 192, 1)` between its two flag-4 boards — converted 112,192 to the pixel 3568,6143 and the player left the 640x480 board (the desktop player's "player vanishes" bug, #1246). `docs/spec/engine/movement-and-collision.md#reawakened-send-board` records the unit and its evidence (the demo's return `send("start.brd", 306, 306, 1)` lands inside the other board's door region), and `docs/spec/formats/board.md#coordinates` now states which script position follows the flag; the placement effects carry `unit: "pixel"` on such a board, so the camera, deactivation and every consumer agree. No golden or save hash changes: no committed scene sends to a flag-4 board, and `coordType` 0 boards keep the tile reading (the `Caoquest` warp programs, the movement oracle's scenes).
- RPGCode `text` cell coordinates now keep a fractional value and truncate only the scaled pixel origin, so `text(17, 10.5, …)` at font size 18 starts at pixel row 171 instead of 162 (`docs/spec/engine/rpgcode-functions.md#reawakened-text-cell-size`; issue #1244). Both 3.1 sample games author their title menu at rows 10.5/12/13.5 for equal 1.5-cell spacing; truncating the cell first collapsed the rows to 10/12/13 and produced the reported uneven "New Game / Load Game / Quit" gaps of 36 and 18 pixels. `emitCellText` and the canvas `text` path follow the same rule; `pixeltext` keeps whole pixel coordinates. Draw lists and closing baselines that contain fractional cell text change deliberately (G5).

A successful step now reports itself with a `step-complete` movement event, which the wall-slide completion path previously bypassed; that also routes the slide path through the same completion path as an ordinary move, so a slide that completes while moves are still queued no longer reports `movement-complete` (the event vocabulary itself is unruled and is #1235). The stock battle screen no longer blanks a `.tbm` background, and the engine turns the file's cells — each cell's tile with its tint — into one picture for `bitmap`, the `setimage*` family and a battle background, using the same tile readers boards already use. A `.tbm` whose tiles have not arrived yet keeps its draw queued until they do, and a broken cell is reported as an invalid asset instead of quietly leaving the flat colour. PNG, JPEG, BMP and GIF backgrounds keep their behaviour, and no golden frame changed.
- Battle participant statuses now end with the battle. Once the final outcome is selected, the core outcome adapter removes every status counter from both parties — enemies included — after that outcome's own handling, so the run, win and game-over programs still see the statuses recorded during the fight, and before it announces `battleEnded`. This covers the outcome codes the package or a custom program handles itself (1 and 3) as well as the automatic ones. Actors that took no part in the battle keep their statuses, a successful escape still lets later charged fighters of that pass tick their statuses first, and a party left at 0 HP by those ticks still loses instead of escaping.
- A battle's identifier is never handed out twice in one run. The number came from the live `battle` section, which loss cleanup clears before a game-over program runs, so a game-over program that started another battle received the first battle's number; the counter now lives in the saved `engine` section as `nextBattleId` (plain data, optional, no schema-version change). A save/restore continues a run's numbering, `reset()` starts a new run at 1, and a save written before the counter existed takes one past the active battle's `id`. A mid-battle save now carries the field, so `fixtures/save/battle-v2-mid.json` records it.
- The compiled-program cache remembers the program it answered for each reference object, so a repeated request no longer rebuilds that reference's cache key. An inline reference carries the whole program text and the VM asks for its frame's program on every instruction, so the battle rigs rebuilt an about 95 KB key per step. References are immutable, so a changed program still arrives as a new reference and compiles afresh, and each cache keeps its own memos, so separate caches and test rigs never share a compiled program. Measured on Node 24.21.0: the core-battle shard 108.8 s to 51.3 s, and 300 single-tick advances of a real battle 19.4 to 12.7 ms per tick.
- Battle UI refresh tests reuse one real battle per screen mode, restoring each changed value and checking its pixels before the next case. The six-tick refresh checks and duplicate-name pixel comparisons remain intact.
- Documented and tested how pre-vector boards handle oversized final tile runs: excess repetitions are discarded, following fields remain readable, and Reawakened warns about the overrun. The original applications did not issue that warning.
- Jensen approved the complete battle screen on 2026-10-28, including by-name revive targeting. It keeps the selected command visible while choosing a move, item, or target and highlights list entries across their column.
- Battle selection keeps the command label and active member name at exactly the same yellow; selected unavailable moves remain visibly dimmed with improved contrast, and the description header no longer exposes the background beneath its label.
- Using a stack in the battle Items list now spends that stack. Before, the "Special Potion" row spent the canonical "Potion" stack, and two non-canonical stacks of one item file healed the target but spent neither. `battleconsume` takes an optional stack `handle` (the `inventory.consume` request carries `handle`, `null` when none is named); the owner consumes exactly the named stack, and the battle screen checks the chosen stack still has a unit before it changes any stat.
- Loading a mid-battle save into a brand-new engine no longer fails to draw. The saved stance animations come back already loaded, so the engine now asks the host for their frame pictures on load, keeps each animation's saved frame and origin tick, and leaves an animation out of the drawn frame until its pictures have arrived instead of reporting `render.failed`.
- The battle UI cadence test now starts a real Fight and checks every fighter's own animation, frame and rendered pixel on every tick (idle and during the action) at 1-, 2- and 3-tick delays; one-tick-early and one-tick-late frames are rejected.
- The battle screen now redraws displayed fighter names, current and maximum HP and SMP, charge and fallen state within six ticks without another key press, idle or in any menu, while keeping one battle pass per tick. Golden draw-list hashes include the snapshot tick, so the merged redraw paths change them even when pixels match. Against the pre-merge golden, only `defeated.png` changes (charge-bar pixels at the recorded battle-loop step); the other four PNGs are unchanged.
- Battle menu redraws hide fighter pictures before publishing a list and restore them only after publishing its replacement, without restarting their animation timelines. Queued Escape presses keep the correct visibility through the intermediate list. Target-picker labels and the target message also refresh when a rename arrives with a cursor move, including changed duplicate-name suffixes.
- Not changed: custom logical resolutions below 640×480 still use the 640×480 layout numbers; this needs an owner decision (see the pull request).

- Script drawing (`setpixel`, `drawline`, `drawrect`, `fillrect`, `drawcircle`, `fillcircle`, `clear`, canvas blits) edits live pixel buffers kept outside saved state, and each command re-encodes only the span it can touch. Inside a thread phase the edits are held and written into the plain-JSON base64 snapshots when the phase ends, including after a thrown command or a debugger pause. Opaque, unscaled copies use clipped scanlines; translucent pixels keep their existing blend behavior, and a surface blitted onto itself reads its pre-blit pixels.
- Bounds are never narrower than what the draw routine can write: an infinite `fillrect` edge clips to the surface like the pixels it draws, and an unknown extent covers the whole surface. An unbounded edit is never narrowed by a later bounded one.
- Batching is off when effect appliers or script observers are installed, and stays on with a main file, package catalogue or phase registrations. Package, catalogue and main-file plugin code (commands, listeners, host-object member hooks and host-type emitter keys) is handed the state tree, so pending drawing is written out before any of it runs, and again when a layer it called through `next` returns; built-in commands never trigger that. Such code therefore sees exactly the snapshots eager drawing would give it, on the call and on any later callback that reads a retained view.
- Each surface keeps one indexed working buffer, so a batch that is closed no longer drops the buffer a newer batch took for the same surface state; two sections that reference one surface entry keep their own pixels until their own batch ends.
- State hashes remain the same FNV-1a hashes. Cached bitmap text avoids reserializing unchanged surface payloads, while per-block transitions can reuse exact hash work even when earlier state changes. Direct edits to bitmap text and metadata still invalidate the relevant cache.
- Canvas text uses the same batch-aware pixel writes as other surface drawing and reuses its raster-asset map; the surface hash cache also handles the render-now on/off flag without changing canonical hashes.
- Each block transition learns only the incoming low-byte value encountered during a hash. A different value requires another scan of that block, so one traversal does not prepare all possible values. The cache holds at most 2,048 blocks per game state: old blocks no longer in the current state are evicted first, and additional blocks use the ordinary hash path if all retained blocks are active. Cold, changing, or highly varied surfaces can still require substantial sequential hashing.
- Measured on Node 24.21.0 against `origin/main` (identical state hashes): 60 direct 640×480 drawing operations plus a complete state hash took about 2.5 s before and about 48–51 ms after in steady rounds (61–73 ms for the first, cold round); a frame of 60 `fillrect`s over four 640×480 canvases plus a hash took about 4.8 s before and about 88 ms (median) after; a tick that edits four high-entropy 640×480 surfaces while the state prefix changes took about 630 ms before and about 61 ms (median) after. The 50 ms budget for 60 direct 640×480 drawing operations plus a complete state hash is **not reliably met**: the cold first round exceeds it and steady rounds sit at its edge.
- Hashing shared inline program owners now reuses canonical fragments and lazily learned exact FNV transitions while checking each owner's current fields for direct edits. Non-ASCII, nested or unusually large owners use the ordinary hash path; newly encountered incoming byte lanes still need a full scan. The per-state cache retains at most 32 program fragments of at most 256 Ki characters each and discards inactive entries when full, so changing or varied workloads may receive less benefit.
