# Changelog

## Unreleased

- Jensen approved the complete battle screen on 2026-10-28, including by-name revive targeting. It keeps the selected command visible while choosing a move, item, or target and highlights list entries across their column.
- Battle selection keeps the command label and active member name at exactly the same yellow; selected unavailable moves remain visibly dimmed with improved contrast, and the description header no longer exposes the background beneath its label.
- The battle UI cadence test now starts a real Fight and checks every fighter's own animation, frame and rendered pixel on every tick (idle and during the action) at 1-, 2- and 3-tick delays; one-tick-early and one-tick-late frames are rejected.
- The battle screen now redraws displayed fighter names, current and maximum HP and SMP, charge and fallen state within six ticks without another key press, idle or in any menu, while keeping one battle pass per tick. The draw-list hashes in `golden/battle-ui/frames.json` changed because the screen now paints charge-bar growth with fewer drawing operations; the five golden PNGs and their pixel hashes are unchanged.
- Not changed: custom logical resolutions below 640×480 still use the 640×480 layout numbers; this needs an owner decision (see the pull request).

- Script drawing (`setpixel`, `drawline`, `drawrect`, `fillrect`, `drawcircle`, `fillcircle`, `clear`, canvas blits) edits live pixel buffers kept outside saved state, and each command re-encodes only the span it can touch. Inside a thread phase the edits are held and written into the plain-JSON base64 snapshots when the phase ends, including after a thrown command or a debugger pause. Opaque, unscaled copies use clipped scanlines; translucent pixels keep their existing blend behavior, and a surface blitted onto itself reads its pre-blit pixels.
- Bounds are never narrower than what the draw routine can write: an infinite `fillrect` edge clips to the surface like the pixels it draws, and an unknown extent covers the whole surface. An unbounded edit is never narrowed by a later bounded one.
- Batching is off when effect appliers or script observers are installed, and stays on with a main file, package catalogue or phase registrations. Package, catalogue and main-file plugin code (commands, listeners, host-object member hooks and host-type emitter keys) is handed the state tree, so pending drawing is written out before any of it runs, and again when a layer it called through `next` returns; built-in commands never trigger that. Such code therefore sees exactly the snapshots eager drawing would give it, on the call and on any later callback that reads a retained view.
- Each surface keeps one indexed working buffer, so a batch that is closed no longer drops the buffer a newer batch took for the same surface state; two sections that reference one surface entry keep their own pixels until their own batch ends.
- State hashes remain the same FNV-1a hashes. Cached bitmap text avoids reserializing unchanged surface payloads, while per-block transitions can reuse exact hash work even when earlier state changes. Direct edits to bitmap text and metadata still invalidate the relevant cache.
- Canvas text uses the same batch-aware pixel writes as other surface drawing and reuses its raster-asset map; the surface hash cache also handles the render-now on/off flag without changing canonical hashes.
- Each block transition learns only the incoming low-byte value encountered during a hash. A different value requires another scan of that block, so one traversal does not prepare all possible values. The cache holds at most 2,048 blocks per game state: old blocks no longer in the current state are evicted first, and additional blocks use the ordinary hash path if all retained blocks are active. Cold, changing, or highly varied surfaces can still require substantial sequential hashing.
- Measured on Node 24.21.0 against `origin/main` (identical state hashes): 60 direct 640×480 drawing operations plus a complete state hash took about 2.5 s before and about 48–51 ms after in steady rounds (61–73 ms for the first, cold round); a frame of 60 `fillrect`s over four 640×480 canvases plus a hash took about 4.8 s before and about 88 ms (median) after; a tick that edits four high-entropy 640×480 surfaces while the state prefix changes took about 630 ms before and about 61 ms (median) after. The 50 ms budget for 60 direct 640×480 drawing operations plus a complete state hash is **not reliably met**: the cold first round exceeds it and steady rounds sit at its edge.
- Hashing shared inline program owners now reuses canonical fragments and lazily learned exact FNV transitions while checking each owner's current fields for direct edits. Non-ASCII, nested or unusually large owners use the ordinary hash path; newly encountered incoming byte lanes still need a full scan. The per-state cache retains at most 32 program fragments of at most 256 Ki characters each and discards inactive entries when full, so changing or varied workloads may receive less benefit.
