# Documentation and public website: install, make, import, debug, package and share games

## Description

User documentation, contributor and developer documentation, and a public website that publishes them. The user documentation covers getting started, installing or opening the product on each shipped host, the project workflow in each editor tool, RPGCode, file formats and importing legacy and TK2 games, debugging, packaging and sharing, troubleshooting, and reference material. The website adds an information architecture, navigation and search, an accessible responsive layout, per-release versions, examples and screenshots, and a publishing step that runs when a release is cut, with documentation QA (link, anchor, terminology, accessibility, sample and drift checks) as a required check. The normative spec stays where it is, in `docs/spec/`; the user documentation links to it and never restates it. Every statement about the product is checked against the built product.

## Outcome

A person who has never seen the project can find the site, install or open the product on a host that ships, make a first game, import an old game, debug a script and package and share the result, using only the published documentation; a contributor can set up the repository and write a plugin from the developer documentation. The CAP-19 success check, a reader who did not write the documentation completing each flagship task from the published site against the release build, is the signal.

## Done when

1. The user documentation has a page set for each task the released product supports: getting started; installing or opening on each shipped host; the project workflow and each editor tool that ships; the RPGCode guide and the built-in reference; file formats and importing legacy and TK2 games, with what does not carry over; debugging and testing scripts; packaging and sharing; troubleshooting and requirements; and reference (project layout, keys, settings, glossary, what is new). A task the product does not ship is not described as available.
2. Every command name, menu label, setting, file name, format name and code sample in the user documentation is checked against the built product or the normative spec: RPGCode samples run through the real VM and language server, built-in names resolve in the shipped registry, and a gate fails on drift between the documentation and the surface inventory.
3. A first-time reader who did not write the documentation walks each flagship task (install or open on each shipped host, make a first game, import a legacy game, debug a script, package and share) from the published site against the release build, and the walkthrough is recorded with its findings fixed.
4. The contributor and developer documentation (setup, repository tour, running the gates, the clean-room rules, writing a command pack or plugin, extension points) is followed once on a clean clone and every command in it runs.
5. The public website is published from the repository by a documented step when a release is cut, serves the documentation for the current and earlier releases, is responsive, meets the accessibility target the owner rules, has navigation and search, and its documentation QA job is a required check that blocks a merge.
6. The normative spec and the user documentation are separate documents with separate rules: no user page restates a normative rule, no page is copied or translated from the legacy user guide, and screenshots and example projects use only original or licensed assets and are regenerated by a documented step.

## Boundaries

Documentation content and the website that publishes it: the information architecture, the site build, hosting set-up, versioning, search, the documentation QA gates, the surface inventory and the sample-verification harness, screenshots and example projects, and the landing, about and status pages. Not the normative spec (`docs/spec/`, ADR 0007), the architecture decision records, `docs/guardrails.md` or `docs/editor-features.md`, which stay engineering documents; not the product's in-app help and tutorial screens (epics editor-foundation and editor-p2 own the editor surfaces, this epic supplies the content and the link contract); not the product's release process (npm publish, PWA deploy, extension publish, signing, store accounts), which no epic owns yet (decision D-13); not translations; not a community platform, forum, game gallery or game hosting service; not publishing recovered community material or naming living people without their say (README promise).

- Touch point: the static site generator, hosting provider and domain - none chosen; owner: this epic (decisions D-3 and D-4 of the inception proposal)
- Touch point: the editor hosts, runner and CLI - consumed to produce screenshots and to extract the surface inventory; owner: epics editor-foundation, web-runner-packaging, rpgcode-tooling
