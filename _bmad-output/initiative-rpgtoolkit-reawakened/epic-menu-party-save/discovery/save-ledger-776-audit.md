# Saved-game ledger and continuation audit (#776)

**Status: discussion draft, not an approved field contract.** Audit baseline: `origin/main` at `05309c31`. This is a planning artifact, not a normative spec or implementation. Candidate labels below are proposals for review, not owner-approved classifications. Source citations use repository paths and line numbers at that baseline. No legacy GPL source was consulted.

**Historical audit:** the owner accepted the subsequent [ledger recommendations](save-ledger-776-proposal.md) on 2026-10-29. The candidate labels and open-decision language below describe this earlier audit, not the current ruling. Engineering proof and implementation remain outstanding.

## Direction and boundaries

- **Savable state is the umbrella**: it must retain the game ledger *and* any continuation needed to resume supported execution. The **ledger is a subset**, not a replacement for the save or for a runnable snapshot. Exact contents and hash projection remain open.
- Preserve existing normal-save script continuation and the plain-data step-machine guarantee in G1 (`docs/guardrails.md:21-34`). A smaller ledger must not silently discard running scripts, waits, or their referenced data. G3 requires the RNG state as part of save state (`docs/guardrails.md:57-62`).
- **Checkpoint recovery is separate from ordinary Save/Load.** Do not infer rollback, recovery fallback, or recovery behavior from this audit. No promise is made to restart a battle; that is a separate unresolved decision, not a consequence of defining a ledger. No changes are proposed to battle/recovery ticket ledgers here.
- The user supplied a Toolkit 3.1 baseline: party, stats, inventory, globals, board placement/items and background threads. It is a scope starting point, not approval of a specific mapping. The existing clean-room save-format spec describes the historical binary format (`docs/spec/formats/save-game.md:3-9,259-340`); this audit did not independently verify that historical description. In particular, its field 26 note says threads come from field 37, while its table numbers items 37 and threads 38–46 (`:287-314`); reconcile as a documentation question, not a conclusion from legacy source.

## Actual format and hash today

`GameState` has 20 schema-versioned sections plus compiler identity (`packages/core/src/save/state.ts:59-81,86-132`). `snapshot()` canonicalizes the whole state (`save/snapshot.ts:76-79`). A game save is canonical JSON over the same tree with `audio` replaced by a playback projection (`save/game-save.ts:15-19`; `audio/save.ts:10-21,37-51`). It is **not** currently a separate ledger, and contains no embedded ledger hash. Canonical JSON uses sorted keys and FNV-1a 64-bit over UTF-8 for `hashState`, with tagged non-finite values (`canon/canon.ts:1-8,180-233`).

The tick report calls `hashGameState` (`engine/engine.ts:2368-2370`), which hashes the runtime tree except `audio.settings` and `vm.stepCounters` (`save/hash.ts:202-216`). It includes surfaces and other runtime/presentation state. Its input is not the same as the game-save blob: the blob uses the audio playback projection and retains step counters. A future ledger hash requires an explicit domain, version, canonical projection and purpose; it must not be confused with replay hash or a checksum of save bytes. FNV-1a is non-cryptographic and **not authentication or a security boundary** (`docs/spec/formats/save-game.md:38-45`).

## Validation, loading and compatibility

`restoreGameSave` parses JSON and checks compiler first, validates audio projection shape and duplicate names, applies current audio configuration, calls `restoreGameState`, and checks the saved audio tick (`save/game-save.ts:62-123`). `restoreGameState` applies section migrations and checks sections, battle and shapes (`save/snapshot.ts:820-864`). Party/inventory/menu migration checks v1 empty placeholders and validates current exact keys and actor/item references (`menu/migrate.ts:15-39`; `menu/model.ts:67-147`). Validation is **not exhaustive for all nested fields**: `validateShape` requires objects for several sections without deeply checking them (`save/snapshot.ts:781-804`); version handling differs by section, with VM/input/triggers accepting `>=` at migration entry while actors/battle/menu reject unsupported versions (`save/snapshot.ts:86-91,229-232,247-248,261-262`; `menu/migrate.ts:23-26`). These are audit observations, not a claim that a malformed example was executed.

Normal Save waits for other in-flight host requests to settle, clones the state and answers its own saved request before serializing (`engine/engine.ts:1105-1119`). Load builds package layers, compiles saved programs, verifies handles and rolls back on failure (`engine/engine.ts:730-770,1216-1235`). The documented owner rule refuses a different compiler for the entire save; a changed source restarts only its thread after compatibility checks (`docs/spec/formats/save-game.md:74-103`). A ledger projection must not weaken that normal-save contract or misrepresent it as checkpoint recovery.

## Existing tests versus verification gaps

The following are source-inspected test cases, **not tests run for this audit**:

- `packages/core/test/script-state.test.ts:50-129,133-171`: section shape, mid-yield snapshot round-trip, compiler mismatch, malformed VM and changed-source restart cases.
- `packages/core/test/save-continuation.test.ts:53-125`: no game save captures an unanswered host request.
- `packages/core/test/menu-state.test.ts:74-118,683-705,720-734`: section validation and owner restoration; v1 migration and rejection cases. `actors.test.ts:271` covers actor record snapshot/hash round-trip.
- `packages/core/test/audio-restore.test.ts:97-130` distinguishes snapshot audio/hash settings and game-save playback projection. `battle-cues-engine.test.ts:404,578` covers one full-engine battle save and an image effect before saving; `battle-fresh-load.test.ts:246-249,306-309` covers fresh-engine continuation. These are existing continuation coverage, **not** a battle-restart commitment.

No separate approved ledger projection or ledger-hash test contract is established by those tests. After owner decisions, acceptance needs field-by-field positive/negative hash vectors, order and non-finite cases, duplicate/derived-state consistency, current and prior save migration, malformed nested data and cross-references, deterministic resumed behavior and compatibility refusal/rollback. Exercise board-item changes, current/off-board persistence, object/closure reachability, multiple background threads and waits, as well as script-visible surfaces and audio. Prove recovery separately; do not substitute its tests for ordinary Save/Load.

## Responsibility and decisions to resolve

Once reviewed, pass concrete validation and migration requirements to #593; do not duplicate its implementation here.

Owner review must decide: (1) authoritative field paths and duplicated/derived owners, including actor and board scope; (2) exact normal-save continuation dependencies and reconstruction, including VM reachability, waits and host requests; (3) ledger hash purpose, version, included fields, identity and collision policy, separately from replay and security; (4) asset/package changes and failures, with no silent loss of progress; (5) prior-save migration and cross-section validation; and (6) independent checkpoint-recovery behavior and the separate battle question. Until ruled, the table remains candidate analysis, not a narrowed persistence promise.
