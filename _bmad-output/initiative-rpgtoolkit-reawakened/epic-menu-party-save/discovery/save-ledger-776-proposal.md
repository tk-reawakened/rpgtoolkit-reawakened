# Proposed saved-game ledger contract (#776)

**Proposed for owner review — not approved, normative, implemented, or a change to the current save format.** Based on `origin/main` `e8f12639`, the [audit](save-ledger-776-audit.md), and [recovery direction](../recovery-direction.md). User-supplied 3.1 baseline is party, stats, inventory, globals, board placement/items and background threads; this is product direction, not independently verified historical detail or approval of the mapping below. No GPL source was consulted. Paths and lines below are relative to `packages/core/src/` unless otherwise named.

## Recommendation in brief

Treat **savable** as the umbrella: game ledger plus the continuation and other state needed for a supported normal save. The **ledger** is the validated, game-owned progress subset, not a replacement for a VM snapshot. Retain today's normal save and plain-data VM continuation, including active threads and G1 behavior (`docs/guardrails.md:21-34`). Add an independent versioned ledger projection and ledger hash only after approval; do not repurpose `TickReport.stateHash` or change existing bytes in this planning PR.

Use small, searchable field labels in the state owner's existing declarations or an adjacent central registry: **L** = ledger and savable; **C** = savable continuation, not ledger; **D** = derived or package/config data, not ledger; **R** = runtime/diagnostic, not ledger. A field can be both L and C: it is hashed once through L and retained for continuation. A label describes *ownership*, not a command to delete anything from current saves. Plain comments, a table, or types are sufficient; no decorator or annotation framework is mandated. A required exhaustive projection and tests, not the comment syntax, enforce the eventual contract. New fields need an explicit classification by their owner; default to retaining existing save behavior until classified, not to discarding data.

## Capture and hash proposal

1. Capture at one coherent state boundary from the same state generation as the normal save or checkpoint candidate; do not read independently across ticks. The existing normal-save request waits for other in-flight requests, copies the state and answers its own request in the saved clone (`engine/engine.ts:1105-1119`). Keep that unchanged. Checkpoint-specific stable eligibility, interrupted writes, and waiting/active operations belong to #777; this proposal does not equate the normal-save gate with recovery safety.
2. Project exactly the L rows above into an immutable plain-data value. Validate all section versions, types, bounds, references, unique identities, equipment consistency and board/sprite authority **before** accepting it; retain field locations in diagnostics. A versioned projection must explicitly resolve presence vs absence and include every mapped field, including actor/item counters, object/cell tables and `rng`. Preserve array order, existing object key-order metadata and non-finite script values using the existing canonical tagging; never serialize `undefined` as an implicit value.
3. Hash the canonical tagged JSON of an envelope such as `{ domain: "tkr.game-ledger", version: 1, ledger: <projection> }` using the existing RFC 8785-style canonicalizer and FNV-1a 64-bit (`canon/canon.ts:1-8,180-233`). Include the projection version in the digest to prevent silent cross-version comparisons. This is a **non-cryptographic progress identity / accidental-change detector**, not authenticity, tamper resistance, collision-proof equality, or a complete replay-state hash. Compare only under the same domain, version and compatible game identity. A stronger authenticated integrity mechanism, if needed, is separate.
4. Store the projection, version and hash with the savable/checkpoint candidate, validate/recompute on read, then promote only according to the recovery transaction (#783). A hash match is not a substitute for schema, cross-reference, package and source validation. Continue using the existing `hashGameState` for tick/replay comparisons; it excludes `audio.settings` and `vm.stepCounters` but otherwise hashes runtime state (`save/hash.ts:202-216`). It is neither this ledger hash nor a checksum of game-save bytes.
5. Ledger restore must precede board re-entry under the existing recovery direction, with flags visible to the entry program and player-controlled resume (`../recovery-direction.md:7-11`). Only stable checkpoints defined by #777 qualify; if the proposed ledger lacks an authoritative item position, listener, pending operation or required asset needed for safe recovery, retain the previous validated checkpoint instead of inventing success. This is not a battle restart promise.

## Migration and tests to hand off after approval

Current saves are a canonical full `GameState` except the audio projection (`save/game-save.ts:15-19`); no separate ledger or ledger hash exists. #778 implements an approved projection and migration; #593 remains the owner of untrusted load validation, section migrations, hydration order and script continuation. Do not assign duplicate restore implementations. Define old-save extraction and handling of malformed/conflicting duplicates explicitly; do not label a legacy blob validated simply because it parses. The current validator checks some sections more deeply than others (`save/snapshot.ts:781-804`), and section future-version gates differ (`save/snapshot.ts:86-91,229-232,247-248,261-262`). Compiler mismatch remains whole-save refusal and changed source a separate thread-restart rule (`docs/spec/formats/save-game.md:74-103`).

Source-inspected existing tests cover mid-yield and compiler mismatch (`packages/core/test/script-state.test.ts:58-129`), no unanswered host request (`packages/core/test/save-continuation.test.ts:53-125`), party/inventory validation and old section migrations (`packages/core/test/menu-state.test.ts:89-118,720-734`), and audio projection versus hash (`packages/core/test/audio-restore.test.ts:97-130`). They do not prove the new projection. Implementation acceptance should add exact projection and hash vectors for each L field and C/D/R non-influence, ordered arrays and absence/tagged-number cases, same-domain/version determinism, actor/item/closure references, board duplicate conflict and missing assets, old-save migration, transaction failure and rollback, plus uninterrupted versus normal-save resumed script behavior and independent recovery tests. Never replace G1 snapshot continuation tests with ledger-only tests. No tests were run for this planning proposal.

## Minimal owner decisions

1. **Approve or amend the table and conservative scope?** Recommended: all live actors and whole VM object/cell tables are ledger data, despite possible transient-state/hash sensitivity, until a proven narrower ownership/reachability model exists. Confirm that current-board item placement/edits and trigger progress belong in ledger. No historical exact-field claim is implied.
2. **Approve or amend hash purpose and policy?** Recommended: versioned, domain-separated FNV-1a 64-bit canonical ledger projection for progress comparison/accidental-change detection only; preserve the separate runtime replay hash and use a stronger separate mechanism if security is required.
3. **Approve the failure-first migration/authority principle?** Recommended: resolve board-item and equipment authority explicitly; reject conflicting or unresolvable data rather than silently losing progress. Exact board/sprite mapping and listener/asset reconstruction are engineering proof obligations, with unsafe recovery checkpoints ineligible under #777, not a promise of unsupported behavior.

If accepted, record the resulting ruling in the owning normative specification and update #593/#778 requirements before implementation. Recovery checkpoint eligibility, battle treatment and the paused re-entry sequence remain with #777/#779; this proposal neither decides them nor closes #776 automatically.
