# Accepted saved-game ledger contract (#776)

**Owner accepted the recommendations on 2026-10-29** (“all the others are perfect as written”). This is a ruling, not a claim that the ledger, hash, migrations or recovery are implemented. Fields marked U and the named validation, reachability and reconstruction proofs remain engineering obligations; approval does not decide those details by fiat. Normative contract: [`docs/spec/formats/save-game.md`](../../../../docs/spec/formats/save-game.md#game-ledger-and-savable-continuation). Based on `origin/main` `e8f12639`, the [audit](save-ledger-776-audit.md), and [recovery direction](../recovery-direction.md). The user-supplied 3.1 baseline is context, not independently verified historical detail. No GPL source was consulted. Paths and lines below are relative to `packages/core/src/` unless otherwise named.

## Recommendation in brief

Treat **savable** as the umbrella: game ledger plus the continuation and other state needed for a supported normal save. The **ledger** is the validated, game-owned progress subset, not a replacement for a VM snapshot. Retain today's normal save and plain-data VM continuation, including active threads and G1 behavior (`docs/guardrails.md:21-34`). The accepted separate versioned ledger projection and hash are future implementation; do not repurpose `TickReport.stateHash`.

Use small, searchable field labels in the state owner's existing declarations or an adjacent central registry: **L** = ledger and savable; **C** = savable continuation, not currently proposed as ledger; **D** = derived or package/config data, not ledger; **R** = runtime/diagnostic, not ledger. **U** means the ledger boundary is unresolved and needs engineering evidence. A field can be both L and C: it is hashed once through L and retained for continuation. None of these labels permits a meaningful game-authored mutation to be reset to an asset default: C or D alone does not prove reconstruction is safe. Plain comments, a table, or types are sufficient; no decorator or annotation framework is mandated. An explicit projection and tests, not comment syntax, enforce the eventual contract. Retain current save behavior until each field is classified and safe recovery is proved.

## Capture and hash proposal

1. Capture at one coherent state boundary from the same state generation as the normal save or checkpoint candidate; do not read independently across ticks. The existing normal-save request waits for other in-flight requests, copies the state and answers its own request in the saved clone (`engine/engine.ts:1105-1119`). Keep that unchanged. Checkpoint-specific stable eligibility, interrupted writes, and waiting/active operations belong to #777; this proposal does not equate the normal-save gate with recovery safety.
2. Project approved L fields into an immutable plain-data value from the **same serialized candidate** that will be read back. Validate section versions, types, bounds, references, unique identities, equipment consistency and board/sprite authority before accepting it, with located diagnostics. Complete the unresolved sprite-mutation and persistent-object reachability rules before calling the ledger complete. Explicitly resolve absence and include approved fields and `rng`; preserve array order, object key-order metadata and tagged non-finite script values. Never serialize `undefined` as an implicit value.
3. Hash the canonical tagged JSON of an envelope such as `{ domain: "tkr.game-ledger", version: 1, ledger: <projection> }` using the existing RFC 8785-style canonicalizer and FNV-1a 64-bit (`canon/canon.ts:1-8,180-233`). Include the projection version in the digest to prevent silent cross-version comparisons. This is a **non-cryptographic progress identity / accidental-change detector**, not authenticity, tamper resistance, collision-proof equality, or a complete replay-state hash. Compare only under the same domain, version and compatible game identity. A stronger authenticated integrity mechanism, if needed, is separate.
4. Make the savable/checkpoint candidate the **single authoritative mutable state**. On readback validate that candidate, derive its ledger projection again, and recompute its versioned hash from that projection before recovery promotion (#783). Persisting a separate projection is optional only as immutable derived data: compare it exactly with the projection derived from that same readback and reject any mismatch; never independently mutate or trust it as a second store. A hash match is not a substitute for schema, cross-reference, package and source validation. Continue using `hashGameState` for tick/replay comparisons; it is neither this ledger hash nor a checksum of game-save bytes.
5. Ledger restore must precede board re-entry under the existing recovery direction, with flags visible to the entry program and player-controlled resume (`../recovery-direction.md:7-11`). Only stable checkpoints defined by #777 qualify; if the proposed ledger lacks an authoritative item position, listener, pending operation or required asset needed for safe recovery, retain the previous validated checkpoint instead of inventing success. This is not a battle restart promise.

## Migration and tests to hand off

Current saves are a canonical full `GameState` except the audio projection (`save/game-save.ts:15-19`); no separate ledger or ledger hash exists. #778 implements an approved projection and migration; #593 remains the owner of untrusted load validation, section migrations, hydration order and script continuation. Do not assign duplicate restore implementations. Define old-save extraction and handling of malformed/conflicting duplicates explicitly; do not label a legacy blob validated simply because it parses. The current validator checks some sections more deeply than others (`save/snapshot.ts:781-804`), and section future-version gates differ (`save/snapshot.ts:86-91,229-232,247-248,261-262`). Compiler mismatch remains whole-save refusal and changed source a separate thread-restart rule (`docs/spec/formats/save-game.md:74-103`).

Source-inspected existing tests cover mid-yield and compiler mismatch (`packages/core/test/script-state.test.ts:58-129`), no unanswered host request (`packages/core/test/save-continuation.test.ts:53-125`), party/inventory validation and old section migrations (`packages/core/test/menu-state.test.ts:89-118,720-734`), and audio projection versus hash (`packages/core/test/audio-restore.test.ts:97-130`). They do not prove the new projection. Acceptance should cover field/hash vectors, ordered arrays and absence/tagged numbers, object/cell reachability and cycles, persistent changes to sprite speed and other properties despite changed assets, candidate-readback/projection mismatches, duplicate-board conflicts, missing assets, migration and rollback. Demonstrate that foreground-local-only objects do not perturb the ledger while globally reachable closures survive. Prove normal-save continuation and recovery independently; never replace G1 snapshot tests with ledger-only tests. No tests were run for this planning proposal.

## Accepted player-facing rulings

The owner accepted these separate recommended defaults; the unresolved technical mapping and proofs above remain open:

1. **Keep the progress a game has changed.** Recommended: party, stats, inventory, flags, current-board placement and game-modified properties such as movement speed survive recovery; changing a game asset must not silently reset those values. If the engine cannot establish which value is authoritative, it should not claim that checkpoint is safe.
2. **Keep normal saves resumable.** Recommended: normal Save/Load continues running scripts exactly under the existing compatibility rules. A recovery checkpoint is separate and should not depend on a foreground program being halfway through an instruction. Engineering must prove which data belongs to persistent game values versus temporary program execution; the owner need not choose object or cell IDs.
3. **Compare progress, not authenticate it.** Recommended: a versioned, domain-separated ledger hash detects ordinary differences in the selected progress data; it is not a security check or the existing replay hash. Use a separate stronger mechanism if authentication is needed.
4. **Never choose silently between conflicting saves.** Recommended: one saved candidate is authoritative; derive and validate its ledger on readback. Reject inconsistent derived copies or unresolvable values rather than discarding progress. Checkpoint eligibility and any battle-specific behavior remain separate decisions.

The ruling is written through to the owning normative specification. #593 retains load/continuation ownership and #778 implements approved ledger gaps; neither implementation nor audit acceptance criteria are closed by this ruling. Recovery checkpoint eligibility, battle treatment and paused re-entry remain with #777/#779.
